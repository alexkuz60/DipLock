# DipLock frontend (Vite + React + TS)

Дев-сервер и сборка UI для бэкенда FastAPI.

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173 (проксирует /api на :8000)
npm run test       # Vitest (jsdom)
npm run typecheck  # tsc --noEmit
npm run lint       # ESLint
npm run build      # сборка в ../backend/app/static/ui (раздаётся FastAPI по /ui/)
```

Бэкенд должен быть запущен:

```bash
cd ../backend && venv/bin/uvicorn app.main:app --reload --port 8000
```

Адрес бэкенда для dev-прокси переопределяется переменной `VITE_BACKEND_URL`.

## Слои результата во вьюере

Слои — это результат предподготовки (зоны артефактов, границы эпох, штриховка отброшенных),
нарисованные **DOM поверх canvas-треков uPlot** (`app/sections/viewer/TrackLayers.tsx`). Так зона
остаётся кнопкой: клик даёт детали, а зум только пересчитывает позиции через `timeToX`, не трогая
canvas. Геометрия и фикстура — в `shared/lib/viewerLayers.ts` (чистые функции, покрыты тестами).

Пока стадии `artifacts`/`epochs` не подключены к серверу (срез 2.7), слои берутся из
детерминированной фикстуры `demoLayers` (`source: 'demo'`) — она одинакова между запусками, поэтому
тесты и сравнение «до/после» не шумят. Границы эпох считаются из параметра «длина эпохи», а не из
результата, — сетка живая уже сейчас. Цвета зон — токены темы (`--color-artifact-*`), заливка через
`color-mix`, hex в JS не дублируется.

## Таблица локализации (срез 4)

Раздел `/table` — **представление результата**, а не второй расчёт: он читает `useDipoleCalc().result`
и **не делает ни одного запроса** (`fetch` не вызывается — это фиксирует тест). Поэтому сортировка и
состав колонок — чистая перерисовка:

- чистая логика — `shared/lib/tableRows.ts`: `TABLE_COLUMNS` (эпоха, пик GFP, MNI x/y/z, полушарие,
  амплитуда, GOF, поле Бродмана), `localizationRows`/`tableRows`, `sortRowsByEpoch`, `cellText`,
  `rowTooltip`;
- настройки просмотра — `shared/state/tableParams.ts` (направление сортировки по эпохе и видимость
  колонок, персистятся; результат задачи — нет, он в `dipoleCalc`);
- компоненты — `app/sections/table/LocalizationTable.tsx` (семантическая `<table>` со «липкой» шапкой),
  `LocalizationTableSection.tsx` (состояния: нет записи / нет результата / пустой результат / таблица
  с подписями), `LocalizationTablePanel.tsx` (сортировка, колонки, справка по результату).

Что важно в поведении: строки — **все точки результата**, включая точки без MNI (координаты «—», они
не наводятся на проекции, но в таблице показаны: «все результаты» это все); полушарие выводится из
знака MNI x (x > 0 — правое, RAS-раскладка) и это написано в подсказке колонки; колонки ROI нет, пока
ROI не считается — пустая колонка читалась бы как «не определено». Порог «КД ≥ X нАм» из раздела
«Диполи» таблицу **не фильтрует** (он параметр отображения проекций) — о расхождении говорит подпись.
Если параметры расчёта изменили после расчёта, таблица предупреждает «параметры изменены — результат
не пересчитан» (отпечаток `calcSignature`/`resultSignature` в `dipoleCalc`), но числа не подменяет и
пересчёт не запускает. Фильтры, поиск, виртуализация, клик по строке → диполь и экспорт выборки —
следующий срез.

## Правило обработки данных

UI **не запускает расчёт сам**. Правка параметра только складывает выбор в стор раздела
(`shared/state/edfParams.ts`), а расчёт идёт отдельной задачей строго по кнопке
(`markApplied()` фиксирует снимок параметров, для которого получен результат). Пока результат
не получен или параметры изменились, панель показывает это статусом в блоке «Запуск».

Кнопки стадий в тулс-хедере (`EdfRecalcButtons`) ставят задачу `POST /recordings/{id}/preprocess`
(`stage=filter|artifacts|epochs`), опрашивают прогресс через `GET /jobs/{id}` и кладут результат в
слои вьюера (`layers.source === 'result'`). Снимок параметров берётся в момент запуска
(`stageSignature` → `markStageApplied(stage, signature)`), поэтому правка параметра во время задачи
честно показывает «параметры изменены».

**Ожидание задачи — одно на весь UI** (`shared/lib/jobPolling.ts`, A10): `waitForJob` опрашивает
`GET /jobs/{id}` до `succeeded`, отдавая каждый опрос в `onTick`, а токен запуска раздела
(`createRunToken`) отменяет устаревшее ожидание — новый расчёт, сброс раздела и «Закрыть запись»
делают прежние ответы неактуальными (`isCancelled`). Своих копий поллинга и своих токенов в сторах
нет: новая задача = пара методов клиента (`recordingJob(kind)` в `shared/api/client.ts`) плюс вызов
`waitForJob`.

Планируемый функционал разделов — в `docs/ui.md` (корень репозитория).

## Интерактив вьюера (срез 2.9) и разметка эпох (срез 2.10)

- **Навигация по окну.** Кнопки `<<` `<` `>` `>>` в шапке листают окно на его ширину или прыгают в
  начало/конец записи. Команда идёт не напрямую, а через состояние: `requestNav(command)` кладёт в
  `edfRecording` пару `{command, seq}` с монотонным `seq`, а `TrackStack` применяет только новую
  команду (`handledNavSeqRef` инициализируется текущим `seq`, поэтому повторное монтирование вьюера
  не проигрывает старую команду). Сервер окно не пересчитывает — это чистая перерисовка кадра.
- **Курсор** ставится кликом и живёт до следующего клика (мышь его не таскает). Клик после
  панорамирования и клики по кнопкам (названия каналов, стрелки разворота, зоны артефактов)
  игнорируются, поэтому перетаскивание окна не сбивает курсор.
- **Разворот трека.** Стрелка под названием канала разворачивает трек на высоту видимой области,
  повторный клик — сворачивает; остальные треки уезжают в скролл. Высота берётся из `ResizeObserver`
  (в jsdom — фолбэк `TRACK_HEIGHT`). Само название канала — переход в раздел «ЭЭГ» этим каналом
  (`useEegParams.setChannel` + `navigate('/eeg')`), кнопки в шапке EDF для этого нет. Разворот и центр
  окна живут в локальном состоянии вьюера: это параметры отрисовки, они не обесценивают стадии и не
  переживают выход из раздела.
- **Оверлеи внутри прокручиваемого контента** (срез 2.11). Абсолютный потомок скролл-контейнера
  скроллится вместе с содержимым, но его `inset-y-0` считается по высоте *видимой области*: линия
  курсора, будучи ребёнком контейнера, при прокрутке вниз обрывалась на середине стека. Поэтому
  линия курсора живёт в `data-testid="viewer-content"` и тянется на весь стек, а подпись времени и
  карточка выделенной зоны «липнут» к верху области (`position: sticky` внутри `absolute inset-0`
  высотой во весь контент). Проверяйте прокруткой в браузере: jsdom раскладку не считает.
- **mute/solo убраны** — видимость каналов задаётся чекбоксами панели «Каналы».
- **Скроллбар неотключаемый**: утилита `.scroll-y-always` (`overflow-y: scroll` +
  `scrollbar-gutter: stable`) в треках и панели опций, чтобы полоса не
  «дёргалась» при смене раздела и показывала долю окна в записи. Ширина полосы (20 px, срез 2.11)
  задана только через `::-webkit-scrollbar`: стандартные `scrollbar-width`/`scrollbar-color` в
  Chrome отключают legacy-псевдоэлементы, поэтому для Firefox они вынесены в
  `@supports (-moz-appearance: none)`. Скролл существует только потому,
  что каркас (`AppShell`) ограничен высотой окна: grid со строкой `grid-rows-[minmax(0,1fr)]` —
  проверяйте такие правки в браузере, jsdom раскладку не считает.
- **Разметка эпох привязана к нарезке, которой считался результат** (`gridEpochLength`): у слоя
  `source: 'result'` сетка берётся из `epochLengthMs` (= `epoch_length_ms` стадии «эпохи»),
  у фикстуры — из параметра панели. Так смена длины эпохи в панели не переносит штриховку
  отброшенных эпох на другой участок записи; расхождение видно пилюлей «разметка эпох: N мс».
- **Ручные пометки эпох** (`Ctrl`+двойной клик по треку): `toggleEpochMark` инвертирует итоговый
  вердикт эпохи (снять штриховку алгоритма или поставить свою) и хранит пометку **интервалом на
  таймлайне** в сторе записи (`edfRecording.epochMarks`, не localStorage). Пометки видно даже при
  выключенной штриховке, счётчик — в полосе вьюера, снять все — кнопкой «Снять» в панели «Эпохи».
  Счётчик считает **пометки** (`epochMarks.length`, срез 2.11), а не ячейки сетки: после смены длины
  эпохи одна пометка накрывает несколько эпох новой нарезки, но остаётся одной пометкой — так же
  считает и панель «Эпохи».
  В расчёт на сервере правки пока не уходят (`docs/ui.md` §12).

## Экспорт окна (срез 2.8)

Экспорт **клиентский**: данные уже в браузере (кадр пирамиды сигналов, слои, окно просмотра),
поэтому сервер не участвует — ни запросов, ни пересчёта того, что видно на экране. Кнопки PNG/CSV
живут в полосе окна вьюера (`app/sections/viewer/ExportActions.tsx`), рядом со шкалой времени: им
нужны окно, видимые каналы и canvas'ы треков (регистрируются в `TrackStack` через
`canvasesRef`/`registerCanvas` — ref, а не состояние, чтобы регистрация холста не перерисовывала
вьюер).

- **CSV** — длинный формат `time_sec,channel,min_uv,max_uv`: строка на пару «временная корзина ×
  канал», то есть ровно то, что показывает окно. Кадр уровня ×k уже прорежен сервером, и выдавать
  его за полноразрешённый сигнал нельзя — «одного числа на точку» в файле нет.
- **PNG** — снапшот окна, а не только линии сигнала: canvas'ы uPlot склеиваются с подписями каналов,
  шкалой времени, зонами артефактов, сеткой эпох и легендой. Canvas не читает CSS-токены, поэтому
  цвета разрешаются через `getComputedStyle` с hex-fallback.
- Имя файла `<запись>-win<from>-<to>s-<level>.csv|png` (уровень 0 → `full`), имя записи
  санитизируется: экспорт не должен уметь записать файл за пределами каталога загрузок.
- Если браузер не умеет `toBlob` (или холст не закодировался), кнопка показывает ошибку текстом:
  пустой файл хуже отказа.

Форматы и геометрия — в чистом `shared/lib/exportWindow.ts` (без React и zustand, DOM трогает только
`drawSnapshot`), доставка файла — в `shared/lib/download.ts`. Оба покрыты тестами
(`exportWindow.test.ts`, `download.test.ts`, `viewer/ExportActions.test.tsx`).

## Раздел «Диполи»: проекции, спектр и расчёт (срезы 3.1–3.4)

Раздел показывает **геометрию, анатомию и результат**: реальный срез МРТ, силуэт головы, схему
среза MNI, поля Бродмана и точки диполей из результата задачи. Расчёт запускается **только кнопкой**
в шапке (`POST /recordings/{id}/dipoles`), спектр — своей кнопкой в выдвижной панели
(`POST …/spectrum`); правка параметров панели ничего не запускает и не делает запросов (единственный
фоновый запрос — `/meta` за ссылкой на срезы и длинами эпох). Картинки срезов и топокарт грузит и
кэширует сам браузер по URL.

- **SVG, а не canvas.** Цвета берутся токенами темы прямо в атрибутах
  (`stroke="var(--color-mri-dipole)"`, токены `--color-mri-*`), поэтому тема меняется без правок
  геометрии. Реальный срез томографии — тоже SVG-элемент: `<image href>` с PNG сервера, то есть canvas
  не понадобился и для пиксельной заливки. Там, где цвет нужен в JS (canvas-снапшот), —
  `shared/lib/theme.ts` (`themeColor` через `getComputedStyle` с hex-fallback, `withAlpha`).
- **Одна геометрия на все проекции** (`shared/lib/mriProjections.ts`): **единый масштаб мм/пиксель**
  (`PROJECTION_SCALE`, 1.5 px/мм, срез 3.3) — фигуры прямоугольные (`projectionBox`), анатомия не
  растягивается; `x = 0` — срединная сагитталь, `y = 0` / `z = 0` — через AC–PC, поэтому границы
  `MNI_BRAIN_BOUNDS`
  асимметричны и центр фигуры не совпадает с началом координат (срез 3.2 заменил условные границы на
  **реальные** — bounding box маски мозга fsaverage; те же числа лежат в
  `backend/app/services/mri_slices.py`, совпадение проверяет `tests/test_mri_slices.py`). Клик по
  фигуре даёт точку **в плоскости своего среза** (`pointFromProjectionClick`), а наводит все три —
  `applyPointToSlices`; срез «прилипает» к именованным (`snapSlice`, допуск `SLICE_SNAP_TOLERANCE_MM`).
  Компоненты математику не дублируют, второго «невидимого» слоя для мыши нет: попадание в поле
  Бродмана считается по тем же эллипсам, что нарисованы (`brodmannAreaAt`).
- **Срез МРТ — картинка, а не расчёт в браузере** (`shared/lib/mriSlices.ts`): срез квантуется к
  сетке тома (`snapSliceToGrid` — «половина вверх», как в бэкенде: срезов в UI 0.1 мм, а тома — 1 мм,
  иначе браузер кэшировал бы десять копий одной картинки), URL уходит с версией ассета (`?v=…` — после
  пересборки тома старая картинка не «залипнет»), прямоугольник картинки равен прямоугольнику
  плоскости, поэтому `<image>` растягивается на всю фигуру (`preserveAspectRatio="none"`). Недоступная
  картинка показывается текстом под фигурой, а в состоянии хранится **URL** неудачной картинки, а не
  флаг: смена среза — новый URL, и попытка повторяется.
- **Слои** `mri` / `head` / `mni` / `brodmann` / `dipoles` включаются чекбоксами панели (порядок и
  подписи — `shared/state/dipoleParams.ts`); выключенный слой **не рисуется**, а не прячется
  прозрачностью. Пока срез МРТ включён и загрузился, условная схема среза не рисуется: настоящая
  анатомия вместо фикстуры (силуэт головы остаётся — это граница черепа, которой в маске мозга нет).
  Срез наводится кликом (на глаз, с прилипанием) и `shared/ui/SliceScrubber.tsx` в панели (точно, с
  маркерами `x = 0`).
- **Фикстуры детерминированы** (`demoHeadContours`, `demoSliceStructures`, `demoBrodmannAreas` — без
  ГПСЧ): картинка одинакова между рендерами, тестами и повторным монтированием. Реальный срез уже
  есть; реальные поля Бродмана придут из `PALS_B12_Brodmann` (`surface_cache.py`), контур головы — из
  `mri/seghead.mgz`.
- **Слой диполей — из результата задачи** (срез 3.4): на сервер уходят параметры расчёта (полоса
  1–40 Гц, длина эпохи, порог reject, шаг сетки), задача отвечает точками (`shared/lib/dipolePoints.ts`:
  `dipoleLayerFromScan`), и точки без MNI в слой **не попадают** (`mni_coords: null` — fsaverage
  недоступен; раздел показывает предупреждение, а не рисует точку «где-то»). Расчёт — **быстрый
  режим** (`method: 'fast_grid'`): одна точка на эпоху в пике GFP и перебор узлов объёмной сетки
  (~7 мм) на сферической модели — позиция кратна шагу, и метка режима видна в шапке и панели.
- **Порог «КД ≥ X нАм» — параметр отображения**, а не расчёта: `thresholdDipoleLayer` фильтрует слой
  перед отрисовкой, `hiddenByThreshold` считает скрытые, а результат задачи остаётся нетронутым.
  Правка поля в шапке (или в панели) не делает запросов.
- **Спектр — отдельная задача, топокарты — готовые картинки** (`shared/lib/spectrum.ts`): URL
  топокарты собирается из **результата** (`spectrumQueryOf`) — полоса, notch, длина эпохи, порог
  reject и версия ассета, потому что ETag картинки сервер считает по этим же параметрам; `histogramBars`
  нормирует полосы по максимуму, `psdPolyline` рисует PSD по логарифмической шкале, а «—» вместо нуля
  означает «мощность не измерена» (диапазон вне полосы фильтра, `power_uv2 === null`). Сами топокарты —
  `<img>` с PNG сервера: пиксели браузер не считает.
- **Выдвижная панель** — новый проп `drawer` у `AppShell` (полоса между шапкой и рабочей областью):
  открыта одна панель за раз (`dipoleCalc.view`), кнопки — в тулс-хедере раздела (`DipolesToolActions`),
  содержимое — `DipolesDrawer` с `BandTopomaps` (топокарты) или `FftHistogram` (полосы + PSD).

## Воспроизведение траектории (срез 3.7)

- **Кадр — это отображение, а не измерение.** В результате задачи одна точка на эпоху (пик GFP),
  поэтому «движение» строится по сетке нарезки: время сессии непрерывно, эпоха —
  `floor(t / epoch_length_ms)`, длительность — `n_epochs_total × epoch_length_ms` (×1 — реальное время
  записи). Внутри эпохи кадр **интерполируется** к следующей эпохе: позиция по прямой, направление
  момента по дуге (slerp), амплитуда линейно (`shared/lib/playback.ts`). Промежуточных положений никто
  не считал, и UI об этом говорит: интерполяция идёт только между соседними эпохами с точками (кадр
  отброшенной эпохи пуст), а на паузе и при покадровом шаге кадр равен измеренной точке своей эпохи.
- **Состояние команд — в сторе, время — нет.** `dipoleCalc.playback` хранит `playing`, `speed`
  (×1/×2/×4), `epochIndex`, `active` и `seekSeq`; непрерывное время кадра живёт в локальном состоянии
  часов `app/sections/dipoles/playbackClock.ts`, а в стор уходит **только смена эпохи**. Иначе 60
  обновлений в секунду перерисовывали бы облако из сотен точек во всех трёх проекциях.
- **`seekSeq` — как `navRequest.seq` во вьюере EDF.** «Покадрово» на границе записи не меняет номер
  эпохи, но команда обязана быть видна часам: счётчик растёт монотонно. Сдвиг часов
  (`setPlaybackEpoch`) счётчик не двигает и при том же номере стор не трогает вовсе.
- **Маркер кадра обновляется контекстом.** `PlaybackFrameProvider` оборачивает ряд проекций, проекции
  приходят ему как `children` (те же элементы) — React пропускает их перерисовку, и за кадр
  перерисовывается только `FrameMarker` внутри SVG. Тест `PlaybackFrame.test.tsx` фиксирует, что
  статичный сосед рисуется один раз за сотни кадров.
- **Кадр виден и понятен без легенды**: гало (второе кольцо акцентным цветом) при неизменном размере
  кольца позиции (Ø 10 px — правило «все позиции — одинаковые кольца»), облако приглушено
  (`FRAME_DIM_OPACITY`), выделенный кликом диполь не приглушается, порог «КД» действует и на кадр, и на
  шлейф. За кадром тянется **затухающий шлейф** (`trailSegments`): отрезки между измеренными точками
  соседних эпох за последние 10 секунд сессии (окно во времени, а не в числе эпох), гаснущие от кадра к
  хвосту; через разрыв шлейф не тянется, рисуется в слое позиций и под маркером, толщина — как у луча
  (`TRAIL_STROKE_PX`), цвет — токен `--color-mri-dipole` (шлейф принадлежит тому же диполю).
  Конец записи — стоп на последней эпохе, play с последней эпохи — сначала; уход из раздела
  останавливает часы, но кадр остаётся. Хоткей `Space` работает только в разделе «Диполи» (в других
  разделах Space — обычная прокрутка, в полях ввода игнорируется).
  Расчёт и спектр сбрасываются при загрузке новой записи и при «Закрыть запись» (`useDipoleCalc.reset()`
  из `edfRecording`), потому что результат принадлежит конкретной записи.

## Раздел «ЭЭГ»: трек и спектрограмма (срез 5)

- **Две половины одного канала**: сверху сырой трек (canvas, огибающая min/max из той же пирамиды
  сигналов записи `GET /recordings/{id}/signals`, что рисует вьюер EDF), снизу — спектрограмма STFT.
  Второй вьюер здесь не пишется: `EegTrackView` считает огибающую `frameEnvelope` из `viewerMath`,
  поэтому пики артефактов видны на любом зуме так же, как в EDF.
- **Спектрограмма — числа, а не картинка.** Сервер отдаёт метаданные и сетку float32 контейнером
  `DPS2` (`shared/lib/eegSpectrogram.ts` разбирает её в `SpectrogramGrid`). Палитра, окно дБ и
  сглаживание — параметры **просмотра**: они считаются из уже полученных чисел и не делают запросов
  (`paletteLut`, `dbToUnit`, `smoothSpectrogram`). Пиксели красит `ImageData` с таблицей цветов, а не
  `fillRect` на ячейку: сетка бывает 257 × 5000.
- **Одна геометрия на обе половины** (`shared/lib/eegView.ts`): `plotLeftPx`/`plotRightPx` дают
  совпадающие границы графика, `EEG_VALUE_W` — общий столбец значений справа, `EEG_TIMELINE_H` —
  полоса времени (она **одна**, внутри верхней половины — под треком). Поэтому общий курсор и шкалы
  совпадают без «согласований на глаз».
- **Время в пиксель считают `plotTimeX`/`plotTimeAtX`**: они добавляют левый столбец и берут ширину
  области графика, а не холста. Полоса времени раньше мерила шкалу всей шириной (вместе со столбцами
  подписи и значений) — её метки и курсор уезжали от графика. Полосы таймлайна теперь нет у
  спектрограммы: вторая ось дублировала первую и читалась как «вторые часы» (в «обзоре» — вся запись),
  поэтому высота `EEG_TIMELINE_H` вычитается только из холста трека.
- **Клик по спектрограмме даёт время и частоту**: время — в общий курсор, частота — в горизонтальную
  линию (`markerHz`, локальное состояние половины) со значением в правом столбце. Частота клика
  считается `yToFreq` — обратной к `fmaxToY`, которой линия рисуется. Если в «обзоре» точка клика
  лежит вне окна трека, окно подтягивается к ней: иначе курсор был бы виден только на спектрограмме.
- **Клик по треку даёт время и уровень сигнала**: время — в тот же общий курсор, уровень — в
  горизонтальную линию уровня (`levelUv`, локальное состояние) со значением у линейки мкВ
  (`yToAmplitudeUv` — обратная к `valueToY`). Обе горизонтали рисует общая `drawHorizontalMarker`.
  Метки принадлежат точке клика: новый клик, клик по полосе времени и листание окна начинают с чистого
  листа, двойной клик по любой половине снимает метки обеих (точка клика у половин одна).
- **Нулевая линия сигнала** (`drawNullLine`) — пунктир по середине трека: шкала симметрична, ноль ровно
  по центру, смещение сигнала видно без чтения делений. Рисуется под огибающей.
- **Рамка видимой части записи** (`windowFrame` + `drawWindowFrame`) — у половины, чьё окно шире окна
  трека: в «обзоре» видимый на треке отрезок обведён, остальное приглушено, внутри рамки стоит общий
  курсор. Когда окна совпадают, рамки нет — её место занимает весь график.
- **Пиксели спектрограммы — `putImageDataAt`**: `ctx.putImageData` игнорирует трансформацию
  контекста, поэтому `ImageData` набирается в разрешении холста (`canvasScale`) и вставляется при
  единичной трансформации. Иначе на экране с `devicePixelRatio ≠ 1` картинка занимала лишь `1 / dpr`
  области графика (спектрограмма обрывалась до правой линейки). Проверяет `eegCanvas.test.ts`.
- **Окно времени — в сторе** (`eegParams.windowCenterSec`), а не в компоненте: его видят обе
  половины, и в режиме «связано» спектрограмма следует за треком. Команда листания из шапки идёт
  через `eegNav` с монотонным `seq` (как `navRequest` в EDF), колесо и перетаскивание области — теми
  же функциями, что вьюер (`zoomWindow`/`panByPixels`/`anchoredCenter`).
- **Контролы окна общие с EDF** (`shared/ui/ZoomNavControls`): `EdfZoomSelect` и `EegWindowControls` —
  тонкие обёртки своих сторов. Уровень зума в `eegSignature` не входит: это параметр просмотра.
- **Правило обработки то же**: правка любого контрола ничего не запускает. Спектрограмма считается
  кнопкой в шапке (`POST /recordings/{id}/spectrogram`), панель и раздел показывают «параметры
  расчёта изменены», если отпечаток результата разошёлся с текущими параметрами. Фильтр расчёта —
  форма `calcFilter` (полоса + сетевой 50/60 Гц), как в «Диполях».
- **Жесты в тестах — `user.pointer`**: jsdom без `PointerEvent` не передаёт координаты через
  `fireEvent.pointer*`, а прямоугольники элементов нулевые, поэтому компоненты считают геометрию от
  пропа ширины/высоты (в браузере они совпадают с CSS-размером холста).
