# Правила ведения документации

> Появился 17.09.2026 вместе с разрезкой `AGENTS.md` (106 КБ → ≤15 КБ) и `docs/ui.md`
> на тематические файлы. Цель — чтобы знание **не терялось** и **не раздувало** входной файл агента.

## Карта документации

| Файл | Для кого | Что внутри | Размер ориентира |
|---|---|---|---|
| `README.md` | человек | как запустить проект, что уже работает | свободный |
| `AGENTS.md` | ИИ-агент | обзор, команды, структура, конвенции, **карта ссылок** | ≤ 15 КБ |
| `concept.md` | агент + человек | зачем проект: миссия, критерии метода, способности и их статус, кандидаты | живой, уточняется |
| `docs/data-blocks.md` | агент + человек | кирпичики: блоки данных, их ключи, поля, паспорт (до структуры БД) | по кирпичам |
| `docs/rules/*.md` | агент + человек | правила по темам (вьюер, диполи, ЭЭГ, атлас, API, фронт-состояние, данные, безопасность, тесты, эти правила) | по теме |
| `docs/ui.md` + `docs/ui/*.md` | человек + агент | функциональная спецификация UI (номера § сохранены), дорожная карта | по разделу |
| `docs/data_map.md` | агент + человек | какие данные материальны: пайплайн → артефакт → носитель → ключ инвалидации → жизненный цикл | по пайплайну |
| `docs/history.md` | человек | журнал закрытых работ (сюда переезжает «Выполнено» из `todo.md`) | растёт вниз |
| `audit.md`, `audit-2026-09.md`, `audit_strategy.md` | агент | долг и находки (F17–F21 и далее); `audit_strategy.md` — аудит по направлениям: вердикты, альтернативы (N1–N40) | не режем |
| `todo.md` | человек + агент | **только открытые** задачи, коротко | ≤ 1 экран |
| `frontend/README.md` | человек | детали фронтенда | свободный |

## Правила

1. **Длинные блоки не пишем в `AGENTS.md`.** Новое правило по теме — в `docs/rules/<тема>.md`
   + одна строка-ссылка в карте ссылок `AGENTS.md`. `AGENTS.md` — вход, а не хранилище.
2. **Новый срез работы = правило + тест.** Правило идёт в rule-файл своей темы (или создаёт новый),
   тест — рядом с кодом (см. `docs/rules/tests.md`). Срез без правила или без теста — не закрыт.
3. **Данные — в `docs/data_map.md`.** Новый кэш, файл результата, таблица БД, поле в сайдкаре или
   клиентское хранилище → строка в `data_map.md` в том же срезе. Иначе следующий рефакторинг снова
   будет выяснять, «что где лежит» заново.
4. **Перенос текста — дословно.** При разрезке/слиянии документов блоки переносятся без правок
   (скриптом по номерам строк), а не пересказываются: пересказ теряет найденные краевые случаи
   («почему именно 20 px», «почему `evenodd`»).
5. **Номера § в UI-спецификации не меняем.** На них ссылаются код и тесты
   (`docs/ui.md §8`, `§3.3`, `§9`, `§12`); после разрезки § живут в `docs/ui/*.md`,
   а индексация — в `docs/ui.md`.
6. **Числа — только измеренные и со ссылкой.** «7 мм — 2.2 с» допустимо с указанием записи/даты
   замера; источник чисел — журнал шагов (`GET /api/v1/journal`, формат — `docs/data_map.md` §9):
   замеры стоят в продакшен-пути, поэтому цифру из документа можно воспроизвести повторным расчётом
   на том же файле, а не «профилировщиком на машине автора». Обещания вместо замеров не пишем.
   Когда понадобятся запросы («сколько всего шло на `psd`»), агрегация идёт в **отдельный**
   `data/analytics.db` — проекцию журнала, а не в таблицы основной БД и не вместо `logging`
   (решение владельца 17.09.2026, `docs/data_map.md` §9).
7. **Пути, URL и env-имена проверяем.** Упоминаете файл/эндпоинт/переменную — убедитесь, что они
   существуют (`grep`/`ls`), иначе документ врёт с первого дня. Проверка ссылок:

   ```bash
   # все пути docs/rules + docs/data_map существуют?
   # (подсказка: шаблоны с {…} проверку не проходят — это ожидаемо, смотрите на остальные строки)
   grep -rhoE '`(backend|frontend|docs|data)/[A-Za-z0-9_./-]+`' AGENTS.md docs/rules docs/data_map.md \
     | tr -d '`' | sort -u | while read -r p; do [ -e "$p" ] || echo "НЕТ: $p"; done
   ```
8. **`todo.md` обновляется вместе с закрытием задачи.** Закрыл пункт — перенёс (дословно) в
   `docs/history.md` со датой среза. Список задач не должен расти в журнал.
9. **Смыслы и кирпичики — отдельно от кода и друг от друга.** Зачем проект и что он обязан
   уметь — `concept.md` (новый шаг плана либо закрывает способность из его §6, либо явно помечен
   инфраструктурным; меняется методика или смысл — сначала правка `concept.md`, потом код). Из
   каких блоков собираются данные — `docs/data-blocks.md` (кирпич описывается **до** кода, а
   структура БД — после согласования кирпичиков). Появился кирпич или поле — строка в реестре
   `docs/data-blocks.md`; появился носитель (кэш, файл, таблица) — строка в `docs/data_map.md`
   (п. 3).
