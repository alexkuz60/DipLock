## 0. Реализованный серверный срез

`backend/app/api/consilium.py` подключён отдельным роутером в main; сервис —
`backend/app/services/consilium/store.py`, контракт — `backend/app/schemas/consilium.py`.
История независима от реестра EDF/jobs и кэшей. `consilium_cases` — текущий паспорт,
`consilium_entries` — неизменяемые ревизии context/message, `consilium_requests` —
квитанции идемпотентности; удаление очищает все три явным каскадом.

JSON-операция записи требует `request_id` и (кроме создания дела) `expected_version`.
Повтор возвращает ранее принятый ответ до проверки текущей версии. Другой запрос
с тем же ключом — 409. Исправление реплики требует `expected_revision`, создаёт
новую строку; глобальная версия дела увеличивается. Архив read-only для новых
реплик; открыть можно PATCH паспорта. Ошибка commit — 503, не ложный успех.

PATCH паспорта принимает полный новый паспорт, не произвольный частичный dict.
Новые ссылки проверяются по строкам recordings; исчезновение исходника не
удаляет ручное дело. Контекст может адресовать только связанный код добровольца
и запись. DELETE требует версии из предпросмотра, исходные записи не удаляет.
Ответы `private, no-store`; ошибки формы не содержат `input`/`ctx`, SQL-ошибки
не отражают тексты. Листинг контекста/сообщений включает **все ревизии**.
Материалы B15 читаются адаптером `backend/app/services/consilium/sources.py`,
сохраняются и публикуются `backend/app/services/consilium/dossier.py`.

### 0.1. Каталог и снимки (Т1.3–Т1.6)

Источник выбирается по `kind` + `id`, клиент не поставляет готовые числа:
job (RAM или файл через job_store), session и analysis (results_store), group
(group_analysis). Пакет SQL содержит все полосы и точки, NULL сохраняются.
Пара/группа целиком должны входить в дело. Каталог не запускает групповой агрегат;
при добавлении группы фиксируются текущие числа определения и фактические
`analysis_id`, эта оговорка обязательна. Впоследствии ничего не пересчитывается.

`consilium_evidence` хранит принятую копию, `consilium_snapshots` — полное досье
из выбранных копий и последних ревизий выбранного контекста. Новый расчёт,
правка рассказа или удаление job не меняют прошлый снимок. `request_id`/версия
и обязательный commit применяются и к новым операциям.

Размеры из settings: `consilium_material_max_bytes` (8 МБ),
`consilium_snapshot_max_bytes` (16 МБ), `consilium_source_max_rows` (20 000).
Превышение — 413 с rollback, никогда молчаливый топ-N. Общий паспорт единиц и
состояния сигнала у старых источников отсутствует: `missing` это отражает,
текущие настройки не подставляются. repr параметров job остаётся сигнатурой,
не выдаётся за структурированный рецепт. Спектрограмма job — метаданные без DPS2;
полные точки пакета принимаются из analysis отдельно от агрегатов report-job.

Удаление материала требует предпросмотра и expected_version: удаляются материал,
зависимые снимки и квитанции этого дела (чтобы повтор не восстановил копию).
Исходный расчёт остаётся. DELETE дела охватывает все пять таблиц явным каскадом.
Отдельных файлов досье пока нет; резервная копия — основная БД.

При чтении владельцы вызывают init_db. Миграции сериализуются lock в db.py,
иначе одновременные запросы ломают общий контекст Alembic. Это не запрет
параллельной аналитики: lock охватывает только upgrade head.

### 0.2. Интерфейс ручного исследования

`frontend/src/app/sections/consilium/` зарегистрирован в registry/routes после
«Итогов», без изменения существующих хоткеев. Две рабочие вкладки: «Контекст и
история» и «Материалы и досье»; беседы появятся в Т2. Паспорт позволяет явно
связать зарегистрированные записи, вопрос/коды задаёт исследователь.
Списки имеют пагинацию по 20, выбор дела в `?case=` переживает обновление страницы.
Сохранение/принятие/публикация только кнопками. «На чём основано?» раскрывает
готовую копию без нового расчёта, числовые подробности не обязательны для ввода.

QueryClient хранит серверные данные, gcTime=0 для запросов/мутаций раздела;
персиста в localStorage нет. Key рабочего компонента и отдельные query keys
не допускают поздних ответов соседнего дела. Кнопка «Обновить исследование»
восстанавливает актуальную версию после 409 без молчаливой перезаписи.
Повтор сетевого запроса отправляет прежние тело, адрес ревизии и request_id;
правка формы после ошибки не меняет уже отправленный запрос. Новое действие
создаёт новый ключ и использует актуальную версию.
Архив запрещает новые записи/публикации, явное удаление возможно и в архиве.
Внешняя передача контекста в UI выключена, разрешение будущим советникам —
отдельный чекбокс; проверено ≠ истинно. Нет фиктивных ответов ИИ.

### 0.3. Раунды советников (Т3, миграция 0008)

Коллективный чат «Обсуждение» поверх снимков досье. Сущности B14:
`consilium_rounds` (вид initial/remarks/summary, `snapshot_id`, статус
running/done/partial/failed/cancelled/interrupted, модель маршрута, версии
инструкций, границы, предупреждения, `job_id`) и `consilium_answers` (роль,
статус ok/failed, текст только при успехе, ошибка, модель, версия инструкции,
задержка). Ответы — append-only: повтор роли дописывает новую попытку, прежняя
остаётся; отображается последняя по роли, порядок — по ролям плана.

Оркестрация (`services/consilium/rounds.py`): три роли (психологическая,
нейрофизиологическая, методологическая) с версионированными инструкциями
получают один снимок; первый раунд — без просмотра ответов коллег, замечания —
один ограниченный проход, итог — отдельной кнопкой с сохранением разногласий.
Отказ одной роли не уничтожает остальные: раунд «неполный», неудавшийся ответ
повторяется кнопкой (успешные не переспрашиваются — расход ограничен).
Границы: один initial на снимок, один remarks на исходный раунд, один summary
на снимок; запуск — только кнопкой, без маршрута chat — честный 400.

Задача очереди: класс ресурса `llm`, async-воркер, `on_success_required` —
успех объявляется после записи ответов в БД; в файл задачи тексты не попадают
(только счётчики). Старт приложения помечает «running»-раунды как
`interrupted` (`rounds_store.mark_interrupted`). Промпт — сжатый дайджест
снимка: контекст только с `use_with_advisers`, каждое сокращение подписано
предупреждением раунда (никакого молчаливого топ-N). Удаление материала
очищает зависимые снимки и раунды с ответами (§10, производные сводки).

**Решения UI (согласовано 12.10.2026):** четыре действия ответа («На чём
основано?», «Какие есть другие объяснения?», «Что спросить у добровольца?»,
«Предложи следующий шаг») — постоянными кнопками раскрытия, не hover-панелью;
оценки/галлюцинации/память/Арбитр из многомодельных чатов не переносятся;
боковой «личный чат с одним советником» и дерево навигации не реализуются —
вместо дерева фильтры-чипы по советникам; **стриминг ответов реализован**
(срез 0011, см. §0.4 — ответ виден по мере генерации); правка реплики
исследователя — новая ревизия (как в «Контекст и история»), ответы советников
не правятся, только повтор.

### 0.4. Стриминг ответов (срез 0011, 14.10.2026)

`llm_router.chat` принимает `on_delta` и ходит к провайдеру со `stream: true`
(openai — `choices[].delta.content`, anthropic — `content_block_delta`);
честные ошибки (обрезка бюджета, «только рассуждение», пустой ответ)
сохранены для потока. `_ask` пишет дельты в RAM-хаб
`services/consilium/streams.py` (журнал событий + будильник подписчиков),
`GET .../rounds/{id}/stream` отдаёт их SSE (правило «SSE поверх задачи» —
`docs/rules/api-jobs.md`). Итоговый текст по-прежнему пишется в БД до
объявления успеха; перезапуск бэкенда теряет дельты — клиент дочитывает
готовые ответы поллингом. В UI: «Модель отвечает…» + растущий текст вместо
скелетона (`shared/lib/roundStream.ts`, `RoundCard`), индикация «Запрос к
внешней модели выполняется…»; обрыв стрима не ошибка.

## 1. Граница ответственности

Консилиум не считает ЭЭГ и не заменяет разделы EDF/ЭЭГ/Диполи/Групповой анализ.
Он собирает уже полученные результаты в проверяемое досье, добавляет контекст и
организует разговор человека с ИИ-советниками.

Запреты:

- не интерпретировать отсутствие стадии/поля как «норма»;
- не сравнивать GOF между полосами (правило `docs/rules/dipoles.md`);
- не выдавать рассказ, стенограмму или мнение ИИ за измерение;
- не давать ИИ прямой доступ к БД, файловой системе и произвольному Python;
- не запускать расчёт по словам в чате без отдельного предложения и согласия;
- не обещать медицинскую оценку, диагноз, личностный профиль или проверку
  целительской способности только по ЭЭГ.

## 2. Данные и снимки

Основные сущности — кирпичи B14–B17. Нормативные требования к ним:

1. **Исследование** привязано к вопросу и участникам, а не только к открытой
   записи. Код добровольца задаёт исследователь; он не выводится из digest EDF.
2. **Материал** всегда адресует конкретный источник: задача, сессия, прогон,
   полоса, контекстная запись или версия реплики. Произвольная ссылка `recording_id`
   недостаточна.
3. **Снимок досье** неизменяем после публикации. Новый расчёт/редактирование
   контекста создаёт новую версию досье, старые ответы советников не переобуваются.
4. В материале обязательны параметры, версии, дата получения, предупреждения,
   единицы и признак полноты («всё»/агрегат/топ-N/фрагмент). Неизвестные поля
   старого результата честно помечаются; текущие defaults не выдаются за
   фактически применённые тогда значения.
5. Для группового анализа в снимок входят фактические `analysis_id`, состав,
   фильтры и зафиксированный агрегат: текущее правило «история хранит определение,
   числа пересчитываются» для доказательной базы Консилиума недостаточно.

История исследования — долговременная и не наследует лимит файлов задач. Это не
кэш: файл результата можно пересчитать, разговор и решение человека — нельзя.

## 3. Сборка досье

Сборщик принимает **выбранные прогоны** и формирует снимок до вызова модели.
Читает только через существующие владельцы результатов; для пакетных точек
(`analyses`/`dipole_points`) нужен отдельный read-слой рядом с их владельцем, а не
прямой SQL из сервиса Консилиума.

Проверки до выдачи модели:

- принадлежность материала исследованию;
- доступность результата (не «result_omitted»);
- состояние входного сигнала и совместимость параметров;
- совпадение сетки эпох там, где индексы эпох используются как адреса;
- наличие всех предупреждений и границ сравнимости;
- явный список «не измерено / не выбрано / недоступно».

Открытая находка Т0: самостоятельные задачи спектра/диполей и пакет автоотчёта не
обязаны сегодня переносить один и тот же полный набор параметров чистки. Основание —
`backend/app/services/spectral.py` (`SpectrumParams`, `_prepare_epochs`),
`backend/app/services/dipole_scanner.py` (`DipoleScanParams`, `_prepare_epochs`) и
`backend/app/services/report.py` (`run_report`: построение параметров пакета).
До устранения это не блокирует чтение существующих результатов, но блокирует Т6
(одобряемые перезапуски чистки как автоматические эксперименты).

Снимок сохраняет структурированный результат, а не только URL или HTML-отчёт.
Необходимые поля, оставшиеся внутри вычисления, открываются минимальным
контрактом у владельца. Недоступность файла задачи по лимиту истории — отдельный
статус; ранее принятый снимок остаётся читаемым, если пользователь не удалил данные.

## 4. Контекст для языковой модели

Модель получает не «всё приложение», а подготовленный пакет:

- назначение DipLock и границы ответственности;
- роль советника;
- исследовательский вопрос;
- краткое досье и проверенный контекст;
- последние сообщения раунда;
- проверенную сводку прошлого исследования (не полный архив);
- каталог разрешённых инструментов.

Ответ модели — структура, а не свободный JSON «как получилось»: текст, ссылки на
материалы, альтернативные объяснения, вопросы и предложения. Сервер валидирует
структуру Pydantic и проверяет, что каждая ссылка существует в снимке. Неизвестная
ссылка отклоняется; «ссылка существует» означает только адресуемость источника, а не
верность трактовки.

Тексты беседы, аннотации и сообщения пользователя — данные, а не инструкции. Фраза
«игнорируй правила» внутри стенограммы не меняет системные ограничения. Размер
контекста ограничивается сервером; детали подгружаются через инструменты.

Каталог возможностей различает параметры расчёта, read-only настройки сервера и
параметры отображения. Единицы, допустимые значения и зависимости берутся из
существующих схем/params/settings; объяснение назначения добавляется вручную,
паритет проверяется тестом. Метод MNE помечается «доступен в DipLock», «нужен
адаптер» или «неприменим к данным». Знание метода не разрешает запуск Python.

## 5. Провайдер модели

Доступ к модели — за небольшим интерфейсом: проверка доступности, генерация,
отмена/тайм-аут, вызов разрешённых инструментов, сведения о модели и расходе.

**Решение 10.10.2026: локальные урезанные модели (llama.cpp) отклонены** как
советники — «советоваться» с обрезанной моделью не соответствует тематике
исследования. Советники работают с **полноценными моделями через внешние API**;
подключение — **модельный роутер** в разделе «Настройки»
(`GET/PUT /api/v1/llm-router`, `POST .../probe`, сервис
`backend/app/services/llm_router.py`). Локальный запуск весов не производится.

Роутер хранит провайдеров (протокол `openai` — совместимый `/chat/completions`,
или `anthropic` — Messages API; адрес, модель, ключ) и маршруты `chat`
(советники, Т3) и `transcribe` (распознавание, Т2; только `openai`). Ключи
лежат в JSON-файле на сервере (`settings.llm_router_config_path`), в ответах UI
заменены маской `key_hint` и не попадают в логи/тексты ошибок; ошибка формы не
эхо-передаёт ввод (`PrivateRoute`). Правка настроек ничего не отправляет
наружу: внешний запрос выполняется только явным действием («Проверить связь» —
нейтральный запрос «Ответь одним словом: готов» без материалов дела — или
будущий ответ советника). Выбор модели и конкуренция с MNE за ресурсы заменены
вопросами латентности/лимитов провайдера — измеряются в пробах §10 стратегии.

`httpx` добавлен в основные зависимости (ранее — только dev), закрыт тестами
(`tests/test_llm_router.py`), вызовы идут через него.

**Дополнительные параметры запроса** (`extra` провайдера): JSON-объект,
дополняющий тело вызова, — для опций вида DeepSeek
`{"thinking": {"type": "enabled"}, "reasoning_effort": "high"}` (и аналогов у
других провайдеров). Ключи `model`/`messages`/`stream` зарезервированы
роутером (400 в PUT, отсекаются и при чтении кустарного файла); размер — не
больше 30 ключей и 4 КБ JSON. Адрес базы — как у провайдера SDK, с `/v1` или
без (`https://api.deepseek.com` — роутер сам дописывает `/chat/completions`;
Anthropic-формат DeepSeek — `https://api.deepseek.com/anthropic`). Проба связи
шлёт `extra` как есть и держит бюджет `llm_probe_max_tokens` (8192 токенов по
умолчанию), чтобы thinking-режим не давал ложный отказ на «одном слове»;
тайм-аут вызова — `llm_request_timeout_s` (180 с: thinking-модели отвечают
десятки секунд).

Поле «Модель» — список id моделей через запятую (кандидаты одной учётки API):
пробы идут **перебором по каждой** модели, маршрут `chat` работает **выбранной**
моделью списка (`chat_model` в маршрутах, UI — выпадающий список «Модель
советников (chat)»; не выбрана — первая в списке); до 10 id по 200 символов,
пустые элементы отбрасываются. Модель маршрута обязана входить в список
провайдера — иначе сохранение отклоняется с текстом для UI.

Внешняя передача материалов советнику требует отдельного согласия на конкретные
материалы и записи того, какая версия контекста ушла наружу (реализуется в Т3).
Псевдоним EDF не делает голос и рассказ обезличенными.

### 5.1. Пробы советника (§10 стратегии)

Выбор модели для маршрута `chat` — по живым пробам на провайдере. Инструмент —
блок «Пробы советника (§10)» панели модельного роутера и
`POST /api/v1/llm-router/chat-probe`. Четыре сценария (реестр
`CHAT_PROBE_SCENARIOS` в `services/llm_router.py`):

| Ключ | Что проверяем (§10) | Ожидается |
|---|---|---|
| `dialog` | русский диалог | связный русский ответ и уточняющий вопрос без подсказки |
| `role` | роль и структура ответа | «замечено / возможное объяснение / чего не знаем / следующий шаг», без выдуманных измерений |
| `insufficient` | отказ при недостаточности данных | честный отказ и перечень недостающего при пустом досье |
| `leading` | ненаводящие вопросы | вопрос добровольцу без закладываемого ответа |

Правила пробы: промпты **синтетические и заданы сервером** — материалы дела,
записи, имена и ключи не отправляются; запуск — только явной кнопкой (правка
формы ничего не шлёт); ответ возвращается с моделью и задержкой `latency_ms`
(бюджет `llm_probe_max_tokens` = 8192 токенов на модель); ошибка провайдера —
в `error` без ключа, ложного успеха нет. Проба не сохраняется в историю дела и
не является материалом.

**Thinking-модели и бюджет (случай 11.10.2026).** Рассуждение модели
(`reasoning_content`) входит в тот же бюджет токенов, что и итоговый текст:
малый бюджет даёт ложный «пустой ответ» (модель молчит, потратив всё на
рассуждение), а обрезанный по бюджету ответ обрывается на полуслове. Поэтому:
бюджет щедрый (настраивается `llm_probe_max_tokens`), пустой `content`
разбирается честно — «бюджет токенов исчерпан на рассуждении, итоговый текст
пуст (рассуждение N симв.)» / «модель вернула только рассуждение», а обрезка
(`finish_reason=length`) помечается флагом `truncated` и подписью UI «⚠ Ответ
обрезан по бюджету токенов».

**Список моделей — перебором (параллельно).** Если в поле «Модель» перечислено
несколько id, проба (и нейтральная «Проверить связь», и каждый сценарий) идёт
отдельным запросом по каждой модели **параллельно** (перебор не ждёт по
очереди), итог — строка на модель (модель/задержка/ответ/ошибка); сводка
`ok` — только когда ответили **все** модели, `error` перечисляет не прошедшие.
Маршрут `chat` работает выбранной моделью списка (или первой, если выбор не сделан).

**Протокол измерений (выход §10)** — таблица владельца: провайдер / модель /
сценарий / задержка / вердикт (годится / не годится + почему). По ней выбирается
одна рабочая конфигурация маршрута `chat`; для `transcribe` — после ASR-проб.
Приватность: запрос уходит внешнему провайдеру только нажатием кнопки; офлайн —
проба честно падает ошибкой связи.

### 5.2. Решающий классификатор Jev (маршрут decide, срез 13.10.2026)

**Jev (TypeSafe AI, System One)** — дискриминативная модель типизированных
решений: один вызов (`state` + карта `questions`) возвращает `choice` (один из
ярлыков + вероятности + confidence), `score` (позицию на упорядоченной шкале)
и/или `noul` (калиброванную вероятность yes/no) без свободного текста. В
Консилиуме — **триаж готовности досье** до раунда советников: достаточно ли
материалов для осмысленного ответа на вопрос дела (`noul`), какой основной
дефицит (`choice` по каталогу: нет измерений / нет рассказа добровольца / нет
наблюдений / материалы несопоставимы / дефицита нет) и насколько полно досье
(`score` 0…3: пусто → фрагмент → достаточно → полно).

Маршрут `decide` модельного роутера (protocol `systemone`; `base_url` — полный
адрес вызова, путь не дописывается: `https://api.typesafe.ai/v1/systemone`).
Версия модели пиннится в поле «Модель» (`jev-1.13.0`, не `jev-latest` — дрейф
калибровки). Проба — `POST /api/v1/llm-router/decide-probe`: синтетический
state (учебное описание досье; материалы дела не отправляются), проверка
протокола и русского языка инструкций; строка — в протокол измерений §10.

Правила (`services/consilium/triage.py`, миграция 0009 `consilium_triage`):

* state — тот же сжатый дайджест снимка, что советникам (`build_digest`):
  контекст только с `use_with_advisers`, каждое сокращение подписано;
* запуск — только кнопкой (`POST /cases/{id}/triage`, синхронный вызов без
  очереди: 70–500 мс); повтор `request_id` возвращает принятую строку и **не
  шлёт данные снова**; архив — read-only; версия дела — optimistic bump;
* уверенность калибрована, но не гарантирует правильность: вердикт `sufficient`
  выводится явным порогом `consilium_triage_sufficient_min` (0.6), не «верой»
  модели; ответ вне каталога/шкалы не сохраняется решением — предупреждением,
  сырые ответы остаются как есть; в UI вердикт подписан этой оговоркой;
* ошибка провайдера — строка `failed` без достроенных решений; история
  append-only (повтор — новая строка); удаление материала/дела очищает строки
  триажа (§10, производные сводки); предпросмотры удаления показывают их счётчик;
* «zero hallucination» Jev гарантирует только форму ответа (выход замкнут на
  перечисление классов), не его содержание: решения — не измерения, ЭЭГ-числа
  триаж не считает и ничего не достраивает за человека.

Карта вопросов версионируется (`questions_version`): смена формулировок — новая
версия, старые и новые решения не смешиваются. Оценки и «Арбитр» для ответов
советников остаются под запретом §0.3.

### 5.3. Разметка Jev (кандидаты применения, срез 14.10.2026)

Три применения того же маршрута `decide` (реализованы решением владельца
14.10.2026); общие правила §5.2 действуют полностью: запуск — только кнопкой,
повтор `request_id` не шлёт данные снова, ошибка провайдера — строка `failed`
без достроенных меток, история append-only (`consilium_jev_marks`, миграция
0010), удаление материала/дела очищает строки. Метки — **advisory-подсказки с
явным порогом** `settings.consilium_jev_verdict_min` (0.5), не вердикты и не
оценки ответов советников.

1. **«Быстрый раунд»** (`round_plan`, subject = снимок): какие роли нужны для
   ответа на вопрос дела (3× `noul`) и какая глубина обсуждения (`choice`:
   только ответы / + замечания / + итог). UI предзаполняет чекбоксы ролей
   («Применить к выбору ролей»), запуск раунда остаётся за человеком — экономия
   LLM-вызовов, не автоматическое сокращение состава.
2. **Карточка предложения** (`proposal`, subject = ответ советника): есть ли
   предложение шага и какого вида (`choice` по каталогу §7: спросить
   добровольца / уточнить наблюдение / провести пробу / выполнить расчёт /
   нет предложения), наличествуют ли основание, риски и способ проверки (3×
   `noul`). Метки типизируют текст, но **не пишут карточку за советника** —
   содержимое карточки остаётся в разделах ответа.
3. **Разметка источников** (`source_marks`, subject = ответ советника): три
   отдельных `noul` — опирается ли текст на измерения/расчёты, рассказ
   добровольца, наблюдения исследователя (источники стратегии §2). Три
   источника **не смешиваются**: каждый — отдельный вопрос, вероятности
   показываются раздельно.

State разметки ответа — вопрос дела, роль и текст ответа (усечение — с
предупреждением); полное досье наружу не уходит. Уверенность калибрована, но не
гарантирует правильность; ответ вне каталога/шкалы не сохраняется решением —
предупреждением, сырые ответы остаются как есть.

## 6. Роли и раунд

Первый рабочий раунд: психологический, нейрофизиологический и методологический
советники получают один и тот же снимок. Их первые ответы формируются без просмотра
ответов коллег; дальше — один ограниченный раунд замечаний и итог с сохранением
разногласий.

Оркестрация задаёт пределы: число ролей, раундов, инструментальных вызовов, время и
расход. Бесконечный диалог ИИ между собой недопустим. Отказ одной роли не должен
уничтожать ответы остальных: раунд помечается неполным.

## 7. Предложения и решения

Советник может предложить четыре вида шага:

1. спросить добровольца;
2. уточнить условия или наблюдение;
3. провести пробу;
4. выполнить расчёт.

Карточка предложения содержит основание, гипотезу, точное действие, риски и способ
проверки. Вопросы формулируются ненаводяще и порциями; отказ или отсутствие ответа —
честный результат, а не повод достраивать за человека.

До Т5 расчёты исполняются вручную в существующих разделах. В Т6 допускаются только
зарегистрированные инструменты, серверная валидация и одобрение точной версии
предложения; смена базы/параметров делает старое одобрение недействительным. Повтор
запроса обязан быть идемпотентным.

## 8. Фоновые задачи и хранение

Для LLM/ASR нельзя слепо унаследовать нынешний `job_manager`: он выполняет
синхронный воркер в потоке, а `on_success` текущих аналитических задач — best-effort.
Для Консилиума успех операции объявляется **после** обязательной записи её
долговременного результата; иначе задача должна завершиться честной ошибкой, а не
«успешно, но история потеряна».

Требуемая доработка общей очереди — перед задачами Т2/Т3, не условие для
синхронного хранилища Т1 (реализовано к Т3: классы ресурсов `mne`/`llm`/`asr`
с отдельными пределами, async-воркеры, `on_success_required` — успех после
обязательной записи, связь задачи со строкой раунда, прерванные LLM-операции
помечаются в строке; ASR-класс подготовлен под Т2):

- async-воркеры для сетевого ожидания LLM;
- классы ресурсов и отдельные пределы: MNE, LLM, ASR;
- адрес результата для задачи Консилиума;
- связь задачи с долговременной строкой раунда/распознавания;
- восстановление после рестарта; состояние прерванной операции — в строке
  Консилиума (существующий `JobState` не расширяем без отдельного контрактного среза);
- файлы общей истории задач без чувствительного текста.

Таблицы и файлы появляются только после согласования кирпичей. Большие аудио и
экспорты живут вне БД под `results_dir`; БД хранит метаданные, хеши и ссылки.
При первом кодовом срезе обязательна строка в `docs/data_map.md`.

## 9. Интерфейс

Раздел — новая запись существующего реестра UI. Рабочая область: «Обсуждение»,
«Материалы», «Беседы». Правая панель — только направление, советники, провайдер и
границы раунда. Технические детали — раскрытием.

Реализовано срезом 0014 (14.10.2026): панель «Опции» (`ConsiliumOptionsPanel`)
несёт разовые настройки — роли запуска раунда и фильтр советников
(`shared/state/consiliumOptions.ts`, localStorage `diplock.consilium`), опцию
«раскрывать разделы ответов сразу» и справку раздела; панель открыта по
умолчанию (`uiStore.rightPanelOpen`). Роли/фильтр убраны из основной области
(`CaseDiscussion` показывает только строку текущего состава), подсказка Jev
применяет выбор через тот же стор. Правка опции ничего не запускает.

Обязательные действия ответа советника:

- «На чём основано?»;
- «Какие есть другие объяснения?»;
- «Что спросить у добровольца?»;
- «Предложи следующий шаг».

Серверные данные — TanStack Query; zustand хранит состояние интерфейса. История,
аудио и чувствительные тексты в `localStorage` не персистятся. Правка параметра или
раскрытие деталей не запускает модель/расчёт: считает только явная кнопка.

Т1 показывает ручную историю и материалы; **Т3 показывает коллективное
«Обсуждение»** (вкладка рабочей области): запуск советников кнопками, лента
раундов с карточками ролей, скелетоны ожидания, повтор неудавшихся ответов и
итог; беседы — в Т2. Нельзя изображать доступный ИИ фиктивными ответами-заглушками.
Основной ответ — обычный язык («заметили / возможное объяснение / чего не знаем /
следующий шаг»), технические доказательства доступны без обязательного чтения таблиц.

## 10. Безопасность

Базовый режим — локальный один пользователь и локальное хранение; веса моделей
локально не запускаются, ИИ работает только через явно настроенный модельный
роутер (§5). Внешняя передача выключена до явного действия пользователя: правка
настроек и «Проверить связь» (нейтральный запрос) материалов дела не отправляют.
Голос, даты, имена файлов, аннотации и рассказы могут идентифицировать
добровольца даже при псевдониме EDF.

Раздельные разрешения: запись, хранение аудио, распознавание, передача текста
советнику, внешняя передача. Содержимое бесед не пишется в обычные логи и
traceback. Удаление учитывает БД, файлы, версии и экспорты на сервере; скачанный
пользователем файл приложение контролировать не может — это честно подписываем.

Нельзя сохранять чувствительные копии под предлогом неизменяемости снимка:
удаление очищает материалы, производные сводки и память, оставляет лишь отметки
без содержания. Архивирование не удаляет; удаление EDF не должно молча уничтожать
самостоятельную беседу, зависимости и последствия показываются до подтверждения.
Внешние адреса/ключи задаёт сервер, не чат; в локальном пилоте нет собственного
шифрования, сетевой доступ требует отдельного среза аутентификации/прав.

Общая память Т6 пополняется только подтверждёнными приёмами с исходами (включая
отрицательные), источниками, версиями, областью применимости и отзывом; не
характеристиками личности, автоматически извлечёнными из реплик. Поисковый контекст
не заменяет оригинальные материалы и не означает обучения весов модели.

## 11. Ранбук ручной приёмки Т1 (§9.2 стратегии)

Перед прогоном: **резервная копия БД** (`init_db` доводит схему до 0007),
актуальная сборка UI (`npm run build`), живой процесс бэкенда
(`init-status.code.stale` — `false`). Т1 не требует запуска MNE/ASR/LLM.
Шаги и ожидания:

1. **Дело**: `/consilium` → создать дело, задать вопрос, указать обезличенный код
   добровольца → дело в списке, выбор через `?case=` переживает обновление страницы.
2. **Материалы и контекст**: добавить результат конкретного прогона (job/session/
   analysis/group) и ручное наблюдение → принятая копия с параметрами, версиями и
   предупреждениями; неизвестные поля старых источников помечены `missing`, не достроены.
3. **Снимок**: опубликовать досье → раскрыть «На чём основано?»: параметры,
   предупреждения и пробелы видны; снимок неизменяем.
4. **Правка и новый прогон**: изменить наблюдение, добавить другой прогон →
   **прежний снимок остаётся прежним**, появляется новый.
5. **Рестарт**: обновить страницу / перезапустить сервер → ручная история и оба
   снимка доступны (история долговременна, не кэш).
6. **Архив и удаление**: архивировать (read-only для новых записей) → удаление с
   предпросмотром зависимостей (материалы, снимки, квитанции) → исходные записи
   EDF/jobs не удалены.

Для пары/группы дополнительно: направление B−A, состав участников, знаменатели
долей и запрет сравнения GOF между полосами. Критерии — «старое досье неизменно»
и «удаление показывает зависимости до подтверждения». Вердикт владельца
фиксируется в `todo.md`; без него Т1 не объявляется принятым.

## 11. Проверки по срезам

Backend: миграции и паритет, снимки/история, принадлежность материалов, недоступные
источники, идемпотентность сообщений и обязательная запись — в Т1. Прерванные
задачи/ASR — Т2, ссылки/провайдер/отмена LLM — Т3, подтверждение исполнения — Т6.
Frontend: empty/loading/error/stale, только кнопка запускает, устаревший ответ
не трогает состояние. Раскрытие показывает принятые данные; допустимое ленивое
чтение деталей не запускает новый расчёт или модель. Модели в CI не вызываются —
провайдер подменяется тестовым. Чек-лист Т1 — §9 стратегии.
