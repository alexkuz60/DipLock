# Консилиум: архитектура, данные, ИИ-советники

> План принят 10.10.2026. **Реализовано серверное основание Т1.1/Т1.2**:
> исследования, ручная история/контекст, версии и удаления (миграция 0006).
> Материалы, снимки, UI и ИИ ещё не реализованы. Смыслы — `docs/strategy/05-consilium.md`; кирпичики —
> `docs/data-blocks.md` (B14–B17); беседа и стенография — `docs/rules/interviews.md`.
> Нарушать существующие правила результатов нельзя: данные читаются через своих
> владельцев, схема БД — только alembic, новый контракт API — только Pydantic.

## 0. Реализованный серверный срез

`backend/app/api/consilium.py` подключён отдельным роутером в main; сервис —
`backend/app/services/consilium/store.py`, контракт — `backend/app/schemas/consilium.py`.
История независима от реестра EDF/jobs и кэшей. `consilium_cases` — текущий паспорт,
`consilium_entries` — неизменяемые ревизии context/message, `consilium_requests` —
квитанции идемпотентности; удаление очищает все три явным каскадом.

JSON-операция записи требует `request_id` и (кроме создания дела) `expected_version`.
Повтор возвращает ранее принятый ответ до проверки текущей версии. Другой запрос
с тем же ключом — 409. Исправление реплики требует `expected_revision`, создаёт
новую строку; глобальная версия дела увеличивается. Архив read-only для новых
реплик; открыть можно PATCH паспорта. Ошибка commit — 503, не ложный успех.

PATCH паспорта принимает полный новый паспорт, не произвольный частичный dict.
Новые ссылки проверяются по строкам recordings; исчезновение исходника не
удаляет ручное дело. Контекст может адресовать только связанный код добровольца
и запись. DELETE требует версии из предпросмотра, исходные записи не удаляет.
Ответы `private, no-store`; ошибки формы не содержат `input`/`ctx`, SQL-ошибки
не отражают тексты. Листинг контекста/сообщений включает **все ревизии**.
Поля B15 (Evidence/Snapshot) пока проектный Python-контракт, без persistence/API.

## 1. Граница ответственности

Консилиум не считает ЭЭГ и не заменяет разделы EDF/ЭЭГ/Диполи/Групповой анализ.
Он собирает уже полученные результаты в проверяемое досье, добавляет контекст и
организует разговор человека с ИИ-советниками.

Запреты:

- не интерпретировать отсутствие стадии/поля как «норма»;
- не сравнивать GOF между полосами (правило `docs/rules/dipoles.md`);
- не выдавать рассказ, стенограмму или мнение ИИ за измерение;
- не давать ИИ прямой доступ к БД, файловой системе и произвольному Python;
- не запускать расчёт по словам в чате без отдельного предложения и согласия;
- не обещать медицинскую оценку, диагноз, личностный профиль или проверку
  целительской способности только по ЭЭГ.

## 2. Данные и снимки

Основные сущности — кирпичи B14–B17. Нормативные требования к ним:

1. **Исследование** привязано к вопросу и участникам, а не только к открытой
   записи. Код добровольца задаёт исследователь; он не выводится из digest EDF.
2. **Материал** всегда адресует конкретный источник: задача, сессия, прогон,
   полоса, контекстная запись или версия реплики. Произвольная ссылка `recording_id`
   недостаточна.
3. **Снимок досье** неизменяем после публикации. Новый расчёт/редактирование
   контекста создаёт новую версию досье, старые ответы советников не переобуваются.
4. В материале обязательны параметры, версии, дата получения, предупреждения,
   единицы и признак полноты («всё»/агрегат/топ-N/фрагмент). Неизвестные поля
   старого результата честно помечаются; текущие defaults не выдаются за
   фактически применённые тогда значения.
5. Для группового анализа в снимок входят фактические `analysis_id`, состав,
   фильтры и зафиксированный агрегат: текущее правило «история хранит определение,
   числа пересчитываются» для доказательной базы Консилиума недостаточно.

История исследования — долговременная и не наследует лимит файлов задач. Это не
кэш: файл результата можно пересчитать, разговор и решение человека — нельзя.

## 3. Сборка досье

Сборщик принимает **выбранные прогоны** и формирует снимок до вызова модели.
Читает только через существующие владельцы результатов; для пакетных точек
(`analyses`/`dipole_points`) нужен отдельный read-слой рядом с их владельцем, а не
прямой SQL из сервиса Консилиума.

Проверки до выдачи модели:

- принадлежность материала исследованию;
- доступность результата (не «result_omitted»);
- состояние входного сигнала и совместимость параметров;
- совпадение сетки эпох там, где индексы эпох используются как адреса;
- наличие всех предупреждений и границ сравнимости;
- явный список «не измерено / не выбрано / недоступно».

Открытая находка Т0: самостоятельные задачи спектра/диполей и пакет автоотчёта не
обязаны сегодня переносить один и тот же полный набор параметров чистки. Основание —
`backend/app/services/spectral.py` (`SpectrumParams`, `_prepare_epochs`),
`backend/app/services/dipole_scanner.py` (`DipoleScanParams`, `_prepare_epochs`) и
`backend/app/services/report.py` (`run_report`: построение параметров пакета).
До устранения это не блокирует чтение существующих результатов, но блокирует Т6
(одобряемые перезапуски чистки как автоматические эксперименты).

Снимок сохраняет структурированный результат, а не только URL или HTML-отчёт.
Необходимые поля, оставшиеся внутри вычисления, открываются минимальным
контрактом у владельца. Недоступность файла задачи по лимиту истории — отдельный
статус; ранее принятый снимок остаётся читаемым, если пользователь не удалил данные.

## 4. Контекст для языковой модели

Модель получает не «всё приложение», а подготовленный пакет:

- назначение DipLock и границы ответственности;
- роль советника;
- исследовательский вопрос;
- краткое досье и проверенный контекст;
- последние сообщения раунда;
- проверенную сводку прошлого исследования (не полный архив);
- каталог разрешённых инструментов.

Ответ модели — структура, а не свободный JSON «как получилось»: текст, ссылки на
материалы, альтернативные объяснения, вопросы и предложения. Сервер валидирует
структуру Pydantic и проверяет, что каждая ссылка существует в снимке. Неизвестная
ссылка отклоняется; «ссылка существует» означает только адресуемость источника, а не
верность трактовки.

Тексты беседы, аннотации и сообщения пользователя — данные, а не инструкции. Фраза
«игнорируй правила» внутри стенограммы не меняет системные ограничения. Размер
контекста ограничивается сервером; детали подгружаются через инструменты.

Каталог возможностей различает параметры расчёта, read-only настройки сервера и
параметры отображения. Единицы, допустимые значения и зависимости берутся из
существующих схем/params/settings; объяснение назначения добавляется вручную,
паритет проверяется тестом. Метод MNE помечается «доступен в DipLock», «нужен
адаптер» или «неприменим к данным». Знание метода не разрешает запуск Python.

## 5. Провайдер модели

Доступ к модели — за небольшим интерфейсом: проверка доступности, генерация,
отмена/тайм-аут, вызов разрешённых инструментов, сведения о модели и расходе.
Первая реализация — один локальный HTTP-адаптер совместимого чат-API (кандидат —
сервер llama.cpp); выбор модели — только после измерения качества русского языка,
следования контракту и потребления GPU. Конкуренция с MNE за RTX A4000 учитывается
отдельным классом ресурса.

`httpx` уже присутствует в dev-окружении, но при runtime-использовании его нужно
явно добавить в основные зависимости и закрыть тестом, как принято в проекте.

Облачные провайдеры выключены по умолчанию. Для них требуется отдельное согласие
на передачу конкретных материалов, серверное хранение ключей и запись того, какая
версия контекста ушла наружу. Псевдоним EDF не делает голос и рассказ
обезличенными.

## 6. Роли и раунд

Первый рабочий раунд: психологический, нейрофизиологический и методологический
советники получают один и тот же снимок. Их первые ответы формируются без просмотра
ответов коллег; дальше — один ограниченный раунд замечаний и итог с сохранением
разногласий.

Оркестрация задаёт пределы: число ролей, раундов, инструментальных вызовов, время и
расход. Бесконечный диалог ИИ между собой недопустим. Отказ одной роли не должен
уничтожать ответы остальных: раунд помечается неполным.

## 7. Предложения и решения

Советник может предложить четыре вида шага:

1. спросить добровольца;
2. уточнить условия или наблюдение;
3. провести пробу;
4. выполнить расчёт.

Карточка предложения содержит основание, гипотезу, точное действие, риски и способ
проверки. Вопросы формулируются ненаводяще и порциями; отказ или отсутствие ответа —
честный результат, а не повод достраивать за человека.

До Т5 расчёты исполняются вручную в существующих разделах. В Т6 допускаются только
зарегистрированные инструменты, серверная валидация и одобрение точной версии
предложения; смена базы/параметров делает старое одобрение недействительным. Повтор
запроса обязан быть идемпотентным.

## 8. Фоновые задачи и хранение

Для LLM/ASR нельзя слепо унаследовать нынешний `job_manager`: он выполняет
синхронный воркер в потоке, а `on_success` текущих аналитических задач — best-effort.
Для Консилиума успех операции объявляется **после** обязательной записи её
долговременного результата; иначе задача должна завершиться честной ошибкой, а не
«успешно, но история потеряна».

Требуемая доработка общей очереди — перед задачами Т2/Т3, не условие для
синхронного хранилища Т1:

- async-воркеры для сетевого ожидания LLM;
- классы ресурсов и отдельные пределы: MNE, LLM, ASR;
- адрес результата для задачи Консилиума;
- связь задачи с долговременной строкой раунда/распознавания;
- восстановление после рестарта; состояние прерванной операции — в строке
  Консилиума (существующий `JobState` не расширяем без отдельного контрактного среза);
- файлы общей истории задач без чувствительного текста.

Таблицы и файлы появляются только после согласования кирпичей. Большие аудио и
экспорты живут вне БД под `results_dir`; БД хранит метаданные, хеши и ссылки.
При первом кодовом срезе обязательна строка в `docs/data_map.md`.

## 9. Интерфейс

Раздел — новая запись существующего реестра UI. Рабочая область: «Обсуждение»,
«Материалы», «Беседы». Правая панель — только направление, советники, провайдер и
границы раунда. Технические детали — раскрытием.

Обязательные действия ответа советника:

- «На чём основано?»;
- «Какие есть другие объяснения?»;
- «Что спросить у добровольца?»;
- «Предложи следующий шаг».

Серверные данные — TanStack Query; zustand хранит состояние интерфейса. История,
аудио и чувствительные тексты в `localStorage` не персистятся. Правка параметра или
раскрытие деталей не запускает модель/расчёт: считает только явная кнопка.

Т1 показывает ручную историю и материалы; работающие кнопки советников появляются
в Т3, беседы — в Т2. Нельзя изображать доступный ИИ фиктивными ответами-заглушками.
Основной ответ — обычный язык («заметили / возможное объяснение / чего не знаем /
следующий шаг»), технические доказательства доступны без обязательного чтения таблиц.

## 10. Безопасность

Базовый режим — локальный один пользователь, локальное хранение, локальные модели,
внешняя передача выключена. Голос, даты, имена файлов, аннотации и рассказы могут
идентифицировать добровольца даже при псевдониме EDF.

Раздельные разрешения: запись, хранение аудио, распознавание, передача текста
советнику, внешняя передача. Содержимое бесед не пишется в обычные логи и
traceback. Удаление учитывает БД, файлы, версии и экспорты на сервере; скачанный
пользователем файл приложение контролировать не может — это честно подписываем.

Нельзя сохранять чувствительные копии под предлогом неизменяемости снимка:
удаление очищает материалы, производные сводки и память, оставляет лишь отметки
без содержания. Архивирование не удаляет; удаление EDF не должно молча уничтожать
самостоятельную беседу, зависимости и последствия показываются до подтверждения.
Внешние адреса/ключи задаёт сервер, не чат; в локальном пилоте нет собственного
шифрования, сетевой доступ требует отдельного среза аутентификации/прав.

Общая память Т6 пополняется только подтверждёнными приёмами с исходами (включая
отрицательные), источниками, версиями, областью применимости и отзывом; не
характеристиками личности, автоматически извлечёнными из реплик. Поисковый контекст
не заменяет оригинальные материалы и не означает обучения весов модели.

## 11. Проверки по срезам

Backend: миграции и паритет, снимки/история, принадлежность материалов, недоступные
источники, идемпотентность сообщений и обязательная запись — в Т1. Прерванные
задачи/ASR — Т2, ссылки/провайдер/отмена LLM — Т3, подтверждение исполнения — Т6.
Frontend: empty/loading/error/stale, только кнопка запускает, устаревший ответ
не трогает состояние. Раскрытие показывает принятые данные; допустимое ленивое
чтение деталей не запускает новый расчёт или модель. Модели в CI не вызываются —
провайдер подменяется тестовым. Чек-лист Т1 — §9 стратегии.
