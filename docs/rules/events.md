# События записи и ERP (N2, шаг 2.7)

> Событийный режим: чтение EDF+-аннотаций/маркеров, нарезка по событиям, усреднение ERP.
> Открыто N2 (`audit_strategy.md`): «маркеры и аннотации исходного EDF+ не доходят ни до
> вьюера, ни до нарезки; событийного режима нет вовсе».

## Источники событий — один механизм

- **EDF+-аннотации (TAL)** — MNE парсит их в `raw.annotations` при чтении файла.
- **Стим-каналы** (`status`/`trigger` — MNE помечает типом `stim` при `stim_channel='auto'`;
  плюс имена `stim`/`sti`/`markers`/`marker`/`trig` ловит свой детектор по имени) — коды
  триггеров `mne.find_events` превращает в аннотации **`STIM/<код>`**.

Оба сводятся к аннотациям (`services/edf_events.py`): дальше паспорт, нарезка и ERP
работают одним механизмом (`mne.events_from_annotations`). Стим-каналы **удаляются** из
записи сразу после чтения (`attach_stim_annotations`) — они не ЭЭГ и не должны попадать в
масштаб/QC/монтаж. Извлечение — **до** `pick`/фильтров/ресемпла: события привязаны к
исходному времени файла (zero-phase фильтр и ресемпл секунды не сдвигают).

## Правила

1. **Аннотации объединяются, а не перетираются** (N2): `epoch_segmenter.merged_annotations`
   ставит `raw.annotations файла ∪ артефактные ∪ краевые BAD_edge`. Файловые `BAD_*`
   роняют эпохи наравне с нашими детекторами (правило N6), стимульные описания на `BAD_`
   не начинаются и нарезку не трогают. Никогда не вызывайте `raw.set_annotations(...)`
   с одним набором — только через `merged_annotations`.
2. **`BAD_` — отбраковка, а не события.** В паспорт (`RecordingMeta.events`), слой событий
   вьюера и селекты нарезки/ERP `BAD_`-аннотации не попадают; `events_from_annotations`
   их тоже пропускает. Описание с префиксом `STIM/` в паспорте маркируется
   `source='stim'` (остальные — `'annotation'`).
3. **События живут в паспорте** (`RecordingMeta.events` + `event_counts`, сайдкар
   `recording.json`): вьюеру слой маркеров нужен до какой-либо задачи. Список режется
   по `EVENTS_CAP` (5000), счётчики считаются по всем; сайдкары до шага 2.7 дочитываются
   лениво (`ensure_record_events` при `GET /recordings/{id}`).
4. **Слой событий во вьюере** — информационные вертикальные линии с тултипом
   «описание, интервал» (`TrackLayers.EventLayer`), тумблер «Маркеры событий» в панели
   (`eventsLayer` — ключ **отрисовки**, в `STAGE_PARAM_KEYS` не входит). Кликов у слоя нет:
   события приходят из файла, а не правятся руками.
5. **Событийная нарезка — режим стадии `epochs`** (`epoch_mode='events'`): окна
   `[−epoch_pre_ms; +epoch_post_ms]` вокруг моментов события `event_id`. В отличие от
   фиксированного режима длительность окна **не** обязана быть из `epoch_lengths_ms`
   (ERP-окна вида −100…500 мс в дискретный список не влезают); валидация —
   `api/params.py` (400 с текстом: описание события, 0 ≤ pre ≤ 10000, 100 ≤ post ≤ 10000,
   pre+post ≤ 10000).
   **UX-правило (фидбэк 26.09.2026):** кнопка стадии «Нарезка эпох» без выбранного
   события **выключена** (тултип объясняет: «выберите событие в блоке «Эпохи»» или
   «в записи нет событий — переключите на «Фиксированные»»); включение режима сразу
   подставляет первое событие, а выбор сверяется с событиями **новой** записи
   (`reconcileEventId`) — пустой `event_id` из localStorage не должен ронять запуск в 400.
6. **Нерегулярная сетка вьюера.** Результат стадии несёт `epoch_starts_sec` (начала окон:
   onset + tmin) и параметры события; индексы `rejectedEpochs` живут **в порядке событий**.
   Вьюер строит ячейки из явных начал (`buildEpochCells(..., startsSec)`), а не `n × length` —
   та же причина, по которой штриховка привязана к нарезке результата
   (`docs/rules/edf-viewer.md`). `epoch_starts_sec = null` — прежняя регулярная сетка.
7. **ERP — отдельная задача `kind='evoked'`**, а не четвёртая стадия: усреднённая волна —
   результат анализа, а не шаг подготовки. Форма повторяет форму стадии «Нарезка эпох»
   (те же пороги — числа согласованы со штриховкой) плюс baseline (пара значений мс от
   события внутри окна эпохи; `None` — без коррекции). Главные числа ответа
   (`EvokedResult`) — `n_used` из `n_total` и `rejected_epochs`: «сколько событий вошло
   в среднее» — первое, что обязан видеть исследователь.
8. **Ограничение шага (осознанно):** диполи, спектр, спектрограмма и legacy-`/analyze`
   остаются на **фиксированной** нарезке; карта по Evoked и событийные диполи — отдельная
   задача после 2.7 (`audit_strategy.md`: «стимул → эпоха → усреднение → карта»).
   Слой событий в разделе «ЭЭГ» и PNG-экспорт слоя — тоже не входят.

## Ловушки MNE (см. также `docs/rules/safety.md`)

- `find_events(raw, stim_channel='auto')` **падает** ('auto' — не имя канала): используйте
  `stim_channel=<имя>` или вызов без параметра (первый stim-канал).
- `raw.drop_channels(...)` не принимает `verbose` в MNE 1.13.
- TAL-формат: разделитель длительности — `\x15`, описаний — `\x14` (`+onset\x15dur\x14desc\x14\x00`);
  с `\x14` вместо `\x15` MNE читает «длительность» как отдельное описание.
- `events_from_annotations(raw, event_id={...})` без совпадений кидает свой `ValueError`
  («Could not find any of the events») — проверяйте наличие описания **до** вызова и
  отдавайте свой текст со списком доступных событий.
