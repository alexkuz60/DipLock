> `docs/rules/docs.md` п.9: кирпич описывается **до** кода, структура БД — **после** кирпичиков).

## Что здесь будет

- полные поля трёх кирпичей: **B11** «QC-снимок записи» (профиль грязи), **B10** «Протокол
  препроцессинга», **B12** «Отчёт о потерях» (метрики L1–L9 Части 1 §7);
- **таблица шагов препроцессинга в разделе «Таблица» — производная проекция** (B10 + B12 + журнал для
  времён), а не отдельный кирпич: один источник — один владелец, иначе числа разъедутся
  (`docs/rules/data-and-caches.md`);
- **носитель протокола на первой итерации решён: файл задачи** (`job_store`) + журнал шагов — хранение
  протоколов нужно уже сейчас, БД — позже (решение владельца 22.09.2026, вторая волна);
- решения по остальным носителям: дисковый кэш (`cache_store`), сайдкар записи, будущие таблицы
  `sessions`/`epochs`/`dipoles` (`todo.md` 4.4) + миграции (`todo.md` 4.2);
- строки в `docs/data_map.md` (носитель, ключ инвалидации, жизненный цикл);
- экспорт протокола (JSON) и его версия: протокол, применённый год назад, должен читаться;
- что именно писать в журнал шагов, чтобы пары «профиль → рецепт → метрики» накапливались
  (это условие Части 4).

## Границы

Структура **основной** БД здесь не проектируется: только то, что нужно для протоколов и качества.
Групповой анализ и каталог сессий — `concept.md` С7/С8 и `todo.md` 4.7, не эта часть.
