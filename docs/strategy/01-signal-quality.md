# Часть 1. Качество сырого сигнала и реставрация

> Индекс стратегии — `docs/strategy.md`. Здесь: **что пользователь-нейрофизиолог должен узнать о
> своём файле до расчётов**, какими категориями описывается «грязь», какими методами она снимается,
> как измерить, что при этом потеряно, и как из очищенного сигнала получить разбивку на ритмические
> поддиапазоны для расчёта диполей.
>
> Язык документа — пользовательский, не программный: «что видно», «что решаем», «чем платим».
> Статусы методов приведены по коду на 22.09.2026 и проверены запуском в venv (MNE 1.13.2).

## §1. Рабочий сценарий глазами пользователя

Сегодняшний путь в приложении: **загрузил EDF → вьюер треков (раздел EDF) → нашёл артефакты →
нарезал эпохи → посмотрел спектр (раздел ЭЭГ) → посчитал диполи (раздел «Диполи»)**. Формально всё
есть. Не хватает **одного звена**: между «в файле есть грязь» и «диполи посчитаны» нет места, где
пользователь видит **ответ на вопрос «насколько мой файл испорчен и что именно я с ним сделал»**.

Что нейрофизиолог делает руками сейчас и что должен делать в приложении:

| Шаг | Сегодня | Должно быть (видение) |
|---|---|---|
| 1. Познакомиться с файлом | Смотрит трек, крутит зум, глазами ищет выбросы | **Паспорт качества**: SNR по каналам, уровень сети и её гармоник, доля мёртвых каналов, доля годного времени, список подозрений по категориям — до единого расчёта |
| 2. Назвать проблему | «Что-то дёргается в лобных» — без имени и без числа | **Категория с числом**: «моргание: 42 события, 7 % времени, Fp1/Fp2/F7/F8» |
| 3. Выбрать лечение | Перебирает переключатели пресетов | **Протокол**: список процедур по категориям, с ожидаемой ценой (время) и ожидаемым риском потерь |
| 4. Убедиться, что не испортил | Сравнивает на глаз «до/после» на одном экране | **Оценка потерь**: сколько убыло в каждой полосе (дБ), какая доля времени/каналов/эпох выведена, что стало с КД и GOF |
| 5. Работать с ритмами | Фильтрует пресетом и пересчитывает заново | **Разбивка по поддиапазонам**: δ…γ одновременно, отдельная дорожка на полосу, свой пик GFP в каждой, диполи по каждой полосе |
| 6. Вернуться к этому через месяц | Не помнит, чем чистил | **Протокол сохранён** рядом с результатом: тот же файл → тот же результат (воспроизводимость) |

Ключевая мысль: **пользователь принимает решение не по форме волны, а по числам качества**; форма —
подтверждение. Отсюда требование к приложению: любая процедура обязана уметь показать «до» и «после»
в числах, иначе выбор метода остаётся вкусовым.

Второй мотив — **масштаб архива** (`concept.md` §5): сотни записей, накопленных на разном
оборудовании. Ручной подбор процедур для каждой нереален, поэтому числа качества — это ещё и
**вход для автоматики** (§11, Часть 4): сначала приложение считает профиль грязи, потом по нему
предлагает протокол.

## §2. Карта фактов: что в коде есть сегодня

Проверено по коду на 22.09.2026 (файлы указаны, чтобы документ не расходился с реализацией).

**Порядок обработки при чтении** (`backend/app/services/edf_loader.py:116–152`):

```text
чтение EDF → физические единицы (fix «без размерности») → нормализация имён каналов
→ pick стандартных 10-20 → монтаж 10-20 → average reference (projection=False)
→ bandpass FIR (firwin) → notch FIR (одна частота) → resample 500 Гц
```

Что тут методически значимо:

1. **Референс стоит ДО фильтров.** Следствия: (а) QC по каналам считается на уже взаимозависимых
   сигналах — амплитуда каждого канала «подмешана» средним по всем, поэтому порог «плохой канал»
   теряет чувствительность; (б) мёртвый электрод маскируется средним — flat-line после референса
   почти не виден (это же названо в `todo.md` 2.2); (в) сетевую наводку конкретного канала
   референс **размазывает на все каналы** — и notch потом снимает её уже «отовсюду».
2. **`pick` до ICA** — `ica.find_bads_eog` ищет каналы с «eog» в имени среди 20 каналов 10-20,
   поэтому EOG-каналов не находит никогда (`todo.md` 2.1).
3. **Ресемплинг в конце** — 500 Гц, только если запись чаще. Nyquist = 250 Гц.

**Детекторы артефактов** (`services/artifact_detector.py`): z-score (по глобальным среднему и σ),
peak-to-peak скользящим окном, flat-line оконным критерием; ICA-EOG — как выше. Аннотации `BAD_`
влияют на отбраковку эпох (`reject_threshold_uv = 150 мкВ`).

**Полосы** (`core/config.py`): δ 1–4, θ 4–8, α 8–13, β 13–30, γ 30–40; «одиночная частота» — ±0.25 Гц.
Длины эпох 250…2000 мс, по умолчанию 2000 мс.

**Спектрограмма** (`services/spectrogram.py`): окно 500 мс (допустимо 64…4000), перекрытие 75 %,
верхняя частота по умолчанию 40 Гц (**допустимо до 120 Гц**), пол шкалы — 60 дБ ниже 99.9-процентиля.
Полосу фильтра для просмотра можно **не задавать вовсе** (тогда виден весь диапазон до верхней
частоты сетки) — именно так получен скриншот в §4.

**Доступность инструментов в окружении** (проверено в venv):

| Инструмент | В MNE 1.13.2 | Зависимость | Статус в проекте |
|---|---|---|---|
| `annotate_muscle_zscore` | есть | — | не используется |
| `annotate_nan`, `annotate_break` | есть | — | не используется |
| `compute_proj_eog` (SSP) | есть | — | не используется |
| `notch_filter(method="spectrum_fit")` | есть (`mt_bandwidth`, `p_value`) | — | не используется (сейчас `method="fir"`) |
| `autoreject` | — | отсутствует | отложено (`todo.md` п.4) |
| `mne-icalabel` | — | отсутствует | кандидат после 2.1–2.3 |
| `mne-connectivity`, `specparam` | — | отсутствуют | отложено (С5, 2.4) |
| `scipy` | есть | есть | используется |

### 2.1. Что доступно пользователю сегодня (UI-инвентарь поиска артефактов)

**Параметры стадии «Поиск артефактов»** (правая панель; дефолты — из `/api/v1/meta` →
`artifact_thresholds`, а не хардкод в UI):

| Что настраивается | Дефолт | Поле конфига | Комментарий |
|---|---|---|---|
| Порог z-score | 5 | `z_score_threshold` | σ считается глобально по всей записи (не медиана/MAD) |
| Порог peak-to-peak | 100 мкВ | `peak_to_peak_threshold_uv` | окно 2 с, шаг 1 с — **в UI не видны** |
| Порог flat-line | 1 мкВ | `flat_line_threshold_uv` | критерий «размах в окне», а не абсолютная амплитуда `abs(x)` |
| Длительность плоского участка | 200 мс | `flat_line_min_duration_ms` | минимум для зачёта зоны |
| Запуск ICA-EOG | всегда включён | — | `run_ica` в UI не выведен и всё равно недостижим (§2) |

**Что есть из визуализации и контроля:**

| Элемент | Что даёт |
|---|---|
| Слои зон (4 типа: `zscore_outlier`, `peak_to_peak`, `flat_line`, `ica_eog`) | чекбоксы видимости, легенда, тултип «по каким каналам сработало» |
| QC-иконки каналов (`channel_qc_summary`) | суммарные секунды и доля «плохого» времени по каналу, слияние интервалов, разбивка по типам в тултипе |
| Счётчики `stats.by_type` / `total`, флаг `ica_applied` | сколько событий нашёл каждый детектор; честный факт «ICA не применялась» |
| Штриховка отброшенных эпох, маркеры границ, ручные пометки (Ctrl+двойной клик) | состав эпох и ручная правка поверх авто-детекции |
| Кнопки стадий + точки состояния (серая/жёлтая/красная) + «Готовность: k из 3» | что посчитано, что устарело, что упало |
| Порог отбраковки эпох 150 мкВ | но это параметр расчёта **диполей** (`rejectThresholdUv` в разделе «Диполи»), в стадии артефактов он не правится |

**Чего в инвентаре нет** (это и есть предмет §13): детекторов ЭМГ, разрывов/NaN, кардио, окулярных
(отдельно от общего peak-to-peak), клипа/перегруза, дрейфа; выключателя конкретных категорий; числа
«остаток наводки» (в том числе гармоник); интерполяции/исключения каналов и прорезки интервалов; любой
оценки потерь; протокола и таблицы шагов. Иными словами, сегодня поиск артефактов — это **три
амплитудных порога по всей записи**, а не набор детекторов по категориям.

## §3. Каталог «грязи»: категории, вред, детекторы, снятие

Логика каталога: **каждая категория обязана иметь четыре ответа** — что видно, чем вредит конечному
результату (диполю и ВП), чем детектируется, чем снимается и что при этом теряется. Категория без
детектора — это «мы её не измеряем и честно об этом говорим», а не «её нет».

### 3.1. Сетевые наводки

| Что видно | Вред для диполей/ВП | Детектор: сегодня → кандидат | Снятие и что теряем |
|---|---|---|---|
| Ровная линия на 50 Гц (60 Гц) на спектре/спектрограмме, «пила» на треке | Ложная когерентная компонента на всех каналах: фитинг одиночного диполя находит «источник» в центре или на границе сетки; шумовая полка задирает уровень, маскируя γ; при малой амплитуде ЭЭГ отношение сигнал/наводка падает | Сегодня: `notch_filter(50)` + наблюдение глазами. Кандидат: уровень пика над локальным фоном в дБ (число, а не «видно») | Notch FIR (есть). Цена: узкая «дыра» в спектре; при узкой полосе анализа (α) провал на 50 Гц безвреден, при счёте γ (30–40) — тоже, но для широкополосных мер (ЭМГ) дыра искажает |
| **Гармоники** 100 / 150 / 200 / 250 Гц | То же, но **незаметнее для глаза**: гармоника не отфильтрована, не попадает в отчёт и не уменьшает КД-проходимость явно, зато остаётся в сигнале как периодическая компонента; при широкополосном просмотре (спектрограмма до 120 Гц) видна как яркая линия — см. §4 | Сегодня: **никак** (notch только на одну частоту). Кандидат: список частот-кандидатов по сетке 50 Гц + оценка «дБ над фоном» | `notch_filter([50,100,150,200])` или `method="spectrum_fit"` (MNE 1.13, специально для гармоник). Цена: широкий notch на 100–200 Гц задевает ЭМГ-полосу → для ЭМГ-анализа отключать |
| Нестабильная частота сети (дрейф 49.8–50.2 Гц, «плывущая» наводка) | Остаточная наводка **после** notch: провал стоит на 50.0, а помеха уехала на 50.2 — снятия нет, но отчёт считает её снятой | Сегодня: никак. Кандидат: ширина пика в спектре PSD (по записи) + «остаток после чистки» | `method="spectrum_fit"` с полосой поиска, либо `notch_widths` шире. Цена: шире вырезаем — больше теряем рядом |
| Наводка только на части каналов (плохой контакт) | Ложная «локальность»: один-два канала дают собственный период 50 Гц → при одиночном диполе он «залипает» в соответствующей области | Сегодня: QC-иконки каналов (по амплитуде). Кандидат: пик 50 Гц **по каналам** | Notch по каналам (`picks`) + ремонт контакта/интерполяция. Цена: индивидуальный notch маскирует диагноз «канал отваливается» |

### 3.2. Кардио-артефакт (ЭКГ)

| Что видно | Вред | Детектор: сегодня → кандидат | Снятие и что теряем |
|---|---|---|---|
| Регулярные острые комплексы ~1 Гц (чаще в затылочных/височных/референтном канале), на спектре — подъём в δ/θ | Самый коварный: ритмичен, значит **даёт стабильный ложный диполь** в δ/θ с высоким GOF — именно то, что попадает в результат как «источник». При усреднении ВП даёт синхронный выброс → ложный пик | Сегодня: попадается частично (peak-to-peak). Кандидат: автокорреляционный/шаблонный детектор QRS по одному каналу + регулярность пиков | ICA (после починки 2.1), SSP по шаблону, реже — простая прорезка интервалов. Цена: удалённые компоненты уносят часть δ/θ-контента, а он — сердце методики |

### 3.3. Окулярные артефакты (движение глаз)

| Что видно | Вред | Детектор: сегодня → кандидат | Снятие и что теряем |
|---|---|---|---|
| Медленные большие волны 0.1–3 Гц, максимальные в Fp1/Fp2/F7/F8, полярность в противофазе при моргании (до 200+ мкВ) | **Глазное яблоко — настоящий диполь**, и одиночный фитинг честно сажает источник в глазницу → фронтальная «локализация» моргания; в ВП моргание даёт серию пиков в начале эпохи | Сегодня: peak-to-peak ловит, но **не отличает** моргание от фронтального ЭЭГ-всплеска. Кандидат: Fp1/Fp2-прокси (корреляция пары с порогом), SSP `compute_proj_eog` (доступен), EOG-канал, если он есть в файле | ICA / SSP. Цена: ICA на 20 каналах снимает вместе с морганием часть фронтального α/θ; прокси-каналы требуют осторожности (Fp1/Fp2 — тоже ЭЭГ) |
| Саккады, движения глазных яблок (быстрее, 1–10 Гц, фронтально-полярные) | Короткие фронтальные всплески в θ/α-диапазоне, ложные фронтальные диполи | Сегодня: никак отдельно. Кандидат: тот же Fp1/Fp2-прокси с более коротким окном | SSP/ICA. Цена: как выше |

### 3.4. Мышечные артефакты (ЭМГ)

| Что видно | Вред | Детектор: сегодня → кандидат | Снятие и что теряем |
|---|---|---|---|
| «Лохматый» высокочастотный шум (>20 Гц), при жевании/глотании/напряжении — пачки, часто с фронта/височных | Широкополосная энергия **попадает прямо в β/γ**, а γ — верхняя полоса набора: мощности γ и «диполь в γ» могут быть целиком артефактом. Именно поэтому категорию нельзя оставлять «на глаз» | Сегодня: **никак**. Кандидат: `annotate_muscle_zscore` (готов в MNE, без новых зависимостей) | Отбраковка эпох (уже работает через `BAD_`), ICA/SSP для устойчивых источников, сужение полосы. Цена: отбрасываем эпохи — теряем время записи; в γ-анализе спрятать ЭМГ корректно **нельзя**, только исключать |

### 3.5. Механические и электродные (дрейф, шевеление, импеданс)

| Что видно | Вред | Детектор: сегодня → кандидат | Снятие и что теряем |
|---|---|---|---|
| Медленный дрейф baseline (<0.5 Гц), «дыхание» линии, потоотделение | Прямая добавка в δ-мощность и в положение «нулевой» линии; центрирование окна смещает пик и момент GFP → диполь δ «съезжает» | Сегодня: частично (высокочастотный фильтр 1 Гц отсекает часть). Кандидат: остаточный дрейф окна (медленная составляющая на эпохе) | Полосовой фильтр (есть), детренд окна, буферы края. Цена: фильтр 1 Гц сам по себе подрезает δ 1–2 Гц — при δ-анализе это методический выбор, а не «настройка» |
| Шевеление/импульс движения (широкополосный «ляп» на многих каналах) | Даёт «всплеск GFP» → **выбирается как момент пика** → диполь движения. Это один из двух главных источников ложных диполей (второй — кардио) | Сегодня: peak-to-peak/z-score ловят как амплитуду, но не отличают от физиологического всплеска. Кандидат: одновременность по многим каналам + широкополосность | Отбраковка эпох/интервалов, ручная пометка во вьюере (есть). Цена: длинные записи с частым шевелением теряют много времени |
| Плохой контакт/высокий импеданс: собственный шум канала, скачки, «звон» | Ложная локальность и широкополосный шум; в QC-числах один канал «выше всех» | Сегодня: QC-иконки, flat-line/шум по каналам (частично). Кандидат: SNR и спектральная «ровность» по каналам | Интерполяция плохих каналов (`interpolate_bads`) или исключение. Цена: интерполяция «дорисовывает» данные — обязателен явный признак в паспорте кирпичика |
| Электродный «pop» (мгновенный скачок с возвратом) | Один отсчёт-выброс меняет масштаб окна и зум; при усреднении ВП даёт острый ложный пик | Сегодня: z-score/peak-to-peak (как выброс). Кандидат: отличение «pop» (одиночный отсчёт) от физиологического пика (несколько отсчётов) | Медианная фильтрация отсчёта/прорезка, ручная метка. Цена: медиана по широкому окну задевает узкие физиологические спайки |

### 3.6. Потери сигнала и перегруз

| Что видно | Вред | Детектор: сегодня → кандидат | Снятие и что теряем |
|---|---|---|---|
| Flat-line: «мёртвый» электрод, прямая линия | Нулевая линия при усреднении не даёт вклада, но её шум/смещение искажают средний референс-канал → «портит» все каналы | Сегодня: flat-line **после референса** — почти не виден (§2 п.1). Кандидат: тот же критерий **до** референса + по сырому файлу | Исключение канала/интерполяция. Цена: канал теряется навсегда — важно видеть это до расчёта, а не после |
| Разрыв записи (пропуск отсчётов, склейка) | Резкое ребро → широкополосный всплеск спектра → ложный «источник» на месте разрыва; момент разрыва может стать пиком | Сегодня: никак. Кандидат: `annotate_nan` + проверка временных меток EDF | Прорезка интервала с `BAD_`-меткой, не нарезать эпохи через разрыв. Цена: граница записи не должна попадать в эпоху |
| Насыщение/клиппирование (перегруз АЦП): плоские вершины на пределе ±N | Ограничение сигнала порождает **гармоники** (в том числе на 100/150 Гц) и ломает спектр; диполь на клипе — следствие клипа, а не источника | Сегодня: никак (клип выглядит как «большая нормальная волна»). Кандидат: доля отсчётов на пределе диапазона, «двойные плато» | Клип **не восстанавливается** — честная метка «испорчено» и исключение. Цена: если клип частый, запись непригодна — это вывод, который лучше получить сразу |
| DC-offset / сдвиг нуля канала | Смещение меняет выбор «нулевой линии» и визуальный масштаб, при усреднении даёт ступеньку | Сегодня: частично (фильтр). Кандидат: оценка среднего по записи и его сдвиг между каналами | Детренд/центровка. Цена: вместе со сдвигом уходит очень медленная составляющая (для δ-анализа учитывать) |

### 3.7. Импульсные мусорные помехи (не физиологические)

| Что видно | Вред | Детектор: сегодня → кандидат | Снятие и что теряем |
|---|---|---|---|
| Одиночные острые спайки (сбои оцифровки, статика, «щелчки» контакта) | Идеальный «пик GFP» для алгоритма: короткий, высокий, изолированный → диполь-фантом; ещё и задирает порог 150 мкВ, отбраковывая нормальные эпохи | Сегодня: z-score их ловит — вместе с физиологическими спайками. Кандидат: отличение по длительности фронта и по «одновременности» на соседних каналах | Медианный фильтр/прорезка, `annotate_*`, ручная метка. Цена: узкая «шумоподавка» задевает физиологические и эпилептиформные спайки — отделять аккуратно |
| Периодическая помеха неэлектрического происхождения (насос, мерцание лампы 100 Гц, вентиляция) | Тот же вред, что сетевые наводки, но частота не кратна 50 → notch её не берёт; регулярность даёт ложный ритм на спектре | Сегодня: никак. Кандидат: поиск узких пиков в PSD, не кратных 50 Гц, с проверкой по каналам | Notch на найденной частоте или ICA-компонента. Цена: узкая полоса, не связанная с ЭЭГ, — обычно безвредна |

### 3.8. Фоновое качество оборудования (устаревший парк)

| Что видно | Вред | Детектор: сегодня → кандидат | Снятие и что теряем |
|---|---|---|---|
| Низкий SNR: аппаратный и электродный шум, «шумная» дорожка | Падение GOF диполей, нестабильность локации; сравнение сессий между приборами становится некорректным | Сегодня: нет. Кандидат: SNR по каналам, ровность спектрального фона (белый/фликкер) | Только усреднение/удлинение эпох и сужение полосы. Цена: усреднение требует много годных эпох |
| Фликкер-дрейф усилителя, «ползущая» низкочастотная составляющая | Раздувает δ/θ, уменьшает читаемость IAF | Сегодня: частично. Кандидат: наклон PSD на низких частотах | Полосовой фильтр, детренд. Цена: отрезание δ |
| Грубое квантование (устаревшие АЦП): «ступеньки» на малой амплитуде | Паразитные гармоники квантования, «лестница» в топокартах | Сегодня: нет. Кандидат: оценка шага квантования по гистограмме отсчётов | Не устранимо; полезно **знать** и указывать в паспорте (объясняет странности картинки) |
| Неизвестный/подозрительный единичный масштаб (В vs мкВ) | Ошибка в 10⁶ — форма «правильная», числа бессмысленные | Сегодня: есть (`looks_unscaled`, warning, `EDF_UNITS`) | Автофикс (есть). Цена: при ложном срабатывании масштаб портится — потому и warning, а не тишина |

### 3.9. Сводка: какие категории бьют по результату сильнее всего

По критерию **«может дать правдоподобный, но ложный диполь или ложный пик ВП»** (а не «портит
картинку») порядок такой:

1. **Кардио (3.2)** — ритмичен и стабилен → ложные диполи в δ/θ с высоким GOF, попадают в статистику.
2. **Шевеление/импульсы движения (3.5)** и **мусорные спайки (3.7)** — дают «пик GFP» → алгоритм
   выбирает именно их как момент для фитинга.
3. **Моргание/движение глаз (3.3)** — «настоящий» диполь в глазнице, фронтальная ложная локализация.
4. **ЭМГ (3.4)** — делает γ-анализ недостоверным целиком.
5. **Клип и разрыв (3.6)** — широкополосные компоненты и гармоники; часто делают запись непригодной,
   и узнать это нужно **до**, а не после часов расчёта.
6. **Сетевые наводки и гармоники (3.1)** — когерентны по всем каналам; низкоразмерны, но сбивают
   одиночный фитинг и задирают фон.
7. **Дрейф / импеданс / фон (3.5, 3.8)** — портят δ и сравнение сессий; GOF падает «вообще», без
   обмана: результат честно хуже, а не ложный.

## §4. Разбор кейса: «50 Гц подавлен, а 100 Гц никто не заметил»

**Наблюдение владельца (22.09.2026, скриншот раздела «ЭЭГ»):** канал F3, запись `test001.edf`,
верхняя частота сетки спектрограммы 120 Гц, полоса фильтра просмотра не ограничена. На спектрограмме
**основная наводка 50 Гц отсутствует, а на 100 Гц стоит яркая ровная линия**. Ни один из четырёх
аудитов гармоники не назвал.

### Почему так получилось — по коду

1. `load_edf(..., notch_hz: float | None)` → `raw.notch_filter(notch_hz, fir_design="firwin")` —
   **одна частота**. Фильтр линейный, поэтому 100 Гц он не создаёт и не убирает: он просто не про неё.
2. Контракт: `notch_hz: float | None` в схемах (`schemas/analysis.py`) и в форме
   (`api/params.py`), во фронтенде — `notchHz: number` (0 = выключен). **Гармоник в контракте нет ни
   в одном представлении**: ни как параметр, ни как отчётная величина.
3. Полосы анализа δ…γ (1–40 Гц) гармонику не содержат, а обычный анализ фильтрует 1–40 → для
   «обычного» пути 100 Гц лежит вне полосы пропускания и формально не вредит. **Вред остаётся в
   четырёх местах:** (а) широкополосный просмотр и QC — то, что видно на скриншоте; (б) оценка фона и
   SNR (наводка задирает шумовую полку); (в) ЭМГ/высокочастотный анализ (100–200 Гц — это его
   область); (г) любая нелинейность тракта (клип, грубое квантование) — интермодуляция и перенос
   энергии «складываются» в низкие частоты.
4. Следствие: 100 Гц не попадает ни в паспорт качества, ни в решения детекторов, ни в отчёт — то есть
   **выглядит как «сеть почищена», а почищена только основа**.

Отдельно: гармоники — признак **несинусоидальной** помехи (импульсная, «грязная» сеть). Поэтому
правильная реакция — не только «вырезать 100 Гц», но и записать в паспорт: «помеха имеет гармоники,
значит форма несинусоидальная»; это же объясняет, почему у такой записи выше шумовая полка.

### Что предлагается (два уровня, чтобы не блокировать друг друга)

| Уровень | Что делаем | Где | Цена |
|---|---|---|---|
| **Индикация** (обязательный минимум) | Считать «остаток наводки» по сетке 50 Гц: для 50/100/150/200 Гц — уровень пика над локальным фоном (медиана в окне ±10 Гц) в дБ; показывать в паспорте качества и, если больше порога, выводить предупреждение «сеть подавлена не полностью» | QC-снимок записи, раздел ЭЭГ (уже есть спектрограмма) | Дёшево: один PSD уже считается для спектра ритмов |
| **Устранение** | Notch по списку частот: `notch_filter([50, 100, 150, 200])`, а для «плывущей» сети — `method="spectrum_fit"` (MNE 1.13; специально для гармоник, устойчив к дрейфу частоты) | `edf_loader` + контракт формы (список вместо числа) | Правка контракта и формы; методический риск: широкий notch на 100–200 Гц задевает ЭМГ-полосу → в профилях ЭМГ-анализа гармоники оставлять или снимать отдельным профилем |

Техническая оговорка для реализации: при ресемплинге до 500 Гц Nyquist = 250 Гц, то есть 200 Гц
снимается, а 250 Гц — ровно на границе (не снимаем, помечаем). Частоты выше `h_freq` обычного анализа
(например 40 Гц) снимать **не обязательно**, если анализа выше 40 Гц нет: важно, чтобы приложение не
утверждало «сеть снята», когда это не так.

**Вывод кейса.** Гармоники — не «мелочь на картинке», а проверяемый пример более общего требования
из §1: **каждая процедура чистки обязана иметь число «до/после»**. Здесь «после» формально равно нулю
искажений, потому что «до» никто не измерил.

## §6. Порядок операций и выбор методов

### 6.1. Канонический протокол (порядок, который предлагается закрепить)

Столбец «число» — то, что обязано появиться в журнале/паспорте на этом шаге (иначе шага «не было»).

| # | Шаг | Почему именно здесь | Число (метрика шага) |
|---|---|---|---|
| 0 | **Чтение и паспорт файла** (единицы, имена, монтаж, sfreq, длительность, каналы) | До любых манипуляций фиксируем «как было» | Есть: паспорт записи (`recordings`) |
| 1 | **QC по сырому** (SNR по каналам, flat-line, клип, уровень сети и гармоник, фон по каналам) | Детекторы и пороги должны опираться на **сырое** состояние, а не на уже переработанное (иначе flat-line после average reference скрыт — §2 п.1) | **Нет** — новый QC-снимок (§9, B11) |
| 2 | **Решение о референсе** (`average` / по каналам / оставить как есть) | Методический выбор: от него зависят и амплитуды каналов, и «средний» шум. Сейчас референс применяется **до** фильтров | Есть (`reference`), нет числа «сколько шума внесено» |
| 3 | **Монтаж/имена/единицы** | Уже в `load_edf` | Есть |
| 4 | **Полосовой фильтр на continuous raw** (δ…γ или «без фильтра») | Ключевое уже верно: короткие эпохи фильтровать нельзя | Есть (`band_hz`) |
| 5 | **Notch: основа + гармоники** | Узкие помехи снимаются до «широких» решений и до ICA (чтобы ICA не тратила компоненту на наводку) | Есть только основа; гармоники — предложение §4 |
| 6 | **Детекторы категорий** (z-score/robust, peak-to-peak, flat-line **до референса**, ЭМГ, разрывы, кардио-паттерн) | Каждый детектор = отдельная категория с числом событий | Частично (4 детектора), нет ЭМГ/разрывов |
| 7 | **Чистка** (SSP/ICA по глазам и кардио, интерполяция каналов, метки интервалов) | Только после того, как известны категории: чистка «на всякий случай» — источник скрытых потерь | Частично (ICA недостижима) |
| 8 | **QC после чистки + оценка потерь** | Сравнение с шагом 1 по одним и тем же метрикам | **Нет** — новый отчёт (§7, B12) |
| 9 | **Нарезка эпох** (reject + `BAD_`) | Уже так: фильтр до нарезки | Есть (`n_epochs_used/total`) |
| 10 | **Разбивка по поддиапазонам** и расчёт диполей по каждой полосе | См. §8 | Есть частично (по одному пресету за раз) |

Две точки решения, которые стоит зафиксировать сознательно (сейчас они «просто так»):

- **Референс до или после фильтров.** Аргументы за «notch и полосовой — до референса»: (а) QC по
  каналам честнее (каналы ещё независимы); (б) flat-line и «отвалившийся электрод» видны; (в) наводка
  не размазывается на все каналы через средний. Аргументы за текущее: `fit_dipole` требует применённый
  average reference, а референс удобно поставить сразу (он линейный и с фильтрацией в основном
  коммутирует). **Решение (владелец, 22.09.2026):** QC и детекторы считаются на **сыром, не
  отреференсированном** сигнале; референс применяется **после чистки** — но до нарезки эпох и до
  `fit_dipole` (MNE требует применённый average reference, поэтому референс остаётся в пайплайне, просто
  перестаёт быть первым шагом). Следствие для реализации: `load_edf` должен уметь отдать «сырой» вариант
  без референса, а референс — отдельная операция протокола (шаг 2 становится шагом «после чистки»).
- **Порядок «чистка ↔ отбраковка».** Сейчас `BAD_`-аннотации влияют на нарезку, но сигнал не
  вырезается. Предлагается различать три уровня потери: «исключено из эпох» (эпохи),
  «исключено из сигнала» (интервалы), «исключено из файла» (каналы). Пользователь должен видеть все три
  раздельно — иначе «потери» остаются невидимыми.

### 6.2. Выбор методов по профилю грязи (правило, а не переключатели)

Идея: QC-снимок (§7) даёт **профиль** — вектор чисел по категориям. Протокол выбирается по профилю,
а не вручную «на всякий случай». Черновой вид правила (числа порогов — к решению эксперта):

| Если в профиле | То процедура | Ожидаемая потеря, которую надо показать |
|---|---|---|
| 50 Гц заметно выше фона и/или гармоники > порога | M2 (notch основа + гармоники) | «дыры» на 50/100/150/200 Гц, ЭМГ-полоса затронута — проверить γ/ЭМГ-выводы |
| Регулярные кардио-комплексы (по числу событий и стабильности интервалов) | M6/M8 (ICA/SSP по кардио-паттерну) | удалённый % дисперсии, изменение δ/θ-мощности |
| Моргание/движение глаз (Fp1/Fp2-корреляция) | M8/M6 | удалённый % дисперсии, фронтальный α/θ |
| ЭМГ: доля времени выше порога | M9 + M13 (метка + отбраковка эпох) | выведенный % времени, число оставшихся эпох; для γ — «вывод недостоверен» |
| Flat-line каналы (по сырому) | M12/M13 (интерполяция/исключение) | «каналы заменены: N», влияние на средний референс |
| Клип выше порога или длительность клипа большая | **не чистка**: пометка «непригодно для локализации» | работа в режиме спектра; локализация отключается с объяснением |
| Шевеление (одновременность/широкополосность) | M15/M14 (метки интервалов) | выведенный % времени, что осталось для эпох |
| Фоновый SNR ниже порога | M13 + удлинение эпох + сужение полосы | падение GOF, «сравнение сессий некорректно» |

Такой набор строк — это и есть **«рецепт»**: именованный протокол (например «архив 90-х: сеть +
кардио + отбраковка ЭМГ») со своим списком шагов и ожидаемых потерь. Отличие от сегодняшних пресетов
фильтра принципиально: пресет меняет одну настройку, рецепт — **последовательность процедур с отчётом**.
Именно рецепт, а не отдельный переключатель, — единица обмена с автоматикой (§11): агент предлагает
рецепт, человек его принимает или правит.

## §7. Оценка потерь полезного сигнала: чем мерим «стало ли лучше»

«Потеря» имеет три независимых вида, и их нельзя складывать в одно число:

1. **Потеря данных** — что физически выведено из анализа (время, каналы, эпохи).
2. **Потеря энергии** — сколько дисперсии/мощности ушло из полос (часть — мусор, часть — сигнал).
3. **Потеря результата** — что стало с конечным критерием методики (КД, GOF, устойчивость локации).

| Код | Метрика | На какой вопрос отвечает | Как считается | Сегодня | Где показывать |
|---|---|---|---|---|---|
| L1 | **Остаток наводки**, дБ | «сеть действительно снята?» | пик на 50/100/150/200 Гц минус медиана в окне ±10 Гц (по PSD записи) | **нет** | QC-снимок, раздел ЭЭГ, паспорт |
| L2 | **Профиль по каналам**: SNR, «шумность», flat-line, клип | «какие каналы не рабочие и почему» | по сырому сигналу, **до** референса | частично (QC-иконки) | паспорт, вьюер |
| L3 | **Δ-спектр по полосам**, дБ | «что убыло/прибыло в δ/θ/α/β/γ после чистки» | PSD(сырой) − PSD(очищенный), интеграл по каждой полосе | **нет** | наложение двух спектров (график — самое наглядное место) |
| L4 | **Сохранённая дисперсия полосы**, доля 0…1 | «сигнал не „съеден“ чисткой?» | корреляция сырого и очищенного в полосе пропускания (высокая = форма сохранена) | **нет** | отчёт о потерях |
| L5 | **Удалённая дисперсия чистки**, % | «сколько унесла ICA/SSP» | доля дисперсии, объяснённая удалёнными компонентами | **нет** | отчёт; для M6/M7/M8 — обязательное поле |
| L6 | **Выведено**: % времени, каналов, эпох | «сколько материала осталось» | три числа отдельно (§6.1, уровни потери) | частично (`n_epochs_used/total`) | вьюер, отчёт |
| L7 | **КД-проходимость**: доля прошедших КД, медиана GOF | «стало ли лучше для метода» — **главный критерий** | по результатам расчёта на одних и тех же параметрах | частично (в задаче быстрого расчёта) | сравнение «до/после протокола» |
| L8 | **Устойчивость локации**: медиана сдвига, мм; разброс | «диполь стоит или дрожит» | сравнение локаций до/после протокола (одни и те же эпохи/пики) | **нет** | отчёт о потерях |
| L9 | **Цена**: время расчёта, память | «сколько стоит протокол» | `duration_sec_calc`, объём кэша | есть (журнал шагов) | таблица протокола |

Правила, без которых эти числа бессмысленны:

- **Сравнение только при одинаковых параметрах расчёта.** Δ-метрики несут отпечаток (как
  `spectrum_signature`): разные наборы полос или разная нарезка → дельта «не та».
- **Базис — «доля от максимума своего поддиапазона»** (`docs/data-blocks.md` §2.2): абсолютные мкВ² в δ
  и γ несравнимы, поэтому «сколько убыло» даётся в двух видах — абсолют (мкВ²/дБ) и доля.
- **Никаких свёрнутых оценок «качество 87 %».** Исследователю нужен вектор, а не интеграл: свёртка
  прячет именно то, что он проверяет.
- **Честная немощь:** где метрику измерить нельзя (клип, грубое квантование, нет ЭКГ-канала) — в отчёте
  «не измерялось», а не ноль.

**Профиль грязи** как итог §7: вектор `{L1 по 4 частотам, сводка L2, доля времени по категориям 3.2–3.8,
L6, L9}` — компактная характеристика файла. Он нужен трижды: пользователю (паспорт качества), отчёту
(обоснование протокола) и автоматике (§11): именно он — вход для выбора рецепта.

## §8. Подготовка и разбивка на ритмические поддиапазоны для расчёта диполей

### 8.1. Что уже решено и не пересматривается

- фильтр по поддиапазону применяется к **continuous raw до нарезки**;
- пик GFP **свой** в каждом поддиапазоне (ключ дипольной точки — «эпоха + пик × поддиапазон»);
- пороги КД нормируются на максимум **своего** поддиапазона;
- прогон по набору полос (B7) — одна задача, много результатов.

### 8.2. Порядок для каждой полосы

```text
очищенный сигнал (результат протокола, §6.1 шаги 0–8)
   → для каждой полосы набора:
        полосовой фильтр этой полосы (на continuous)
        → нарезка эпох → reject по BAD/reject_threshold
        → пики GFP внутри полосы → диполь на каждом пике → КД-вердикт (базис своей полосы)
```

Почему нельзя «посчитать один раз широкополосно и приписать полосам»: пик GFP широкополосного сигнала
почти всегда принадлежит α (её амплитуда максимальна), поэтому δ- и γ-«пики» окажутся не своими —
фитинг найдёт источник, которого в этой полосе нет. Это же объясняет, почему результаты по пресету «α»
и по «γ» расходятся по локации: они и должны расходиться.

### 8.3. Требование к длине эпохи — «эпоха длиннее волны»

Чтобы пик GFP в полосе был **пиком волны**, а не «куском монотонного подъёма», эпоха должна содержать
не меньше двух периодов нижней частоты полосы. Считается однозначно:

| Полоса | Нижняя частота | Период | Минимальная эпоха (2 периода) | Из `epoch_lengths_ms` |
|---|---|---|---|---|
| δ | 1 Гц (при дрейфе/«без фильтра» — ещё ниже) | 1000 мс | **2000 мс** | ровно 2000 — на пределе |
| θ | 4 Гц | 250 мс | 500 мс | 500…2000 |
| α | 8 Гц | 125 мс | 250 мс | 250…2000 |
| β | 13 Гц | 77 мс | 154 мс | 250…2000 |
| γ | 30 Гц | 33 мс | 67 мс | 250…2000 |

Вывод: **δ-анализ требует максимальной эпохи (≥2000 мс)**, иначе δ-«пик GFP» методически не определён.
Это ограничение сейчас нигде не сказано пользователю: предлагается предупреждать при выборе эпохи
короче «двух периодов полосы» — предупреждать, а не запрещать (правило «не зажимать молча»).

**То же требование распространяется на окно спектра и на фильтр** (уточнение владельца, 22.09.2026):
длина эпохи напрямую связана с размером окна расчёта спектра (`spectrogram.window_ms`: 64…4000 мс) и с
тем, что вообще пропускает фильтр полосы. Короткая эпоха = короткое окно = **медленный δ не «ловится»
вовсе**, а не «ловится хуже»: у 1 Гц период 1000 мс, и окно 250 мс физически не содержит волны. Отсюда
практическое правило согласования: **окно спектра и длина эпохи выбираются по нижней частоте полосы**
(≥2 периодов), и это должно быть видно в UI рядом с выбором длины эпохи, а не выясняться по форме
спектрограммы.

### 8.4. Что пользователь должен видеть из этого блока

- **По полосе — отдельный результат:** число пиков, число прошедших КД, медиана GOF, распределение по
  структурам, и строки «КД не прошёл — почему» (момент ниже X % максимума полосы или GOF ниже порога).
- **Полоса как измерение, а не кнопка:** набор полос показывается **одновременно** (таблица
  «полоса × показатель»), чтобы видеть, в каком ритме источник «жив», а где пусто.
- **Оговорка про δ и 250 мс** (§8.3) — прямо в месте выбора эпохи.
- **Цена:** число полос умножает время расчёта (точный фитинг ≈5,4 с на точку). Практичный сценарий:
  быстрый расчёт по всем полосам → точный фитинг только там, где есть кластеры (пересечение с
  `todo.md` 2.6/1.4). Это же снимает вопрос «10 полос × 200 точек = сутки счёта».

**Обратное следствие для верхних полос — «облако диполей»** (замечание владельца, 22.09.2026): у γ
период 25 мс, поэтому ограничение «эпоха ≥ 2 периодов» её не связывает: допустимы короткие эпохи, а
значит в одной и той же записи **в γ набирается кратно больше эпох и точек**, чем в δ. Это не «шум
метода», а полезный эффект: даже при упрощённом (быстром) расчёте плотное облако точек показывает,
**возле какой структуры мозга оно «топчется»**, — устойчивое сгущение читается как источник там, где
одиночная точка в δ ничего не доказывает. Следствие для плана: у полос разная «экономика» (δ — мало
точек, дорогих по времени эпохи; γ — много точек, дешёвых) и разный способ чтения результата
(плотность/облако против отдельной точки). Как именно это отображать в разделе «Диполи» и как
группировать в таблице диполей — **отдельное планирование (Часть 2)**, здесь фиксируется только
понимание, что оно понадобится.

## §9. Предлагаемые кирпичики (предложение владельцу, не правка `data-blocks.md`)

Часть 3 стратегии будет про носители и таблицы; здесь — только **что за структуры нужны**, чтобы
Часть 1 стала возможной. Нумерация продолжает реестр `docs/data-blocks.md` (B1…B9). Каждый кирпич —
по общим правилам §2 того файла (паспорт, базис, «измерено/модель/интерпретация», ключ + отпечаток).

| Кирпич | Что это | Ключ | Поля (суть) | Чем кормится |
|---|---|---|---|---|
| **B11 «QC-снимок записи»** (профиль грязи) | Измеренное качество **сырого** файла, до любых чисток | `recording_id` + отпечаток алгоритма QC | по каналам: SNR, «шумность», flat-line, клип, квантование; по частотам: остаток 50/100/150/200 Гц (дБ над фоном); по категориям 3.2–3.8: события + доля времени; фон и вердикт пригодности | L1, L2, частично L6 (§7) |
| **B10 «Протокол препроцессинга»** | Что именно сделано с записью: рецепт + фактически выполненные шаги | собственная `protocol_id` + отпечаток (параметры шагов) | `steps[]: {category, method (M1…M20), params, duration}`, `reference`, `band_hz`, `notch_hz[]`, версии инструментов, `warnings` | §6.1 шаги 0–8; журнал шагов |
| **B12 «Отчёт о потерях»** | Числа «до/после» для конкретной пары «протокол × параметры расчёта» | `protocol_id` + отпечаток параметров расчёта | L3 (Δ по полосам), L4 (сохранённая дисперсия), L5 (удалённая дисперсия), L6 (три уровня вывода), L7 (КД/GOF), L8 (сдвиг локации), L9 (цена) | §7 полностью |

Почему именно так, а не «полем в записи»: B11 — свойство **файла**, B10 — свойство **работы**, B12 —
свойство **пары**. Одна запись может иметь несколько протоколов, и сравнивать их — основная работа
исследователя (§10): сложи мы это в одно поле, сравнение стало бы невозможным, а «до/после» потеряло бы
смысл. Носители (файл задачи, кэш, БД) — Часть 3; связь с уже принятым решением `todo.md` 4.4
(результаты UI-разделов → `sessions`/`epochs`/`dipoles`) — там же.

## §10. Видение рабочего пространства (затравка Части 2)

**Блоки ниже — кандидаты, а не макет** (решение владельца 22.09.2026, вторая волна): *куда* и *в каком
виде* попадает каждый элемент, решается **по мере реализации методов** — сначала ручки и числа в UI,
ручные прогоны руками и глазами, и только потом раскладка. Таблица отвечает лишь на вопрос «что вообще
нужно иметь в разделе», чтобы новые числа качества было где посмотреть; порядок появления блоков и их
форма не фиксируются заранее.

**Вывод из §1–§8:** нужен **отдельный раздел** Главного меню (например «Качество и реставрация», между
«EDF» и «ЭЭГ»), потому что задача другая, чем у вьюера: не «посмотреть сигнал», а **сравнить состояния
и протоколы между собой**. Вьюер EDF показывает один сигнал в окне; здесь нужен стол с несколькими
дорожками и таблицей. Расширять вьюер — значит перегрузить экран, который уже несёт зум, эпохи, слои и
тулс-хедер.

| Блок | Что показывает | Откуда числа |

Сортировка, состав колонок и «без единого запроса» — по образцу таблицы локализации; источник — протокол + отчёт о потерях + журнал шагов | **B10 + B12** + журнал |

- правка **вида** (слои, масштаб, палитра) не запускает расчёт — считает кнопка;
- параметры расчёта — в URL (`todo.md` 3.2), чтобы состоянием можно было поделиться и вернуться;
- шаг протокола без числа — не шаг: в таблице 2 обязательны обе колонки «до» и «после»;
- «непригодно» — законный результат: при клиппировании раздел объясняет, что локализация выключена,
  а не показывает красивую пустоту.

## §11. Зачем это ИИ-агенту (затравка Части 4)

Цель, названная владельцем: агент, который **сам решает, какие процедуры провести** для конкретного
EDF. Из Части 1 для этого важны три вещи: **вход**, **единица решения** и **материал для обучения**.

| Компонент | Содержание | Почему именно так |
|---|---|---|
| **Вход агента** | Профиль грязи (**B11**) + требования задачи («нужна локализация γ» / «нужен спектр δ» / «нужно сравнить с сессией 2») + ограничения (время счёта, допустимые потери) | Агент не смотрит «сырые числа сигнала»: он работает с числами качества и паспортами — их можно проверить, объяснить и записать |
| **Единица решения** | **Рецепт**: список шагов (метод M# + параметры), ожидаемые потери (L3–L8), причина («сеть: гармоника 100 Гц на 18 дБ выше фона») | Рецепт — то же, что делает эксперт в §6.2; его можно принять, отклонить или исправить, и он воспроизводим |
| **Ответственность** | Агент предлагает — человек подтверждает. Методические числа (X % КД, порог GOF, границы полос) агент **не выбирает**: это значения эксперта (`concept.md` §11.3) | Иначе «умная кнопка» незаметно переопределит методику |
| **Материал для обучения** | Пары «профиль грязи → рецепт → L7/L8» из журнала шагов: `journal.jsonl` уже даёт «параметры → результат», к ним добавляются B11/B12 | Сначала правила, потом модель: пока замеров мало, §6.2 работает как детерминированный набор правил; когда накопятся десятки пар, появится то, на чём вообще можно обучаться |
| **Что должно попасть в журнал уже сейчас** | профиль (L1/L6), состав протокола (B10), метрики потерь (B12) — строкой на шаг | Если этого нет в журнале, обучать агента будет **не на чем**, и Часть 4 останется красивой идеей |

Практическое следствие для порядка работ: **Часть 1 и есть подготовка к агенту**. Не «сначала ИИ,
потом измерения», а наоборот — измерения качества, единообразный рецепт и запись «что получилось»;
именно они превращают задачу в вычислимую.

Границы, которых у агента быть не должно (предлагается зафиксировать сразу):

- агент не трогает «непригодные» записи (клип) — он их **называет** непригодными;
- агент не запускает расчёт на сотнях файлов без подтверждения человека (пакетный конвейер — С8);
- агент не может «улучшить» файл, изменив критерии: КД и пороги остаются экспертными;
- каждое решение агента объяснимо одной строкой «какая метрика его вызвала».

## §13. Препроцессинг: инвентарь, что добавляем и как это видно

Это секция-ответ на главный вопрос части: **какой вообще есть функционал поиска артефактов, какие
методы устранения добавляем, какая нужна дополнительная визуализация контроля, какие элементы
установки параметров и как оцениваются потери**. Инвентарь «как есть» — §2.1, методы — §5, потери — §7.

### 13.1. Инвентарь сегодня → цель, по категориям

| Категория (§3) | Детектор сегодня | Детектор по плану | Устранение по плану | Метрика контроля |
|---|---|---|---|---|
| 3.1 сеть (основа) | notch 50 Гц | + индикатор «дБ над фоном» | notch (есть) | L1 для 50 Гц |
| 3.1 **гармоники 100/150/200** | **нет** | поиск пиков по сетке 50 Гц, «дБ над фоном» | notch списком / `spectrum_fit` | L1 по 4 частотам |
| 3.2 кардио | попадает в общий peak-to-peak | шаблонный/автокорреляционный детектор по одному каналу | ICA/SSP (пачка C), прорезка интервалов | L5, L3 в δ/θ |
| 3.3 окулярные | peak-to-peak без различения | прокси по Fp1/Fp2 (пачка B) | SSP / ICA | L5, L3 фронтально |
| 3.4 ЭМГ | **нет** | `annotate_muscle_zscore` (пачка A) | метка + отбраковка эпох | доля времени, L6 |
| 3.5 дрейф/импеданс/шевеление | частично (фильтр, амплитуда) | критерий дрейфа, «одновременность» по каналам | фильтр, метки интервалов, интерполяция каналов | L2, L6 |
| 3.6 клип / разрыв / flat-line | flat-line (и то после референса) | доля клиппированных отсчётов; `annotate_nan`/`annotate_break` (пачка A) | метка «испорчено» / исключение | вердикт «непригодно», L6 |
| 3.7 импульсный мусор | z-score без различения | robust z-score (медиана/MAD) + длительность фронта (пачка A) | медианная правка/метка | L6 |
| 3.8 фон / квантование | нет | SNR по каналам, шаг квантования | не устранимо | L2 (паспорт) |

Пропусков «не измеряем» остаётся ровно один — **квантование** (не устранимо, только фиксируется в
паспорте). Всё остальное — вопрос работы, а не принципа.

### 13.2. Пачки методов A → B → C (порядок подтверждён владельцем 22.09.2026)

| Пачка | Состав | Новые зависимости | Что получает пользователь | Почему именно здесь |
|---|---|---|---|---|
| **A** — «дёшево и без зависимостей» | M9 ЭМГ, M10 разрывы/NaN, клип-детектор, M11 robust z-score, индикатор гармоник (L1) + M2 notch списком, предупреждение «эпоха/окно < 2 периодов» | нет (всё есть в MNE 1.13/numpy) | детекторы по категориям вместо трёх порогов; первое число качества; честный notch с гармониками; γ-вывод перестаёт быть «молча артефактным» | не меняет порядок пайплайна и контракты стадий — можно делать сразу |
| **B** — «порядок и структура» | решение по референсу (после чистки), QC/детекторы на сыром, три уровня потери + M15 прорезка интервалов, M8 прокси-окулярные, кардио-детектор, M12 интерполяция каналов, L3 Δ-спектр | нет | сравнение «до/после» в числах; канал можно заменить, а не потерять молча; δ/θ перестают «страдать» от кардио и моргания | меняет порядок шагов и API стадий — лучше, когда категории уже считаются |
| **C** — «после 2.1» | достижимая ICA (M6, `todo.md` 2.1) + обязательная метрика L5; далее по надобности M7 `mne-icalabel`, M19 `autoreject`, M18 ASR | `mne-icalabel` / `autoreject` — новые зависимости | автокомпоненты и автоматические пороги вместо ручных | наибольший риск потери сигнала → идёт после того, как потери можно измерить |

Правило перехода между пачками: **пачка считается пригодной к работе только тогда, когда её шаги
попадают в протокол (B10) и дают измеримую метрику (§7)**. Иначе получается «кнопка, которая что-то
делает», — ровно то, от чего проект уходит.

**Чего пачки НЕ означают** (решение владельца 22.09.2026, вторая волна): A → B → C — это порядок
**разработки** по стоимости и зависимостям (дёшево без новых библиотек → структура пайплайна → ICA), а не
утверждённая методология. Порядок применения шагов внутри записи, значения по умолчанию и «правильный»
рецепт **заранее не проектируются**: сначала все ручки и вся визуализация выводятся в UI, запись
прогоняется руками и глазами, и только потом принимаются решения о дефолтах и последовательности.
Представлять результат мысленно по документации и учебным примерам MNE — знанием не считается.

**Порядок и место заранее не назначаются** (решение владельца 22.09.2026, вторая волна): элемент
выводится вместе с методом, который даёт его числа, и размещается там, где удобно по факту — раскладка
решается по мере реализации, а не проектируется на бумаге. Пачки задают только естественную связку
«метод → его элемент»: №1 и №3 появляются с пачкой A (новые категории и первое число), №2, №6, №7 — с

PSD и оба сигнала). Жёстко решено только два места: раздел «Качество и реставрация» — отдельный, таблица
шагов — в разделе «Таблица» (`/table`).

### 13.4. Элементы установки параметров (только из существующего `shared/ui`)

**Главное решение (владелец, 22.09.2026, вторая волна): дефолты заранее не назначаем.** Все опции
параметризации выводятся в UI как ручки, а значение по умолчанию задаётся **после** ручных прогонов, когда
видно, что вообще даёт метод. Поэтому в колонке «значение» стоит либо факт текущего кода, либо «крутить при
тестах» — и никаких «решений эксперта по числам» до экспериментов.

| Группа параметров | Поля | Контрол | Значение (менять при тестах) | Примечание |
|---|---|---|---|---|
| Пороги амплитудных детекторов | z-score, peak-to-peak, flat-line (мкВ/мс) | `NumberField` | текущие: 5 / 100 мкВ / 1 мкВ / 200 мс (из `/meta`) | сохранить как есть, пока не проверено руками |
| **Категории детекторов** | 8 переключателей «искать ЭМГ / разрывы / кардио / окулярные / клип / дрейф / сеть / гармоники» | `CheckboxRow` | включать/выключать вручную при тестах | вместо «всё сразу тремя порогами» |
| Сеть | notch `0 / 50 / 60 / 50+гармоники / свой список` | `SegmentedControl` + поле списка | крутить при тестах | стадия «Фильтр и референс» |
| Пороги качества | «дБ над фоном», доля клипа, SNR | `NumberField` | числа появятся после тестов (§14) | нужны для вердикта B11 |
| Референс | средний / по каналам / **сырой** (для QC) | `SegmentedControl` | решено: average, но **после чистки** | решение 22.09.2026 (волна 1) |
| Длина эпохи и окно спектра | длина эпохи + `window_ms`, подпись «≥2 периодов полосы» | `SelectField` + `NumberField` | текущие значения + подпись-предупреждение | предупреждение, а не запрет |
| Протокол | выбор рецепта, «Применить», «Оценить потери» | `SelectField` + кнопки | — | считает только кнопка |

Правила, которые эти контролы обязаны соблюдать (уже приняты в проекте): правка параметра **не
запускает** расчёт; параметры живут в URL по стадиям (`STAGE_PARAM_KEYS`); значения по умолчанию берутся
из `/meta`, а не дублируются в UI; ошибка в параметрах — 400 с понятным текстом, а не «странная картинка»;
группа полей соответствует шагу протокола.

### 13.5. Оценка потерь: фазы

Деление на фазы — про **доступность данных** (что можно посчитать, не перестраивая движок), а не про
приоритеты: состав метрик уточняется по факту ручных прогонов, и ни одна фаза не назначает «допустимые»
значения.

| Фаза | Метрики | Что нужно, чтобы посчитать | Куда выводится |
|---|---|---|---|
| **1** (из уже считаемого) | L1 остаток наводки, L2 профиль каналов, L6 «выведено» (3 числа), L9 время, события/доля времени по категориям | один PSD + `zones`/`stats` + журнал | паспорт качества, строка в журнале |
| **2** | L3 Δ-спектр по полосам, L4 сохранённая дисперсия | второй PSD (очищенный) в той же задаче | наложение спектров, отчёт |
| **3** (после пачек B/C) | L5 удалённая дисперсия ICA/SSP, L7 КД/GOF «до/после», L8 сдвиг локации, мм | два прогона расчёта по одним параметрам + отпечаток | кнопка «Сравнить протоколы», таблица шагов |

Оговорка та же, что в §7: ни одна фаза не вводит свёрнутого «балла качества». Пользователь видит
вектор; вывод (какой протокол лучше) делает эксперт по L7/L8, а не приложение по одной цифре.

## §14. Вопросы: что решено, а что отложено до ручных прогонов

**Первая волна: решено 22.09.2026 (владелец)**

- **Референс** — QC и детекторы считаются на сыром (неотреференсированном) сигнале, референс
  применяется после чистки; реализационное следствие — в §6.1.
- **Раздел Главного меню** — отдельное пространство «Качество и реставрация» между «EDF» и «ЭЭГ»,
  таблица шагов — в разделе «Таблица» (см. §10 блок 7).
- **Длина эпохи ↔ окно спектра ↔ фильтр** — не вопрос, а проверяемое следствие: ≥2 периодов нижней
  частоты полосы (§8.3), иначе медленный δ не «ловится» вовсе.
- **Порядок работ по препроцессингу** — пачки A → B → C (§13.2).

**Вторая волна: как работать над функционалом (решение владельца, 22.09.2026)**

Владелец снял почти все шесть вопросов не ответом по существу, а **правилом работы**: пока функционал
нарабатывается, заранее не планируем ничего — все ручки и вся визуализация выводятся в UI, прогоняются
руками и глазами, и только потом решается, что делать значениями по умолчанию и в какой
последовательности применять шаги. Мысленно представлять результат по документации и учебным примерам
MNE — бесполезно. Итог по вопросам 1–6:

| Был вопрос | Итог |
|---|---|
| 1. Числа порогов «грязно/чисто» | **Не назначаем заранее.** Пороги выводятся ручками в UI; числа (и сам вердикт «грязно») появятся, когда будет на чём их проверять. Пока этого нет, B11 показывает измеренное и честно молчит вместо светофора. |
| 2. Список гармоник | **Ручка в UI**: `0 / 50 / 60 / 50+гармоники / свой список`, вплоть до Nyquist. Что оставить дефолтом — решение по результатам прогонов. Индикация остатка (L1) полезна на всех 4 частотах независимо от настройки. |
| 3. Моргание vs фронтальный ритм | **Основной детектор заранее не выбираем:** прокси Fp1/Fp2, SSP и ICA-авто выводятся как переключаемые варианты, сравнение на записях глазами — и только потом решение. |
| 4. Допустимые потери | **Числовых пределов не вводим.** Пользователь видит вектор L-метрик; автоматика (если появится) ограничится техническим «непригодно» (NaN/разрывы/мёртвые каналы) — и это тоже проверяется руками. |
| 5. Хранение протоколов | **Решено: обязательно уже сейчас, файлом** — результат задачи (`job_store`) + журнал шагов. Таблица в БД — позже, если понадобятся запросы по протоколам. |
| 6. Пакетный режим и агент | **После ручного тестирования методов.** Ни пакетный прогон, ни агент не проектируются, пока не пройдены прогоны руками и глазами. |

**Отложено до данных на руках:** числа порогов и сам вердикт пригодности; состав списка гармоник по

## §16. Итог Части 1

1. **Грязь нужно описывать каталогом категорий** (§3) с четырьмя обязательными ответами каждая; по

4. **Порядок операций: одно решение принято, одно остаётся** (§6.1, §14): место референса решено
   22.09.2026 (QC и детекторы — на сыром сигнале, референс — после чистки); три уровня потери

   журнал «параметры → метрики», то есть ровно то, что описано в Частях 1–3.
