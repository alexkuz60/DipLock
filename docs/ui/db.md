# UI §3.10 — БД: записи, готовность результатов, выборка

### 3.10 Раздел «БД — записи и результаты» (`/db`)

**Срез 13.11.2026 (готово):** раздел — визуальный контроль **всех обработанных
ЭЭГ-записей** и степени готовности записанных в БД результатов расчётов, чтобы
не пересчитывать препроцессинг/эпохи/диполи/отчёт заново при каждой загрузке
файла. Раздел **только читает БД**: единственные запросы — `GET
/recordings/readiness` (страница) и `GET /recordings/{id}/readiness` (карточка
по раскрытию строки); ни одной задачи/расчёта раздел не запускает (правило
«Обработка — только по кнопке» выполняется по определению).

**Таблица записей** — семантическая `<table>` со «липкой» шапкой, строки =
записи зеркала `recordings`:

* **Готовность** — «k из N» стадий с записанными результатами + пилюли стадий
  (✔ готово / — нет, тултип — дата последнего прогона): `preprocess`
  (препроцессинг чистки + нарезка эпох), `dipoles` (быстрый расчёт/уточнение),
  `package` (пакет поддиапазонов), `report` (автоотчёт), `spectrogram`.
* **Параметры последних прогонов** — компактные сводки по каждой готовой
  стадии (например «Препроцессинг: 0.5–45 Гц · notch 50 · average · ICA ·
  эпохи 2000 мс · 10/12»): полоса фильтра, notch, референс, метод чистки,
  пороги детекторов, режим/длина нарезки и счётчики эпох, полосы пакета с
  границами Гц, шаг сетки и метод диполей, QC отчёта. `None` контракта —
  честный прочерк «—» («не измерено», а не 0 — инвариант read-API).
* **Раскрытие строки** (клик) — карточка готовности: по каждой стадии полный
  список параметров прогона и **история прогонов** (дата, задача, отпечаток
  `params_sig`); история не UPSERT (§8.4.2 `docs/rules/results-db.md`): повторный
  расчёт добавляет прогон, карточка показывает все, страница — последний.
* **Группировка по испытуемому** (`patient_alias`): у одного человека в работе
  обычно 5–10 файлов — они читаются одной сворачиваемой группой с счётчиком
  «записей N, с результатами M» и кнопкой «Выбрать группу». Режим
  «плоский список» — в панели; сортировка — новые сверху / по имени / по
  готовности.

**Выборка записей и групповой анализ.** Чекбоксы строк (мультивыбор, порядок
выбора сохраняется) — вход для раздела «Групповой анализ»: кнопки тулс-хедера
«В пару (A/B)» (ровно 2 выбранные: A — первая, B — вторая) и «В группу (N>2)»
(2 и больше, порядок выбора = порядок колонок тепловой карты) заполняют
`groupCompare`/`groupRun` и переходят в `/group`. Выборка — состояние сессии
(после перезагрузки набирается заново), настройки просмотра (фильтры,
группировка, сортировка) персистятся (`shared/state/dbView.ts`).

**Панель «Опции»**: «Фильтры» («только обработанные» — серверный `EXISTS`-фильтр
шаблона D, поиск по файлу/псевдониму/id — мгновенный, на клиенте),
«Группировка и сортировка», «Выборка» (счётчик, «Снять выделение»), «Справка»
(расшифровка готовности). Правка параметра ничего не запускает — только
перечитывает страницу.

**Срез 2 (13.11.2026):** поиск, сортировка и пагинация — **серверные**
(шаблоны E–F `docs/rules/results-db.md`): поиск по файлу/псевдониму с задержкой
300 мс, сортировка «новые сверху / по имени / по готовности», страницы
50/100/200/500 записей с навигацией «Назад/Вперёд» и подписью «X–Y из N»
(смена фильтра/порядка возвращает на первую страницу). Кнопка «Открыть» строки
переносит запись в раздел «EDF» (`openRecordingById`, `?rec=` дописывается в URL
зеркалом — ссылка воспроизводима). «Экспорт CSV» — по выборке (чекбоксы):
паспорт, готовность и параметры прогонов, одна строка на запись (RFC 4180,
`shared/lib/dbExport.ts`); выбранные записи с других страниц дочитываются
карточкой готовности — выборка не обрезается границей страницы.

**Срез 3 (13.11.2026 (2)):** выгрузка выборки в трёх форматах (`shared/lib/
dbExport.ts`, клиентские, без запросов — данные уже в строках таблицы):
**CSV** (срез 2), **JSON** (строки контракта `RecordingReadiness` без потерь +
`schema_version`/`exported_at`) и **сводный HTML-отчёт** «Отчёт HTML» по
выборке — самодостаточный документ (стили внутри, печатается без приложения):
группировка по испытуемому, паспорт записи, готовность «k из N» и параметры
каждой стадии (пустые — прочерк «—», «Параметры прогона не записаны»); имена
файлов/псевдонимы экранируются (`<script>` — текст, не разметка). Выборка
собирается едино: строки текущей страницы + дочитывание карточкой для
страниц других.

**Срез 4 (16.11.2026): удаление выбранных записей.** Кнопка «Удалить (N)»
тулс-хедера работает по выборке (чекбоксы) и требует **два шага**: первый клик
показывает «Подтвердить удаление (N)» и «Отмена» (DELETE уходит только вторым —
проверка выборки до каскада), кнопка подтверждения помечена цветом опасности.
Удаление — существующий каскад `DELETE /recordings/{id}` (§8.4.3
`docs/rules/results-db.md`: файл, кэши и строки результатов), по одной записи:
отказ одной не мешает остальным. Отказавшие записи **остаются выбранными** с
текстом ошибки рядом («Не удалены: id — причина»), успешные уходят из выборки;
страница готовности перечитывается (`invalidateQueries`), открытая в EDF запись
среди удалённых закрывается (`dbActions.deleteRecordings`). Действие
разрушительное, поэтому без подтверждения запросов нет — это проверяет
`DbToolActions.test.tsx`.

Дальше (при потребности): открытие уже собранных автоотчётов записей
(`report_runs` → HTML) прямо из строки.
