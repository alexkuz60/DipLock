# Кирпичики: структура данных до накопления

> **Статус:** черновик к правкам владельца (20.09.2026). Смыслы — `concept.md` (там же §11:
> перед планированием шага освежить память по §1–§3 и §6). Этот файл отвечает на другой
> вопрос: **из каких блоков собирается приложение и что лежит в каждом** — чтобы данные не
> начали копиться в неверной форме.
>
> **Структура БД сознательно отложена** (решение владельца 20.09.2026): сначала кирпичики —
> что и с какими полями, потом таблицы. Физические носители сегодня описаны в
> `docs/data_map.md`; когда у кирпича появится носитель (кэш, файл, таблица), строка уходит
> туда.

## 1. Зачем этот слой

Кирпич описывается **до** кода: имя, что это, ключ, поля, паспорт, носитель. Код кирпича живёт
в одном сервисе (`backend/app/services/*`); «новый кирпич» = строка в реестре + правило, и
только потом расчёт. Так мы сначала договариваемся о структуре, а не переделываем её после
первых сотен записей.

## 2. Общие правила кирпичиков

1. **Паспорт обязателен.** Кирпич = паспорт (что это, чем получено, на каких параметрах) +
   значения. Числа без паспорта — не кирпич.
2. **Базис у каждого порога.** Порог несёт базис: «абсолютный» или «доля от максимума своего
   поддиапазона» (`concept.md` §3): в γ и α абсолютные числа несравнимы.
3. **КД — вердикт, а не отображение.** Составной критерий (момент ≥ X % максимума поддиапазона
   И GOF ≥ порога) — поле кирпича дипольной точки и параметр анализа: он решает, что попадает
   в кластеры и статистику.
4. **Три уровня различаются.** Измерено / модель / интерпретация — в полях и подписях, как
   требует `concept.md` §8.
5. **Идентичность кирпича.** Ключ + отпечаток параметров: один и тот же расчёт не путается с
   другим, а разные не сливаются в один.
6. **Один кирпич — один владелец в коде.** Нет владельца — нет кирпича.

## 3. Решения владельца (20.09.2026)

- **Порядок работ:** (1) согласовать реестр кирпичиков → (2) спектр (B4 + B5) → (3) дипольная
  точка и прогон по поддиапазонам (B6 + B7). Структура БД — **позже**, «совсем рано».
- **В спектральном кирпиче (B4) хранятся два дополнительных поля: «диапазон частот»** (границы
  полосы записаны явно) **и «максимум в диапазоне»** (нормировочная база).
- **Записи группируются по «эпоха + время», и «время» — это момент пика GFP** (решение владельца,
  20.09.2026): спектр привязывается к тем же моментам, что и диполи. Поэтому спектральная величина
  (B4) и дипольная точка (B6) соединяются по одному ключу — (эпоха + момент пика), а не сопоставляются
  «на глазок» по сессии.
- **Спектр считается по эпохе целиком** (решение владельца, 20.09.2026; вариант B): момент пика —
  **метка привязки** к дипольной точке, а не окно расчёта спектра. Отдельного окна «пик ± N мс»
  в B4 нет.
- **Пик GFP специфичен для поддиапазона** (наблюдение владельца, подтверждено кодом): пики
  считаются по сигналу, отфильтрованному в своей полосе (`DipoleScanParams.filter_band`, фильтр
  применяется до нарезки эпох), а длина волны у δ и γ разная — значит максимумы пиков лежат внутри
  эпохи в **разные моменты**. Следствие: пик — свойство пары **«эпоха × поддиапазон»**, и входит
  в ключ кирпичей вместе с поддиапазоном, а не как поле эпохи.
- **«Максимум в диапазоне» (B4) — два поля** (решение владельца, 20.09.2026; вариант C):
  «**полка**» — максимум мощности полосы по эпохам сессии, `band_power_max_uv2` (мкВ²), к ней
  относится X % для КД; «**пик по частоте**» — максимум PSD внутри полосы, `psd_peak_uv2_hz`
  (мкВ²/Гц) вместе с частотой пика `psd_peak_hz` (Гц — предлагаю; поправьте, если частота не нужна).
  Частота пика — готовый вход для выбора узких поддиапазонов (С3).
- **Единицы (B4):** имя поля несёт единицу — `band_power_uv2`, `psd_uv2_hz`, `relative_power`,
  `iaf_hz` (как уже принято в проекте: `amplitude_nam`, `pp_threshold_uv`). Децибелы — только
  представление (как сетка `DPS2`), не единица хранения; `None` вместо нуля, когда не измерено.
- **Набор полос (B7):** базовые пресеты из `freq_bands` (`/meta`) + полосы эксперта + «свой набор»
  с сохранением именованного набора. Набор — это **данные** (список границ) с отпечатком, а не
  хардкод в UI: новая полоса эксперта не должна требовать правки кода.
- **Канал в B4 — измерение структуры, а не обязательный выход сейчас** (решение владельца,
  20.09.2026; вариант D): числа по каналам включаются по потребности (топология, связность), сейчас
  достаточно среднего по каналам и топокарты картинкой. Среднее и любые группы (полушария, области)
  — **производные** от канального измерения, а не его замена.
- **Общий пик по широкой полосе не вводим** (по рекомендации, 20.09.2026): пик считается только
  внутри своего поддиапазона, а «насколько пики разъехались» видно прямо из B4/B6 — в момент пика
  того или иного поддиапазона. Если позже понадобится якорь эпохи, это одно число в паспорте эпохи,
  а не новое измерение.
- **Спектрограмма сессии — агрегат B5, отдельного кирпича нет** (решение владельца, 20.09.2026):
  непрерывная STFT-сетка «время × частота» остаётся представлением по одному каналу
  (`services/spectrogram.py`, контейнер `DPS2`, раздел «ЭЭГ»), а «общая картина сессии» собирается
  из рядов B5 по поддиапазонам. **Уточнение (ревизия 29.09.2026):** «агрегат» — в смысле
  представления, а не пересчёта: STFT считается по непрерывному сигналу иным методом (окна,
  перекрытие), чем PSD B5 (Welch/multitaper по эпохам в их пиках) — численное совпадение сетки и
  рядов B5 не ожидается и не должно стать целью.

## 5. B4 и B5: поля (шаг 2 порядка работ)

окно — эпоха целиком; единицы — в имени поля; канал — измерение структуры, включается по
потребности. Колонка «сегодня» говорит, что уже есть в коде, а что предстоит.

### 8.4. Решения по открытым вопросам (**решено делегированным решением 01.10.2026**, критерий — «лучше для эффективной помощи пользователю»)

1. **`warnings`/QC-причины — JSON-колонки** в `report_runs` (состав свободный, как у
   `job_result`): по текстам предупреждений SQL не нужен, **ничего из сказанного сервером не
   теряется**; числовые поля QC (`qc_status`, `good_data_percent`) — отдельными колонками, по
   ним — сортировка и фильтр.
2. **История прогонов, не UPSERT по `params_sig`**: каждая задача оставляет свою строку,
   «последний отчёт» — `ORDER BY created_at DESC LIMIT 1`; UPSERT теряет «что было раньше»
   (пользователь видит динамику пересчётов) и конфликтует с моделью «задача → файл
   результата» (`job_store`). Повтор с тем же отпечатком — честная новая строка.
3. **TTL строк = TTL записи**: дочерние строки чистятся каскадно вместе с `recording`
   (тот же жизненный цикл, что у `cache/reports/` в `orphans.py`); результаты переживают
   нынешний 24-часовый TTL реестра (в этом смысл 4.4 — «записи не 24 ч») и не осиротеют без
   записи.
4. **`report_name_counts` — все имена, не топ-N**: счётчики считаются на весь словарь
   (`struct_counts` в `report.py`), топ-5/12 — вопрос отображения HTML; в БД писать полный
   срез, иначе ROI-анализ 4.5 упирается в обрезанные топы. Объём — сотни строк на прогон.
   При внедрении `summarize_band` отдаёт полный счёт рядом с `top_*` (изменение 4.4, не §8).

**Порядок внедрения (решение того же делегирования):** ① `recordings` + TTL + PHI-псевдоним
(4.4, как написано в `todo.md`) → ② `sessions`/`epochs`/`dipoles` (write-API результатов UI-разделов,
остаток F21) → ③ `analyses`/`analysis_bands`/`dipole_points` + `report_*` (кирпичный слой B6/B7/B13,
пишется прогоном отчёта). Каждый шаг — свой срез с миграцией и тестами.
