## 1. Алгоритм: канонический порядок (консенсус всех пяти)

```
[«Нейромузыка»: мастер 48 кГц]        [«ЕмоЛаб»: wav/mp3 → моно 32 кГц]
        └────────────┬──────────────────────┘
                     ▼  (backend, один раз)
  окна FFT 32768, шаг 32000, zero-pad хвоста        → §2
  |X_m| полного FFT (прямоугольное окно)             → §2
  14 октавных блоков (2^b−1, 2^b), b = 1…14          → §2
  7 счётчиков C_k = блок(k+1) + блок(k+8)            → §2
  дБ: 20·log10(C/P), P глобальный → % радиуса        → §2
  emo.json v6: frames[{t_sec, rays[7]}] + key_track + tempo_track
                     ▼  (frontend, каждый кадр анимации)
  дБ-диапазон (опция) → интерполяция → вращение по аккордам
  → темп-коррекция → условная нормализация → вершины → доминанты
```

Инварианты, подтверждённые **всеми** экспертизами и кодом:

* расчёт двухэтапный: бэкенд считает **только данные кадров** (7 чисел на
  кадр + карты VAMP), вся геометрия — на клиенте; граница — контракт
  `AudioEmoOut` (`emo.json`);
* порядок шагов в кадре **нельзя переставлять**: лучи dB → дБ-диапазон →
  вращение (углы) → темп-коррекция (по углам **после** поворота) → вершины →
  доминанта → облако/центроид;
* математика одна на оба входа и параметризована `fs_audio` (кадр 1 с
  «ЕмоЛаб» / 2/3 с «Нейромузыка»);
* «эмо» — **номинальная семантика** партитуры: kimi формулирует это прямо
  («никакой эмоциональной модели в этой цепочке нет: звезда — спектральный
  профиль громкости трека, повёрнутый по аккорду и растянутый по темпу»),
  остальные подтверждают (подписи δ…γ-high — имена/цвета UI, не полосы
  `freq_bands`).

## 2. Пошаговый кросс-разбор

Для каждого шага: **Совпало** (консенсус экспертиз = код), **Расхождения**,
**Предложения** (из экспертиз), **Рекомендация** (итоговая).

### 2.1 Подготовка данных (входы, VAMP)

**Совпало (все пять):** моно `(L+R)/2` (каналов > 2 — первые два); «ЕмоЛаб» —
зонд `sf.info`, отказ 400 при > 1800 с / NaN/inf / не-аудио, ресемпл
`resample_poly` (kaiser) в 32000 Гц, `fs_source` в паспорте; «Нейромузыка» —
мастер 48 кГц после пик-контроля 0.891; VAMP — WAV PCM_16 моно, отдельный
GPL-процесс, `VAMP_PATH` явно, таймаут 300 с, **best-effort** (`null` при
отказе, расчёт не падает); порядок конвейера «ЕмоЛаб»: декод → аккорды → темп →
сегменты → ФФТ-кадры → кэш `emolab/{track_id}/` (манифест = коммит, sha256
дедупликация, семафор ≤ 2).

**Расхождения:** нет содержательных. Мелкие акценты: ds — точные проценты
статуса и `VAMP_TIMEOUT_S = 300`; qwen — параметры transform-файлов
(Chordino step 0.1 с / block 0.512 с, ловушка hop 0.2 с; tempo — 512/1024 при
rate 44100; segmenter 32к — 6400/19200); mimo — обобщённо.

### 2.2 Сетка кадров

**Совпало:** окно `N = 32768`, шаг `H = 32000`, перекрытие 768; старты
`s_k = k·H`; число кадров `K = ⌈(Nсэмпл − N)/H⌉ + 1` (при `Nсэмпл ≤ N` — один
кадр, при `Nсэмпл ≤ 0` — ноль); хвост добивается нулями; `t_sec = s_k/fs`;
кадр = 1 с (32 кГц) / 2/3 с (48 кГц); сверка: `32768 → 1`, `32769 → 2`,
`64768 → 2`, `64769 → 3`, `96000 → 3` (ds — таблица, qwen — сверочные числа).

**Расхождения:** формулировка kimi/gml/ds «окон из одних нулей не появляется»
верна по числу кадров, но последний кадр может быть **почти целиком из нулей**
(`64769` сэмплов → третий кадр с 769 реальными) — нюанс озвучивают только mimo
(«добивка нулями») и qwen («zero-pad занижает энергию последнего кадра»).

**Предложения (qwen §15.6):** масштабировать суммы на долю заполнения окна;
трактовать `t_sec` как центр тяжести кадра `t + hop/2` (сейчас — начало окна).
Обе правки меняют данные → только вместе с решением по §2.6.

### 2.3 ФФТ и бины

**Совпало:** `X = np.fft.fft(окно)` — **полный** комплексный спектр (не
`rfft`!), амплитуда `A_m = |X_m|`, окно **прямоугольное** (без аподизации,
буквально спецификация), нормировки на `N` нет (сокращается в `S/P`);
участвуют бины **1…32766** (бин 0 и бин 32767 — вне); `f_m = m·fs/32768`
(Δf = 1.4648 Гц @48к / 0.9766 Гц @32к).

**Расхождения:**
* mimo пишет «DC и **Найквист** вне расчёта» — **неточно**: исключены бины 0 и
  32767; Найквист-бин 16384 **участвует** (входит в блок 14) — ds и qwen
  раскрывают это явно;
* мотивация лог-шкалы у kimi («из-за утечки») расходится с содержательной
  мотивацией остальных (шкала громкости, «дыхание» трека);
* утечка прямоугольного окна: все упоминают; qwen измерил — боковые лепестки
  ±13 дБ, на чистом тоне соседний луч получает ~74 %.

**Предложения (qwen §15.6):** окно Hann/Hamming (снижает утечку, **меняет
данные** → к §2.6).

### 2.4 Октавные блоки

**Совпало (формулы идентичны у всех):** блок `b = 1…14`: `start = 2^b − 1`,
`width = 2^b`, бины `[2^b − 1 … 2^(b+1) − 2]`; покрытие бинов **1…32766 ровно
по одному разу** (`Σ ширин = 32766`; страж-тест
`test_octave_blocks_cover_bins_once`).

**Расхождения — только в таблицах чисел** (формулы везде верны):

| Источник | Статус таблиц |
|---|---|
| ds §4.1 | **эталон** (бины и Гц @32к/@48к сходятся полностью) |
| qwen §8.2 | верна; но qwen §7 — **сбои** в строках 9–14 («996.09», «1992.19», «24000.98» против эталонных 998.05 / 1998.05 / 23998.54) — несогласованность §7 ↔ §8.2 |
| gml §4 | бины верны; Гц @32к сбоят в строках 11–14 («3997.85», «7995.12», «15996.09») |
| kimi §A4 | верна (мелочь: верх блока 14 «31999.0» вместо 31998.05) |
| mimo §5 | **таблица неверна**: бины нижних блоков счётчиков 2–6 — 7–12, 13–24, 25–48, 49–96, 97–192 вместо 7–14, 15–30, 31–62, 63–126, 127–254 (формулы §4/§5 при этом верны) |

**Рекомендация:** канон — эталонная таблица §3; архивные экспертизы не править,
ошибки зафиксированы здесь (F11).

### 2.5 Семь счётчиков

**Совпало:** `C_k = S_{k+1} + S_{k+8}` (свёртка `index % 7`); бинов на счётчик
`2^(k+1) + 2^(k+8) = 129·2^(k+1)` — 258 / 516 / 1032 / 2064 / 4128 / 8256 /
16512 (Σ = 32766); луч k несёт имя `BAND_ORDER[k]` (δ…γ-high).

**Совпавшие независимые наблюдения** (каждый нашёл со своей стороны):
* счётчики **не нормированы на ширину**: у луча 6 в 64 раза больше слагаемых
  (ds «структурно завышен», qwen «веер +6 дБ/луч на белом шуме» с замерами
  `39.8 / 49.9 / 59.7 / 70.0 / 79.7 / 90.0 / 100`, mimo «§15.5»);
* подписи δ…γ-high — **не** границы полос `freq_bands` (ds §4.2, gml §5,
  kimi §A5, mimo §5; qwen §8.5 — количественно, см. ниже).

**Расхождения:** нет (кроме таблиц чисел §2.4).

### 2.6 Зеркало полного FFT и блок 14 — главная содержательная находка

**Эталон (прогон саммари):** для вещественного сигнала `|X_m| = |X_{N−m}|`,
поэтому блок 14 (бины 16383…32766) = бин 16383 + Найквист 16384 + **зеркала
бинов 2…16383** — почти вся спектральная сумма (тождество `np.isclose = True`;
у qwen в замере то же: «262153.435351 = 262153.435351»). Следствия (ds §5,
qwen §8.3 / §15.5):

1. `S_6 ≥ S_k` для всех `k` доказуемо; луч 6 — не «высокая гамма», а
   **широкополосный интегратор полного спектра**, = 100 % почти в каждом кадре
   (замеры qwen на белом/розовом/красном шуме, тоне и семи стемах; саммари —
   `argmax = 6` во всех кадрах шума; синус 100 Гц —
   `[55.9, 55.8, 56.9, 59.7, 70.8, 91.3, 100]`);
2. `P = global_max` фактически = «полная энергия самого громкого кадра» (это
   всегда счётчик 6), а не пик отдельной полосы;
3. доминанта кадра и суммарная **систематически подтянуты** к направлению
   `θ_6 + φ` (64.286° + φ) — смещение расчётное, а не содержательное;
4. форма звезды несёт на 1/7 меньше независимой информации: на тоне 1 кГц
   `S = [0, 8637.8, 0, 0, 0, 0, 8637.8]` → `rays = [0, 100, 0, 0, 0, 0, 100]`
   («содержание» и «зеркало» равны в разных лучах).

**Кто увидел:** qwen — полностью (доказательство + замеры + последствия);
ds — полностью (§5 + ссылка на тест-контракт
`test_sine_peaks_in_counter_of_its_bin_and_mirror`; позиция ds: «это текущий
контракт алгоритма, а не рекомендация к исправлению»); kimi — частично
(«блок 14 состоит в основном из зеркала», но без количества последствий и с
неподтверждённым тезисом «осознанная особенность спецификации»);
**gml и mimo — не увидели** (привели Гц блока 14 как реальные частоты выше
Найквиста).

**Предложения по исправлению (qwen §15.5):**
* **A.** считать блоки только по положительным частотам (бины 1…16383) —
  убирает дублирование;
* **B.** нормировать счётчик на ширину блока (`S_k / width_k`) — убирает и
  дубль, и «веер» §2.5;
* **C.** оставить как контракт (позиция ds), но раскрыть в описании шкалы
  («0 дБ = полная энергия громкого кадра») и в тултипах UI.

A/B меняют данные → `schema_version` +1 и пересчёт кэшей (`emo.json` v6 → v7);
текущее поведение воспроизводимо и покрыто тестами — **решение за владельцем
метода**.

### 2.7 ДБ-шкала и глобальная нормировка

**Совпало (все пять, формулы идентичны):** референс глобальный
`P = max C_k` по всем счётчикам всех кадров (`global_max`);
`db = 20·log10(C/P)` (множитель **20** — счётчики суммируют амплитуды, не
мощности); `pct = 100·(db + 60)/60`, clip 0…100; `C = 0` → 0 % без `log10(0)`;
округление лучей до 3 знаков; шкала **глобальная** → звезда «дышит» с
громкостью (тихий кадр сжат, громкий расправляет); «один громкий участок
опускает остальные кадры» — осознанное следствие, не баг (ds §6.3).

**Мелкие расхождения акцентов:**
* ds — эквивалентная форма `pct = 100·(1 + log10(S/P)/3)`, таблица
  `S/P → db → pct` (1/2 → −6.02 дБ → 89.97 % и т.д.), «60 дБ = коэффициент
  1000 по амплитуде»;
* kimi — мотивация лог-шкалы «утечкой спектра» (единичное расхождение;
  содержательная мотивация — громкость/динамика);
* mimo — «данные глубже −60 дБ не сохраняются» (совпадает с ds/qwen).

**Предложения:** перцентильный референс вместо `max` (mimo §15.2 — альтернатива
устойчивая к всплескам; не реализована, меняет данные).

### 2.8 Динамический диапазон в UI (`raysDbRange`)

**Совпало:** перенос окна `[−60…0]` → `[−D…0]` дБ без пересчёта анализа:
`scale = fromFloor / toFloor` (−60→−40 = ×1.5; −60→−96 = ×0.625), зажим
0…100; окно шире серверного **не восстанавливает** данные ниже −60 дБ;
применяется **до** вращения и темп-коррекции (единое место — `scaledFrames`,
«Эмограмма» читает ту же шкалу).

**Расхождения — в оценке, а не в механике:**
* qwen §15.3: **имя параметра не совпадает с математикой** — «−96» сжимает
  видимые значения (0 дБ не доходит до обода: 62.5 % R), а не расширяет
  диапазон; в «−40» всё громче −20 дБ прижимается к ободу;
* ds §7: зажим в «−40» меняет относительные длины лучей, а значит **и
  направление доминанты** — побочный эффект, который UI не проговаривает;
* gml §8: защищает выбранную линейность («обрезанная тишина не выпрыгивает из
  центра»).

**Предложения (qwen §15.3):** переименовать параметр («Наклон шкалы /
цена деления») либо дать подсказку в UI; альтернатива — писать кадры с порогом
−96 дБ (меняет данные, растёт вес `emo.json`).

### 2.9 Интерполяция кадров

**Совпало полностью:** `hopSec = H/fs`; `position = (t − t_sec[0])/hopSec`;
`index = clamp(⌊position⌋, 0, K−1)`; линейная интерполяция `from + (to−from)·frac`;
хвосты держатся (до первого — первый, после последнего — последний);
некорректное время — первый кадр; три параллельных ряда (лучи, угол, темп)
одной сеткой → фазы не расходятся; у темпа: `from = null → null`,
`to = null → from`.

**Расхождения:** нет. Единственный нюанс (qwen §15.6): `t_sec` — начало окна
без поправки на пол-окна («центр тяжести» кадра `t + hop/2`).

### 2.10 Аккорды и вращение звезды

**Совпало (все пять):** `chord_key_code` — regex `^([A-G])([#b]?)`, полутоны
`C=0…B=11` (+1 `#` / −1 `b`), `minor = («dim» в хвосте) или (хвост «m…», но не
«maj»)`, `key_code = (13 if minor else 1) + semitone` → 1…24; примеры
`C→1, Bb→11, B→12, Cm→13, Am→22, Dm6→15, Ebm6→16, Cdim→13, Gaug→8, G7→8,
Cmaj7→1, Csus4→1`; «N»/мусор — сегмент не создаётся (звезда держит прошлое
вращение); дедуп подряд идущих меток. Угол: `δ = π/42 ≈ 4.2857°` (1/12
сектора); мажор `φ = +(код−1)·δ` (против часовой); минор
`φ = −((9−tonic) mod 12)·δ`, `tonic = код−13` (Am = 0, Abm = −δ … Bbm = −11δ);
диапазон ±11δ ≈ ±47.14° меньше сектора → линейная интерполяция без
shortest-path. Таблицы углов ds §9.4 и qwen §12.2 совпадают покомпонентно.
Активный сегмент = последний с `t_sec ≤ t` (hold до следующего); доминанты —
**после** вращения.

**Расхождения (содержательная находка):**
* ds §9.3 и qwen §15.4 — **энгармонические крайности `Cb`/`B#`**: формула не
  нормализует `semitone` по модулю 12 → `Cb` даёт `key_code = 0`, `B#` минор —
  25, то есть **вне контракта** `AudioKeySegment.key_code (ge=1, le=24)` —
  qwen уточняет риск: валидация ответа падает **целиком** (один сегмент ломает
  весь `GET …/emo`). В живых выхлопах Chordino такие имена не встречались —
  потенциальный, но не подтверждённый дефект (ds); kimi/gml/mimo не заметили;
* qwen §15.6 — дрейф комментария: `keyRotation.ts` всё ещё описывает коды как
  «QM Key Detector», хотя со `schema_version` 6 их даёт Chordino (поведение
  верное, устарел текст).

**Предложения (qwen §15.4):** `semitone = ((semitone % 12) + 12) % 12` перед
сложением (`Cb → 1`, `B# → 1`, `Cbm → 13`) + отбрасывать в `parse_chord_csv`
коды вне 1…24 (локализация отказа до одного сегмента) + страж-тесты на три
имени; поправить комментарий `keyRotation.ts`.

### 2.11 Темп-коррекция

**Совпало (все пять, включая численные таблицы):** темп кадра — среднее оценок
`tempo_track` в `[t, t+hop)` (полуоткрытый интервал, курсор вперёд), hold до
следующей оценки, `null` до первой; ось `y = clamp(log2(bpm/120), −1, +1)`
(60/120/240 → −1/0/+1); «синус метки» `s = sin(π/2·y)`, `Kr = s² ∈ [0,1]`
(90 bpm → Kr ≈ 0.368, 150 → ≈ 0.235, 180 → ≈ 0.632 — таблицы ds §10.4 и qwen
§13.3 совпадают); половина круга по **знаку `s`** и углам вершин **после**
вращения: `s < 0` (bpm < 120) → квадранты 3–4 (`θ ∈ [π, 2π)`), `s > 0` →
квадранты 1–2; `r ← r·(1+Kr)`; **условная нормализация** — деление на max
только при `max > 100` (ds §10.5 — таблица примеров «все 70 → 100/50»);
без поворота верхняя половина = лучи **0, 1, 5, 6**, нижняя — **2, 3, 4**
(ds §10.4; подтверждено углами §3). Порядок «вращение → темп → доминанты»
зафиксирован у всех.

**Расхождения:** содержательных нет. Разные уровни детализации: ds —
пофреймовые примеры `frameTempos` (включая hold-таблицу); qwen — полный
псевдокод и чекбокс `tempoRays` (выкл → `bpm = null`, но метка темпа живёт);
gml — 180 bpm → ≈0.63 в опорных значениях; kimi — пример 100 bpm; mimo —
формулы и порядок.

**Предложения:** нет (механика признана согласованной всеми; связка
«квадрант зависит от аккорда» проговорена ds как инвариант: «ключ и темп
связаны»).

### 2.12 Геометрия звезды

**Эталон (код `starPolygon` = `segmentBoundaries() + rotation`; прогон
саммари):** вершины стоят **на границах секторов**:

```
θ_k = SEGMENT_START + k·SEGMENT_STEP = π/2 + π/7 + k·2π/7,  k = 0…6
θ, град: 115.714 / 167.143 / 218.571 / 270.000 / 321.429 / 12.857 / 64.286
```

(вершина 3 смотрит точно вниз; сектор между лучами 6 и 0 симметричен
вертикали). Радиус `r_k = R·clip(pct_k, 0, 100)/100`; SVG
`x = cx + r·cos θ`, `y = cy − r·sin θ`; сетка 25/50/75 % R; `sectorIndexOf`
для цвета сектора угла.

**Кто прав:** ds §11.1, qwen §14.1 (с таблицей положений), gml §12, kimi §B3 —
**верно** (границы секторов). **mimo §11 — неверно**: «вершина луча лежит в
центре своего сектора» и формула `θ_i = 3π/7 + i·2π/7` (и промежуточное

опровергнута (F11).

**Расхождения:** только указанная ошибка mimo. Совпадает у всех: поворот —
жёсткое вращение полигона (сетка/сектора неподвижны), квадранты для темпа
считаются по повёрнутым углам.

### 2.13 Доминанты и «Эмограмма»

**Совпало (все пять):** доминанта кадра — векторная сумма вершин **без**
деления на 7, зажим к `R` (формально длина до ~1.6 R); облако — доминанты
кадров **после** вращения и темп-коррекции; суммарная доминанта — **центроид**
облака (правка 08.10.2026: сырая сумма на тысячах кадров упиралась в обод);
«Эмограмма» — те же точки в полярных координатах: `radiusFrac = |D|/R`,
угол `atan2(−Y, X)`, шкала 14 эмоций «страх»…«агрессия» с шагом π/7 (2 эмоции
на сектор радара), кадры с нулевым радиус-вектором не рисуются.

**«Общая эмо-характеристика аудио-трека»** (24.10.2026, шаг 9 «ЕмоЛаб»,
`emoHistogram`): накопленные суммы векторов доминант по 14 категориям той же
шкалы. Категория угла — `i = clamp(⌊emoAngleFraction(θ)·14⌋, 0, 13)`
(сектор `[SEGMENT_START + i·π/7, +π/7)`); вклад кадра — `radiusFrac` (длина
`|D|`, сырые числа как в старом EmoLab — перенос «Динамический диапазон» на
суммы не влияет); кадры с `radiusFrac = 0` не участвуют. Порядок строк — по
шкале «Эмо», без сортировки.

**Расхождения/находки:**
* qwen §15.5: из-за луча 6 доминанта **систематически смещена** к `θ_6 + φ`,
  и межзаписное сравнение «куда указывает доминанта» частично отражает эту
  константу — критично для смыслового прочтения графика и для статьи;
* ds — семантика `null` vs `[]` в контракте (`null` — инструмент недоступен,
  `[]` — отработал, пусто; для UI эквивалентны) — единственный, кто раскрыл;
* gml/kimi/mimo — согласны, без дополнений.

## 5. Консенсус-инварианты (не трогать)

Формулы и поведение, подтверждённые **всеми** экспертизами, кодом и тестами —
их исправление не требуется:

1. сетка кадров (`K`, zero-pad, `t_sec`, 1 с / 2/3 с) и покрытие бинов
   1…32766 блоками ровно один раз;
2. свёртка 14 блоков в 7 счётчиков `C_k = S_{k+1} + S_{k+8}`;
3. дБ-шкала `20·log10(C/P)` с глобальным `P` и порогом −60 дБ → «дыхание»
   звезды;
4. порядок шагов UI: dB → диапазон → вращение → темп → нормализация → вершины →
   доминанты (квадрант — по углу после поворота);
5. правила `chord_key_code` (1…24, «N» без сегмента, дедуп) и углы
   `±n·δ`, δ = π/42;
6. темп: `y = clamp(log2(bpm/120), ±1)`, `Kr = sin²(π/2·y)`, выбор половины по
   знаку синуса, условная нормализация;
7. доминанты: сумма без деления, зажим к R, центроид для суммарной;
8. best-effort VAMP (`null` → нулевые коррекции) и hold-семантика карт;
9. контракт `emo.json` v6 (17 полей) и воспроизводимость (детерминированный
   JSON, кэш по sha256).

## 6. Базис для будущей статьи (публикации)

### 6.1 Ключевые тезисы

1. **Что есть алгоритм:** «Эмо-звезда» — двухэтапный вычислительный конвейер
   «спектральный профиль громкости → полярный полигон»: сервер считает
   логарифмический октавный профиль громкости (7 счётчиков на кадр), клиент —
   геометрию (вращение по аккорду, деформацию по темпу, доминанты). Математика
   параметризована частотой дискретизации — один код для трека и рендера.
2. **Честная рамка (обязательна в публикации):** «эмо» — номинальная
   семантика партитуры (14 меток «страх»…«агрессия» на шкале угла), а не
   психофизическая модель; лучи несут спектральную громкость, повёрнутую по
   аккорду и растянутую по темпу (формулировка kimi). Нельзя выдавать длину
   луча за «силу эмоции» без оговорки (F12).
3. **Сильные стороны метода** (qwen §15.1 + консенсус): единая математика на
   два раздела (нет дрейфа «две реализации»); глобальная дБ-шкала →
   сравнимость кадров во времени («дыхание» — реальная динамика);
   self-describing payload (`fft_size`, `db_floor`, `global_max` едут с
   данными); детерминизм и воспроизводимость (кэш по sha256, тесты-стражи
   формул).
4. **Известные ограничения — отдельный раздел «limitations»:** зеркало
   полного FFT и луч 6-интегратор (F1), веер ширины блоков (F2), поворот
   подписей «полоса → луч» (F3), порог −60 дБ и его необратимость (F5/F8),
   прямоугольное окно (F9). Это не слабость статьи, а её честность: поведение
   зафиксировано тестами и воспроизводимо.
5. **Варианты развития с количественной оценкой последствий:** A (только
   положительные частоты), B (нормировка на ширину), C (контракт + раскрытие
   смысла шкалы); каждый вариант — с оценкой влияния на контракт (`schema v7`,
   пересчёт кэшей) и на интерпретацию доминант.
6. **Методологическое приложение:** сама процедура «5 независимых разборов
   одного алгоритма + кросс-сверка с эталоном» — воспроизводимый способ
   верификации документации и находки скрытых дефектов (2 из 5 разборов не
   увидели зеркало — и именно кросс-сверка это выявила). Это самостоятельный
   сюжет для публикации о качестве ИИ-документации.

### 6.2 Рекомендуемая структура статьи

1. Постановка и область («ЕмоЛаб»/«Нейромузыка», связь с ЭЭГ-сессией).

## 10. Реализация: ФФТ v7 (22.10.2026)

Решения владельца метода по F1/F2/F9 внесены в код (`emo_radar.py`), контракт
`emo.json`/`AudioEmoOut` — **v7** (+`window` в паспорте кадров), кэши v6

  зеркало отрицательных частот.
* **F2 — вариант B (нормировка на ширину):** счётчик k = среднее двух
  блоковых средних `(M_{k+1} + M_{k+8})/2` — равный голос двух октав
  (объединённое среднее по бинам уронило бы обрезанный блок 14 против
  блоков-«гигантов»); счётчики стали сравнимы («веер ширины» убран).
* **F9 — окно Блекмена-Харриса** (4-членное, боковые лепестки ≈ −92 дБ)
  вместо прямоугольного (−13 дБ); интеграция — по амплитудам `|X_k|`
  (`rfft`), фаза не вычисляется и не используется (решение метода:
  амплитуда, а не мощность `|X|²`).
* **Замеры до/после:** синус на бине 400 — луч его счётчика = 100 %, остальные
  < 1e-6 пика (до v7 зеркало давало равные счётчики 0 и 6); `argmax` кадров
  белого шума: **6 → 2**; лучи синуса 100 Гц @48 кГц:
  `[55.9, 55.8, 56.9, 59.7, 70.8, 91.3, 100]` → `[−55.8, −57.0, −57.5, −57.2,
  −37.8, 100, −69.2]` — доминанта переехала с γ-high на γ (луч 5): бывший
  «луч 6» был завышен зеркалом.

  края окна BH гасят транзиенты у границ кадров (в обоих соседних кадрах
  событие попадает в зону ≈ −60…−92 дБ краёв окна); стационарный сигнал не
  затронут — когерентный выигрыш окна (~0.359) общий множитель и сокращается
  в `raw/global_max`. Лечится только сменой hop (ломает контракт «кадр =
  1 с») — не делаем; при жалобах на «мигание» ударов вернуться к вопросу.

## 12. Поправка v9 (23.10.2026): двухзаходная схема счётчиков (сверка со старым EmoLab)

Владелец разобрал счётчики бинов ФФТ в старом EmoLab (проект `~/emolab`
собран и запускается, Essentia+GPU / TensorFlow GPU починены) и зафиксировал
истинную схему сборки (уточнение: «нулевой счётчик» в первом описании — это
**первый счётчик** = индекс 0, тот, что получает `fft[0]`):

* сборка идёт **от нулевого DC-бина**: в первом счётчике — одно значение
  `fft[0]`; далее по счётчикам следующие **2, 4, 8, 16, 32, 64** бинов;
* после наполнения всех 7 счётчиков — **возврат к первому счётчику** и
  дополнение суммой следующих **128, 256, 512, 1024, 2048, 4096, 8192**
  бинов (всё по Найквисту);
* из спектра берётся **только амплитуда** (`|X_k|`); никаких средних
  «сумма / число бинов» **нет** — за счёт естественной убыли амплитуд
  (лог-закон спектра) суммарные доли счётчиков автоматически соизмеримы:
  например, счётчик 7 у владельца (= индекс 6) = 64 бина низких частот +
  8192 бина самых высоких;
* получается **7 накопительных значений из 14 диапазонов за 2 захода**;
  итоги нормируются по **макс. сумме** → 0…1 = радиус радара (`peak_rays`,
  проценты = ×100); дальше — без изменений: начальный полигон звезды,
  коррекция вращения по аккордам, темпа по квадрантам лучей, доминанты и
  окончательное нормирование границы радара.

**Реализация (код v9, `emo_radar.counter_blocks`):** блоки идут сплошняком
от бина 0 ширинами `2^0…2^13` (1, 2, 4 … 8192), блок 13 добирает хвост до
Найквиста (8191–16384 = 8194 бина — покрытие 0…16384 ровно по одному разу);
счётчик k = блок k + блок k+7. Контракт `EMO_SCHEMA_VERSION = 9` (кадры v8
отвергаются `parse_emo` → пересчёт «ЕмоЛаб» / добивка из `master.wav` у
рендера). Средние (вариант B) и дБ-шкала остаются отменёнными (§11).

**Честное замечание о сверке с исходником.** Буквальный код
`calcBrainWaves` (`~/emolab/libs/emolib.py`) даёт ширины блоков `1,1,2,4,…,4096`
(сумма 8192 бина — половина спектра essentia `Spectrum`), а схема владельца —
`1,2,4,…,8192` (полный спектр до Найквиста). Разница — сдвиг на один блок
(дубль ширины 1 в исходнике). Реализована **схема владельца** («Попробуй
сделать так»): она самосогласована (примеры «7-й счётчик = 64 + 8192»,
«1-й = бин 0 + 128» сходятся) и доводит сборку до Найквиста. При расхождении
на реальном треке (Suzi Quatro: квадрант доминанты, гистограмма) — первым
кандидатом на сверку остаётся буквальная пара `bw_frame14[i] + bw_frame14[i+7]`
старого кода.

## 13. Поправка v10 (23.10.2026): энергетические суммы + октавные границы блоков

опрокидывается в 4 квадрант — ей мало веса 1-го счётчика», общая оценка

|---|---|
| магнитудные `Σ\|Z\|` (v9) | 0.13, 0.18, 0.25, 0.36, 0.50, 0.71, 1.00 — веер **8×** |
| энергетические `sqrt(Σ\|Z\|²)` (v10) | ≈0.9 … 1.0 — **ровные** |

Магнитудные суммы по блокам с разбросом числа бинов 2:8193 структурно
раздувают верхние счётчики (лучи β/γ сидят у 270°/321° — 4-й квадрант), а
счётчик 0 гасят — звезда и падает в 4-й квадрант. Формула консультации
(Gemini, `спектр-октавы.pdf`): энергия полосы `M_band = sqrt(Σ|Z[k]|²)` —
мощности независимых компонент **аддитивны**, магнитуды — нет.

**Реализация (код v10, `emo_radar.counter_blocks`/`counter_sums`):**

* блоки — **ровные октавные диапазоны** от DC-бина, границы на степенях
  двойки: блок 0 — бины 0–1 («0–2 Гц», `fft[0]` + бин 1), блок 1 — 2–3,
  блок 2 — 4–7, …, блок 12 — 4096–8191, блок 13 — 8192–16384 (8193 =
  8192 + Найквист-добор; покрытие 0…16384 ровно по одному разу);
* счётчик k = блок k + блок k+7, суммирование **квадратов** амплитуд обоих
  блоков, **корень один на счётчик** (мощности аддитивны); без средних;
* гипотеза владельца «2, 2, 4, 8, …» реализована как раз шинами блока 0
  (0–2 Гц вместо 1–2 Гц — DC усиливает первый счётчик);
* `peak_linear`/нормировка 0..1 — без изменений; `EMO_SCHEMA_VERSION = 10`
  (кадры v9 отвергаются `parse_emo` → пересчёт «ЕмоЛаб» / добивка из
  `master.wav` у рендера).

**Контрольный прогон на реальных треках** (первые 3 минуты 8 mp3 из
`~/emolab/audio`, квадрант доминанты по формуле `dominantPoint` UI без
поворота/темпа; доля кадров по квадрантам 1/2/3/4 и число «переворотов»
квадранты между кадрами):

| Схема | кв.1 | кв.2 | кв.3 | кв.4 | перевороты (средн.) |
|---|---|---|---|---|---|
| v9 магнитудные суммы | 28 % | 18 % | 9 % | **46 %** | ~81/кадр |
| v10 энергетические | **39 %** | **39 %** | 13 % | **8 %** | ~74/кадр |

«Опрокидывание в 4-й квадрант» исчезло: доля кв.4 упала с 46 % до 8 %, масса
перетекла в квадранты 1–2 (низкие счётчики δ…θ наконец получили вес). По
отдельным трекам квадрант-1 лидер (Stagger Lee 90 %, Zappa 73 %, 1pg 94 %),
у мрачных/тяжёлых треков квадрант-2 (Henry Lee 70 %, Mouse's Night 46 %) —
адекватная дифференциация взамен тотального 4-го. Число переворотов между
кадрами снизилось умеренно (динамика остаётся живой — это её природа).

**Честные замечания.**

* Схема ширин «2, 2, 4, …» против «1, 2, 4, …» сама по себе влияет слабо
  (на уровне сотых долей) — эффект даёт переход на энергию. Схема принята
  как более чистая (октавные границы 0–2, 2–4, 4–8 … бинов).
* Консультация Gemini предлагает для октавных спектров и CWT/синхросжатие
  (ssqueezepy, pywt) — это **отдельная волна** (новые зависимости, только с
  решения владельца); для ЭЭГ-спектра октавные вейвлеты интересны тем более
  (дельта 0.5–4 Гц требует децимации/больших окон — в N=32768 полоса 1–2 Гц
  это 0 бинов по Gemini).
* Кандидат на сверку при следующих расхождениях: буквальная пара
  `bw_frame14[i] + bw_frame14[i+7]` старого кода (§12) и вопрос «суммировать
  ли мощности блоков до корня вместе или по отдельности» (реализовано
  вместе — корень один на счётчик).

## 14. Волна 3 (23.10.2026): конечная дБ-оптимизация и два закона вращения

Постановка владельца 23.10.2026. Реализация — `frontend/src/app/sections/neuromusic/radialDbRange.ts`,
`keyCircle.ts`, `keyRotation.ts`, `emolab/CircleOfFifths.tsx`.

### 14.1 Конечная дБ-оптимизация радиусов (`radialDbRange`)

Радиальные значения векторов вершин и доминанты переводятся в дБ-окно
**после** расчёта звезды (порядок: лучи → вращение → темп → вершины →
доминанта → перенос):

```
db    = 20·log10(v/100)          (v — % радиуса, линейная шкала по пику)
frac₂ = clip((db − floor)/(0 − floor), 0, 1),  frac ≤ 0 → 0
```

`floor ∈ {−40, −60}` (селектор «Динамический диапазон», дефолт −60 дБ).
Направление вектора сохраняется → **углы доминант — инвариант**, ступени
«Динамики Эмо» не меняются; высоты столбиков «Экспрессии Эмо» —
лог-шкала громкости (естественнее). Доминанта считается из исходных вершин,
затем переносится её радиус; облако — точки доминант с перенесёнными
радиусами; суммарная — центроид перенесённого облака.

### 14.2 Гармонический закон вращения (`keyCircle` + `keyRotation`)

Хроматический (дефолт, без изменений): `φ = ±N·δ`, N — полутоны от
C мажор / A минор, δ = π/42 (1/12 сектора). Гармонический: позиция аккорда
в квинтово-квартовом круге:

```
P = (7·(semitone + (минор ? 3 : 0))) mod 12      (квинтовый ход по часовой)
φ = ±P·δ     (мажор +, минор − — как в хроматике)
```

Смещение — **в пределах одного сектора** (1/7 круга), максимум ±11δ ≈
±47.14° < сектор → линейная интерполяция кадров остаётся корректной.
Минор стоит на позиции параллельного мажора (Am ↔ C, Em ↔ G, … Dm ↔ F).

### 14.3 Квинтово-квартовый круг (`CircleOfFifths`)

Внешнее кольцо — 12 мажоров (C, G, D, A, E, B, F#, Db, Ab, Eb, Bb, F),
внутреннее — 12 миноров (Am … Dm), края — подписи альтераций (0, 1♯ … 1♭),
центр — активная тональность. Подсветки (легенда образца): тоника,
суб/доминанта (`P±1`), параллельная (та же позиция другого кольца),
одноимённая (та же тоника другого лада). Диаметр круга = диаметр звезды
(R = 90); круг — только таб «Звезда» секции «ЕмоЛаб».
