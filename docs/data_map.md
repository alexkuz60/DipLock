# Карта данных DipLock: операции, артефакты, носители

> Составлена 17.09.2026 по коду (не по памяти): каждый факт — из чтения сервисов, замеров на живой
> машине или листинга каталогов. Правило ведения — `docs/rules/docs.md` п.3: **новый кэш, файл,
> таблица или клиентское хранилище = строка здесь**, в том же срезе работы.
>
> Как читать: три слоя — «операция → объект данных → носитель». Колонки таблиц:
> `Шаг | Вход | Артефакт | Носитель | Ключ | Жизненный цикл | Факт | Есть/Хотим`.
> «Есть/Хотим» — что уже измерено/реализовано (`есть`) и что должно появиться (`хотим`),
> чтобы карта не превращалась в список пожеланий.

**С 17.09.2026 (этап 2, A3)** все дисковые кэши читаются и пишутся через один модуль —
`services/cache_store.py` (`cache_path` / `cache_read` / `cache_write` / `cache_clear`). Шесть копий
«временный файл + `os.replace`» (`surface_cache`, `recording_signals`, `spectral`, `spectrogram`,
`mri_slices`, `atlas_contours`) сведены к одной функции, очистка кэшей — к одному `cache_clear`.
Исключение осознанное: сайдкар записи (`recordings.write_sidecar`) — не кэш, а носитель дедупа,
у него своя семантика отказа.

## 8. Фоновые задачи и их результаты

| Шаг | Вход | Артефакт | Носитель | Ключ | Жизненный цикл | Факт | Есть/Хотим |
|---|---|---|---|---|---|---|---|
| Постановка задачи | `POST …/{kind}` (`kind` = `analyze`, `preprocess`, `spectrum`, `dipoles`, `spectrogram`) | `JobCreated` (202 + `job_id` + `result_url`) | RAM, реестр задач | `job_id` (uuid) | до вытеснения из истории (50) | одновременно считаются `MAX_CONCURRENT_JOBS` = 2 задачи (семафор) — остальные ждут в очереди | есть |

## 9. Журнал шагов: пошаговые замеры (этап 5)

Сейчас время измеряется в **несвязанных** местах: `duration_sec_calc` внутри расчётов, `Job.elapsed_sec`
(длительность всей задачи), `duration_sec` в ответе `/analyze`. Пошаговых длительностей нет, поэтому
вопрос «почему 8 секунд» приходится выяснять повторным запуском с логами.

**Формат строки журнала** (согласован 17.09.2026, реализация — этап 5; строки складываются в
`data/cache/journal.jsonl` или пишутся в лог-файл, решение по хранению — на реализации):

```
ts | job_id | pipeline | step | params_key | bytes_in | bytes_out | ms | cache_hit | epochs | note
```

| Поле | Что пишем | Источник |
|---|---|---|
| `ts` | ISO-8601 с миллисекундами | момент завершения шага |
| `job_id` | id задачи или `-` (синхронный вызов) | `job_manager` |
| `pipeline` | `analyze` / `preprocess-filter` / `preprocess-artifacts` / `preprocess-epochs` / `spectrum` / `spectrogram` / `dipoles` / `signals` / `asset-surface` … | сервис |
| `step` | имя шага внутри пайплайна: `load_edf`, `montage`, `reference`, `filter`, `notch`, `epochs`, `psd`, `stft`, `grid_scan`, `head_to_mni`, `structure_at`, `encode_png`, `cache_write` … | сервис |
| `params_key` | сигнатура, по которой кэшируется результат (`spectrum_signature`, ETag уровня и т.д.) или `-` | сервис |
| `bytes_in` / `bytes_out` | объём входа/выхода шага, если он материален (файл, контейнер, сетка) | код шага |
| `ms` | длительность шага | `time.perf_counter()` вокруг шага |
| `cache_hit` | `true` / `false` / `-` (шаг не кэшируется) | код шага |
| `epochs` | число эпох, к которым относится шаг (если применимо) | код шага |
| `note` | короткая причина/контекст: `level=4`, `grid=7mm`, `band=8-13`, `reason=cold` | код шага |

Правила: строка на **шаг**, а не на запрос; измерения обязаны быть в продакшен-пути (один
`perf_counter` — не стоит ничего); «числа о времени» в документации берём **только из журнала**,
чтобы через полгода отличать «7 мм — 2.2 с на `test.edf` 17.09.2026» от «кажется, быстро»
(`docs/rules/docs.md` п.6).

## 10. Открытые вопросы (что карта выявила)

1. **Сироты кэша.** `_drop_signal_cache` срабатывает только вместе с вытеснением записи, а вытеснение —
   при обращении к реестру (`_drop_expired` в `get`/`list`). Каталог кэша, чьей записи в реестре уже
   нет (или никогда не было), не удаляется ничем. Факт на 17.09.2026: `data/cache/spectrograms/edf/`
   — 2 файла (84 и 88 КБ, mtime 07:39), записи `edf` в реестре нет (реестр знает только uuid-каталоги
   из `data/edf/`). Нужен обход кэшей «по каталогам против реестра» (место — `prune_orphans`
   или отдельный скрипт рядом с `backend/scripts/dedupe_recordings.py`).
2. ~~**Нет кэша подготовленного сигнала.**~~ **Закрыто 17.09.2026 (этап 2, A4):** кэш есть —
   `services/prepared_signal.py`, ключ «запись + единицы + каналы + референс + полоса + notch»,
   инвалидация при вытеснении записи, замеры и следствия — §3 (строки «Чтение EDF», «Кэш
   подготовленного сигнала»). Факт закрытия — `docs/history.md`.
3. ~~**Пять ручных копий ETag/304** в `routes.py`~~ **Закрыто 17.09.2026 (этап 3, A2):** все восемь
   мест отдачи ассетов (signals, топокарта, сетка спектрограммы, срез МРТ, контуры, `/surface`,
   `/surface/brodmann`, `/brain-surface`) идут через `app/api/assets.py` (`asset_response`).
   Сравнение `If-None-Match` стало по списку тегов, а не подстрокой (было: `"v1"` совпадал в
   `"v10"`); ручных `status_code=304` вне `assets.py` не осталось — это проверяет
   `backend/tests/test_api_assets.py`. Факт — `docs/history.md`.
4. **Три несвязанных версии ассетов** (`surface_version`, `MRI_GRID_VERSION`, `CONTOUR_VERSION`) плюс
   две «версии результата» (`topomap_version`, `grid_version`) — пять идентификаторов, каждый
   со своим способом подъёма. Изменение общего источника (путь `subjects_dir`, версия MNE) может
   не изменить ни одну из них — стоит проверить, что в отпечатки входит всё, от чего зависит ассет.
5. **БД отражает только `sessions`** (`epochs`/`dipoles` пусты, F21), а результаты задач живут в RAM.
   Пока это осознано (локальная разработка), но любой «список исследований» потребует сохранения —
   решение принять до Фазы 4/5, а не после.
6. **`data/results/` пуст, `backend/diplock.db` весит 24 КБ и лежит в рабочем каталоге** — наследие
   локальных прогонов; в репозиторий не коммитится (`.gitignore`), но при смене `UPLOAD_DIR`/`DATA_DIR`
   легко забыть про существующие файлы.
7. **Кэш сигналов есть только у одной из трёх записей** (`data/cache/signals/` — один каталог):
   уровни строятся лениво, поэтому это не поломка, а признак того, что кэш полностью «по требованию» —
   при аудите кэшей нельзя считать «нет каталога» ошибкой.
