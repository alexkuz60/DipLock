# Карта данных DipLock: операции, артефакты, носители

> Составлена 17.09.2026 по коду (не по памяти): каждый факт — из чтения сервисов, замеров на живой
> машине или листинга каталогов. Правило ведения — `docs/rules/docs.md` п.3: **новый кэш, файл,
> таблица или клиентское хранилище = строка здесь**, в том же срезе работы.
>
> Как читать: три слоя — «операция → объект данных → носитель». Колонки таблиц:
> `Шаг | Вход | Артефакт | Носитель | Ключ | Жизненный цикл | Факт | Есть/Хотим`.
> «Есть/Хотим» — что уже измерено/реализовано (`есть`) и что должно появиться (`хотим`),
> чтобы карта не превращалась в список пожеланий.

**С 17.09.2026 (этап 2, A3)** все дисковые кэши читаются и пишутся через один модуль —
`services/cache_store.py` (`cache_path` / `cache_read` / `cache_write` / `cache_clear`). Шесть копий
«временный файл + `os.replace`» (`surface_cache`, `recording_signals`, `spectral`, `spectrogram`,
`mri_slices`, `atlas_contours`) сведены к одной функции, очистка кэшей — к одному `cache_clear`.
Исключение осознанное: сайдкар записи (`recordings.write_sidecar`) — не кэш, а носитель дедупа,
у него своя семантика отказа.

## 6. Диполи: быстрый расчёт и точный фитинг

| Шаг | Вход | Артефакт | Носитель | Ключ | Жизненный цикл | Факт | Есть/Хотим |

## 9. Журнал шагов: пошаговые замеры (этап 5, реализован 17.09.2026)

До этапа 5 время измерялось в **несвязанных** местах: `duration_sec_calc` внутри расчётов, `Job.elapsed_sec`
(длительность всей задачи), `duration_sec` в ответе `/analyze`. Пошаговых длительностей не было, поэтому
вопрос «почему 8 секунд» приходилось выяснять повторным запуском с логами. Теперь замер один:
`services/journal.py` — `step()` (контекст-менеджер: `perf_counter` на входе/выходе, пишет строку и при
исключении — с `error=…` в `note`) и `record()` (когда шаг уже измерен вызывающим: ступень или **сумма по
циклу**). Строка на **шаг**, а не на запрос: `duration_sec_calc` в ответе остаётся частью контракта UI,
но «почему» решается по журналу.

**Носитель.** `data/cache/journal.jsonl` (рядом с кэшами, путь — `journal_path()`), читается
`GET /api/v1/journal?limit&pipeline`. Файл дописывается под локом (шаги идут из нескольких потоков
job-очереди), перед записью сверяется `JOURNAL_MAX_BYTES` (5 МБ): полное поколение уезжает в
`journal.jsonl.1` — на диске не больше двух файлов, чтение ограничено «хвостом» (1 МБ).
`JOURNAL_ENABLED=false` выключает запись целиком. Журнал **не** ломает расчёт: сбой записи логируется и
гасится (как в `cache_store`).

**Формат строки** (в файле — JSON-объект на строку):

```
ts | job_id | pipeline | step | params_key | bytes_in | bytes_out | ms | cache_hit | epochs | note
```

| Поле | Что пишем | Источник |
|---|---|---|
| `ts` | ISO-8601 с миллисекундами | момент завершения шага |
| `job_id` | id задачи; в файле `-` (синхронный вызов), в ответе `GET /journal` → `null` | `job_manager` (`job_scope`) |
| `pipeline` | `analyze` / `preprocess-filter` / `preprocess-artifacts` / `preprocess-epochs` / `spectrum` / `spectrogram` / `dipoles` / `signals` / `asset-surface` / `asset-mri` / `asset-contours` | сервис |
| `step` | имя шага внутри пайплайна: `load_edf`, `montage`, `reference`, `filter`, `notch`, `epochs`, `psd`, `stft`, `grid_scan`, `head_to_mni`, `structure_at`, `encode_png`, `cache_write` … | сервис |
| `params_key` | сигнатура, по которой кэшируется результат (`spectrum_signature`, ETag уровня и т.д.) или `-` | сервис |
| `bytes_in` / `bytes_out` | объём входа/выхода шага, если он материален (файл, контейнер, сетка) | код шага |
| `ms` | длительность шага | `time.perf_counter()` вокруг шага |
| `cache_hit` | `true` / `false` / `-` (шаг не кэшируется) | код шага |
| `epochs` | число эпох, к которым относится шаг (если применимо) | код шага |
| `note` | короткая причина/контекст: `level=4`, `grid=7mm`, `band=8-13`, `reason=cold` | код шага |

Правила: строка на **шаг**, а не на запрос; измерения обязаны быть в продакшен-пути (один
`perf_counter` — не стоит ничего); «числа о времени» в документации берём **только из журнала**,
чтобы через полгода отличать «7 мм — 2.2 с на `test.edf` 17.09.2026» от «кажется, быстро»
(`docs/rules/docs.md` п.6).

Реализация:

- **`job_id` не передаётся в сервисы руками.** Его кладёт `job_manager.job_scope` (ContextVar) вокруг
  `asyncio.to_thread` — контекст доезжает до потока задачи, потому что `to_thread` его копирует;
  синхронный вызов пишет `-`.
- **`params_key` — та же сигнатура, по которой кэшируется результат** (`spectrum_signature`, ключ
  подготовленного сигнала `PreparedKey.signature()`, ETag уровня сигналов, версия ассета): иначе замер
  нельзя сопоставить с записью в кэше и понять, за что заплачено.
- **Шаги по пайплайнам:** `signals` (`cache_read` / `build_level`), `preprocess-{filter|artifacts|epochs}`
  (+ `load_edf` из кэша подготовленного сигнала), `spectrum` (`load_edf` / `segment_epochs` / `psd` /
  `topomaps` / `topomap_read`), `spectrogram` (`load_edf` / `stft` / `grid_write` / `grid_read`),
  `dipoles` (`load_edf` / `segment_epochs` / `grid_scan` / `head_to_mni`), `analyze` (стадии legacy-пайплайна),
  `asset-{surface|mri|contours}` (`cache_read` / `build`).
- **Цикл = одна строка.** На `test.edf` это 261 эпоха: строка на эпоху засорила бы журнал. Пишется
  остаток «перебор сетки» (цикл минус локализация и чтение структуры атласа) и `head_to_mni` — сумма
  `head_to_mni` + структуры по точкам. Обе строки рядом, поэтому видно и «где время», и «сколько точек».
- **UI журнал не читает** — это диагностика для разработчика (curl/скрипт), раздел «Состояние сервера»
  дорожной карты не затронут.
- **Первое обращение к ассету видно в том же журнале:** сборка объёмов атласа (≈1 с) попадает в шаг
  `asset-contours build`, а не «растворяется» в задаче, из-за которой она случилась.

**Аналитический слой — план (решение владельца 17.09.2026).** Журнал — источник, но не средство
запросов: чтобы ответить «сколько всего шло на `psd` за неделю», нужен SQL. Проекция будет
**отдельным файлом `data/analytics.db`** (SQLite), наполняемым из `journal.jsonl` (или тем же
`journal.step`), а **не** таблицами в `backend/diplock.db`: основная БД остаётся транзакционной
(там `sessions`/`epochs`/`dipoles` анализа), а текстовые логи — на `logging` (обязаны работать до
старта БД и при её падении). Схема — только вместе с alembic/CI (Фаза 6), чтобы её можно было
версионировать; задача — `todo.md` §4.

**Первые замеры из журнала** (17.09.2026, `data/edf/test.edf`: 130.7 с × 500 Гц × 18 кан., три задачи
подряд на свежем `data/cache`, пауза между задачами — время на подготовку к следующей):

| Задача | Шаги, мс | Что видно |
|---|---|---|
| `spectrogram` (канал F3, окно 500 мс, без полосового) | `load_edf` 93 → `stft` 3.5 (сетка 21×1051) → `grid_write` 0.2 (88 КБ `DPS2`) | холодное чтение EDF дороже самого STFT в 25 раз: повтор с теми же параметрами платит только за STFT |
| `spectrum` (эпоха 500 мс, 261 эпоха) | `load_edf` **2.2** (кэш-попадание) → `segment_epochs` 30 → `psd` 486 → `topomaps` 29 (5 карт, 38 КБ) | подготовка сигнала из RAM — 0.4 % задачи: платит Welch, а не чтение файла |

«сетка спектрограммы 0.09–0.76 с» — `audit-2026-09.md` §1).

Три вопроса жизненного цикла данных, которые выявила эта карта, закрыты одним срезом:

| Вопрос | Решение | Носитель и код | Тесты |
|---|---|---|---|
| **A6:** кэши и каталоги исчезнувших записей не убирал никто (только скрипт и тесты) | обход сирот: каталоги загрузок по TTL + кэши `signals`/`spectra`/`spectrograms` + файлы задач исчезнувших записей | `services/orphans.py` (`sweep_orphans`), вызов из lifespan `main.py` и из `dedupe_recordings.py --prune` | `tests/test_orphans.py` (7) |
| **A7:** пять несвязанных версий ассетов и расчёта | входы ассетов объявлены в одном месте, отпечаток — одна функция `fingerprint(kind, subjects_dir)` | `services/asset_versions.py`; вызовы в `surface_cache` / `mri_slices` / `atlas_contours` | `tests/test_asset_versions.py` (8) |
| **A8:** результат задачи жил только в RAM | файл задачи `results_dir/jobs/<job_id>.json` + `JobManager.restore` при старте | `services/job_store.py`, `job_manager.py`; настройки `JOB_STORE_ENABLED` / `JOB_RESULT_MAX_BYTES` | `tests/test_job_store.py` (8) |

Что важно не перепутать при следующем рефакторинге:

- **Файл задачи — не кэш.** Он не участвует в `cache_clear`/ETag и не «пересчитывается при промахе»,
  ключа у него нет (имя файла = `job_id`). Единственное общее с кэшами — атомарная запись
  `cache_store.cache_write` (одна копия «временный файл + `os.replace`» в проекте).
- **Сирота — это «нет ни в реестре, ни на диске».** Каталог загрузки без валидного сайдкара реестр не
  восстанавливает (легаси), но кэш и файл задачи такой записи не сносятся: запись ещё лежит на диске.
- **Обход не трогает ассеты и журнал.** `surface`/`mri`/`contours` живут по версии, `journal.jsonl` —
  диагностика; в обходе участвуют только три каталога кэшей записей, каталоги загрузок и `results/jobs`.
- **Расписания нет.** Обход — один проход при старте приложения (листинг нескольких каталогов); для уже
  запущенного процесса есть `backend/scripts/dedupe_recordings.py --prune`.

**Живой прогон** (17.09.2026, реальные `data/`): первым проходом удалена сирота аудита — каталог
`edf/` в `data/cache/spectrograms/` (2 файла, 169 КБ), остальные каталоги кэшей — живы; синтетическая сирота
