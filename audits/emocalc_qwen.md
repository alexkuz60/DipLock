> Независимый разбор по коду (22.10.2026). Источники — модули backend/frontend и

## 1. Резюме

«Эмо-звезда» — 7-лучевой радар-полигон. Сервер считает **только данные кадров**
(7 чисел на кадр в процентах радиуса) плюс две вспомогательные карты (аккорды и
темп); вся геометрия (вершины, вращение, темп-коррекция, доминанты) считается на
клиенте. Граница ответственности проходит по контракту `AudioEmoOut`
(`emo.json` / `GET …/emo`).

Конвейер целиком (→ — передача данных, номера — разделы этого документа):

```
  [рендер «Нейромузыки»]                     [«ЕмоЛаб»: внешний wav/mp3]
  стемы полос ×2^p → master (Σ)              probe → блоковый декод float64
  → apply_peak_ceiling(0.891)                → [:, :2] → (L+R)/2
  → моно (L+R)/2 @48000 Гц  (кадр 2/3 с)     → resample_poly → 32000 Гц (кадр 1 с)
        │                                          │            §4 (шаг 0)
        └──────────────┬───────────────────────────┘
                       ▼
  окна FFT 32768, сдвиг 32000, zero-pad хвоста            §5 (шаг 1)
                       ▼
  X = fft(окно), mag = |X_k|, окно прямоугольное          §6 (шаг 2)
                       ▼
  14 октавных блоков бинов: (2^b − 1, 2^b), b = 1…14       §7 (шаг 3)
                       ▼
  7 счётчиков: S_k = блок(k+1) + блок(k+8)                 §8 (шаг 4)
                       ▼
  peak = max S (глобально), db = 20·log10(S/peak),
  pct = 100·(db + 60)/60, зажим 0…100                      §9 (шаг 5)
                       ▼
  payload: frames[{t_sec, rays[7]}] + key_track + tempo_track + segment_track   §16
                       ▼  (клиент)
  перенос дБ-окна (dbRangeDb)                              §10 (шаг 6)
  → выбор кадра + линейная интерполяция лучей              §11 (шаг 7)
  → вращение по аккордам (δ = π/42)                        §12 (шаг 8)
  → темп-коррекция радиусов (Kr = sin²) + нормализация      §13 (шаг 9)
  → вершины starPolygon → dominantPoint                    §14 (шаг 10)
  → dominantCloud → totalDominant (центроид)               §14
```

## 4. Шаг 0. Подготовка данных

Расчёт всегда идёт по **моно-сигналу float64**. Два входа дают разную частоту и,
как следствие, разную длительность кадра — математика кадров параметризована
`fs`, поэтому одна функция обслуживает оба раздела.

### 4.1. Путь A — рендер «Нейромузыки» (48000 Гц, кадр 2/3 с)

Порядок зафиксирован в `render.py::_run_render`:

1. Полосовые стемы: ЭЭГ-полоса (500 Гц) → `mono = w @ eeg` → `hilbert` →
   ресемпл ×96 по Re/Im → питч-шифт ×2^p (`p = octave_shift` ∈ {5, 6, 7},
   дефолт 7 → ×128) → стерео 48000 Гц (`audio_render/core.py::band_stem`).
2. Нормировка громкости трека/группы (`normalize_track`, `normalize_group`).
3. Мастер: `master = Σ normalized` (float64, без компрессии).
4. **Контроль пика** (`mix.py::apply_peak_ceiling`):

   ```
   peak = max(|master|)
   if peak > 0.891 и peak ≠ 0:  master ← master · (0.891 / peak)
   ```

   Комментарий: 0.891 = 10^(−1/20) — запас −1 dBFS под PCM_24; масштабирование
   только **вниз** (тихий мастер не усиливается).
5. Моно-слияние (`emo_radar.py::frames_from_master`):

   ```
   mono[i] = (L[i] + R[i]) / 2      (arr.mean(axis=1); при 1D — ravel)
   ```

   Комментарий: кадры считаются **из того же массива в памяти**, байты которого
   уходят в `master.wav` и в источник `master` плеера, — анимация синхронна с
   воспроизведением без поправок, временный моно-файл не создаётся. Эффекты
   3D-цепочки применяются позже и в расчёте не участвуют («чистый микс до
   эффектов»).

### 4.2. Путь B — «ЕмоЛаб»: внешний wav/mp3 (32000 Гц, кадр ровно 1 с)

Порядок зафиксирован в `track_input.py::decode_track` и
`track_analysis.py::_run_analysis`:

1. `probe(blob)` — только заголовок (`sf.info`): `fs_source`, `channels`,
   `duration_s = frames / fs_source`. Отказ (400) если файл пуст, не аудио,
   `frames ≤ 0` либо `duration_s > 1800 с`.
2. Блоковое чтение `sf.SoundFile.read(frames=2^20, dtype="float64", always_2d=True)`
   с накоплением; повторный контроль длины (защита памяти: 200 МБ mp3 мог бы
   развернуться в гигабайты float64).
3. `data = concat(blocks)[:, :2]` — у многоканальных (5.1 и пр.) берутся первые
   два канала.
4. `mono = data.mean(axis=1)` = `(L+R)/2`; у моно-исходника — та же дорожка.
5. Контроль конечности `np.isfinite(mono).all()` — иначе «Отсчёты содержат
   NaN/inf» (400, а не 500).
6. Ресемпл в `ANALYSIS_FS = 32000`:

   ```
   g = gcd(fs_source, 32000)
   mono ← resample_poly(mono, 32000/g, fs_source/g)
   ```

   Комментарий: НОД-сокращение даёт точный рациональный коэффициент (44100 →
   320/441). `fs_source` сохраняется в паспорте трека — нужен для сравнения с
   ЭЭГ-сессией. Именно 32000 Гц делает кадр звезды **ровно 1 с**
   (32000/32000), а не 2/3 с как у рендера.
7. `wav_bytes(audio)` — WAV PCM_16 @32000 **моно** в памяти: вход VAMP (Sonic
   Annotator читает только файлы).
8. Карты VAMP и кадры — порядок шагов конвейера (процент — статус поллинга):

   | № | Шаг | pct | Функция |
   |---|---|---|---|
   | 1 | Декодирование аудио | 0.05 | `decode_track` + `wav_bytes` |
   | 2 | Карта аккордов (Chordino, трансформ 32k) | 0.25 | `key_track_from_wav` |
   | 3 | Карта темпа (VAMP) | 0.45 | `tempo_track_from_wav` |
   | 4 | Сегментер (VAMP) | 0.55 | `segment_track_from_wav` |
   | 5 | ФФТ-кадры «Эмо» | 0.65 | `emo_frames(audio.data, fs=32000, …)` |
   | 6 | Сохранение кэша | 0.90 | `store.write_track_files` + манифест |

   Комментарий: карты VAMP считаются **до** кадров и передаются в `emo_frames`
   готовыми — payload собирается один раз. Тяжёлые шаги синхронны и идут в
   фоновом потоке (`MAX_PARALLEL = 2`), event loop не блокируется.

### 4.3. Путь C — ленивая добивка старых рендеров

`render.py::emo_payload_of`: `emo.json` → `parse_emo` (версия ≠ 6 → `None`) →
чтение `master.wav` в память (`soundfile`, без временных файлов) →
`frames_from_wav` + карты VAMP → дозапись `emo.json` и `files` манифеста.
Комментарий: `RENDER_FORMAT_VERSION` не поднимается — байты аудио не меняются,
меняется только производный артефакт.

### 4.4. Идентичность и кэш

`track_id = hashlib.sha256(blob).hexdigest()[: store.TRACK_ID_LEN]`
(`TRACK_ID_LEN = 32` — 128 бит, как `SIG_LEN` рендера; `emolab/store.py`):
повторное открытие того же файла не пересчитывается. Устаревший кэш (`emo.json`
не текущей версии контракта) — промах → честный пересчёт. In-memory статус живёт
`TRACK_STATE_TTL_SEC = 15 мин` (параллельных анализов — `MAX_PARALLEL = 2`),
дальше состояние восстанавливается из манифеста диска.

## 5. Шаг 1. Сетка окон (кадры)

`emo_radar.py::frame_starts(N)`:

```
if N ≤ 0:            K = 0            (пустой сигнал → нет кадров)
elif N ≤ 32768:      K = 1, start₀ = 0
else:                last = ⌈(N − 32768) / 32000⌉
                     K = last + 1
                     start_k = k · 32000,  k = 0…K−1
```

Время кадра и его отрезок:

```
t_k = start_k / fs                       (округление до 6 знаков в payload)
кадр k покрывает [k·h, (k+1)·h) секунд    (h/fs = 2/3 с @48 кГц, 1 с @32 кГц)
```

Окно кадра и добивка хвоста (`emo_frames`):

```
window = x[start_k … start_k + 32768 − 1]
if |window| < 32768:  window ← zero_pad(window, 32768)
```

Комментарии:

* Число кадров — **потолочное**, поэтому хвост короче 32000 сэмплов покрыт
  последним окном с добивкой нулями и лишних «нулевых» кадров не появляется.
  Сверка: `N = 32768 → 1`, `32769 → 2`, `64768 → 2`, `100000 → 4`, `0 → 0`.
* Перекрытие окон — 768 сэмплов (2.34 % окна): почти нулевое, кадры практически
  независимы. Это сознательная сетка **синхронизации** (анимация плеера, задел
  под дипольные эпохи), а не классический 50 %-STFT.
* Zero-pad хвоста занижает энергию последнего кадра (часть окна — нули);
  на глобальный референс `P` это влияет только если максимум приходится на
  последний кадр (обычно нет).

## 6. Шаг 2. FFT и бины

Для каждого кадра (`emo_radar.py::emo_frames`):

```
X = fft(window)          # numpy.fft.fft, окно прямоугольное (без аподизации)
mag_k = |X_k|            # модуль комплексного бина, k = 0…32767
```

Частота бина:

```
f_k = k · fs / n = k · fs / 32768
```

| fs | шаг бина | Найквист |
|---|---|---|
| 48000 Гц | 48000/32768 = **1.46484375 Гц** | бин 16384 = 24000 Гц |
| 32000 Гц | 32000/32768 = **0.9765625 Гц** | бин 16384 = 16000 Гц |

Комментарии:

* **Окно прямоугольное**: `np.fft.fft` вызывается по сырому окну, без `hann`/
  `hamming`. Это значит утечку спектра (spectral leakage) и боковые лепестки
  ±13 дБ: тонкая линия размывается по соседним бинам. Для суммы по широким
  блокам это малозаметно (энергия сохраняется), но на «чистом тоне» даёт
  подтёк в соседние счётчики (см. §8.4, измерение на 1 кГц).
* FFT **ненормированный** (numpy, `norm=None`): амплитуда синусоиды уровня `A`
  даёт `|X_k| ≈ A·n/2`. Абсолютный масштаб не важен — он сокращается в
  отношении `S/P` на шаге 5.
* Сигнал вещественный → спектр сопряжённо-симметричен: `|X_k| = |X_{n−k}|`.
  Это ключ к свойству блока 14 (§8.3).
* Бин 0 (DC/постоянная составляющая) и бин 32767 в расчёте **не участвуют**
  (блоки покрывают 1…32766, см. §7).

## 7. Шаг 3. Октавные блоки бинов

`emo_radar.py::octave_blocks()`:

```
B_b = (start_b, width_b) = (2^b − 1, 2^b),   b = 1…14
бины блока: k ∈ [2^b − 1, 2^(b+1) − 2]
```

* Блок 1 начинается с бина 1 (не 0) — DC исключён, поэтому постоянная
  составляющая и медленный дрейф не «съедают» луч δ.
* Окно 32768 при fs = 32000 Гц даёт разрешение 0.98 Гц — достаточно, чтобы
  различать дельта-полосу (2–4 Гц) исходной ЭЭГ после транспозиции.

## 8. Шаг 4. Семь счётчиков

### 8.1. Формула

`emo_radar.py::counter_sums(mag)` (вход — `|X_k|` длины ≥ 32768, иначе `ValueError`):

```
S = zeros(7)
for index, (start, width) in enumerate(octave_blocks()):      # index = 0…13
    S[index % 7] += sum(mag[start : start + width])
```

`index % 7` сворачивает 14 блоков в 7 счётчиков попарно — блок `b` и блок `b+7`:

```
S_k = Σ_{i ∈ B_{k+1}} mag_i + Σ_{i ∈ B_{k+8}} mag_i,     k = 0…6
```

То есть каждый луч собирает **две октавы, разнесённые на 7 октав**: узкую низкую
(блок `k+1`) и широкую высокую (блок `k+8`). Порядок лучей в payload —
`BAND_ORDER` (`bandLabels.ts`): `delta, delta_theta, theta, alpha, beta, gamma,
high_gamma` (δ 0.5–2 Гц … γ-high 64–128 Гц — границы полос ЭЭГ из
`core/config.py::freq_bands`).

### 8.2. Состав счётчиков (таблица)

Число бинов: `2^(k+1) + 2^(k+8) = 129 · 2^(k+1)`; всего `Σ = 32766`.

| `k` | луч (`BAND_ORDER`) | блоки | бины | бинов | Гц @48000 | Гц @32000 |
|---|---|---|---|---|---|---|
| 0 | `delta` (δ) | 1 + 8 | 1–2, 255–510 | 258 | 1.46–2.93 ∪ 373.5–747.1 | 0.98–1.95 ∪ 249.0–498.1 |
| 1 | `delta_theta` (δ/θ) | 2 + 9 | 3–6, 511–1022 | 516 | 4.39–8.79 ∪ 748.5–1497.1 | 2.93–5.86 ∪ 499.0–998.1 |
| 2 | `theta` (θ) | 3 + 10 | 7–14, 1023–2046 | 1032 | 10.25–20.51 ∪ 1498.5–2997.1 | 6.84–13.67 ∪ 999.0–1998.1 |
| 3 | `alpha` (α) | 4 + 11 | 15–30, 2047–4094 | 2064 | 21.97–43.95 ∪ 2998.5–5997.1 | 14.65–29.30 ∪ 1999.0–3998.1 |
| 4 | `beta` (β) | 5 + 12 | 31–62, 4095–8190 | 4128 | 45.41–90.82 ∪ 5998.5–11997.1 | 30.27–60.55 ∪ 3999.0–7998.1 |
| 5 | `gamma` (γ) | 6 + 13 | 63–126, 8191–16382 | 8256 | 92.29–184.57 ∪ 11998.5–23997.1 | 61.52–123.05 ∪ 7999.0–15998.1 |
| 6 | `high_gamma` (γ-high) | 7 + 14 | 127–254, 16383–32766 | 16512 | 186.04–372.07 ∪ 23998.5–47997.1\* | 124.02–248.05 ∪ 15999.0–31998.1\* |

\* Вторая половина луча 6 — выше Найквиста, т.е. зеркало (§8.3).

Комментарии:

* Счётчики **не нормированы** на число бинов и не взвешены (нет `1/width`, нет
  A-взвешивания, нет `sqrt`) — это сумма амплитуд «как есть». Следствия — §8.4.
* Низкая половина луча (блок `k+1`) узкая: 2…128 бинов; высокая (блок `k+8`) —
  256…16384 бинов. Поэтому вклад высокой половины доминирует при любом
  широкополосном содержимом.
* Проверка покрытия/парности — стражи
  `test_octave_blocks_cover_bins_once`, `test_counter_sums_maps_blocks_to_counters`.

### 8.3. Свойство блока 14: зеркало спектра (проверено)

Сигнал вещественный, поэтому `|X_k| = |X_{n−k}|`. Блок 14 — бины 16383…32766, их
зеркала — бины `n − k` = **2…16385**, т.е. практически весь нижний спектр:

```
Σ_{B_14} mag = Σ_{i=2}^{16385} mag_i        (измерено: 262153.435351 = 262153.435351)
```

Отсюда два следствия:

1. **`S_6 ≥ S_k` для всех `k`** — доказуемо: блоки лучей 0…5 лежат внутри бинов
   1…16382, а `Σ_{B_14}` содержит их все. Поэтому луч 6 (`high_gamma`) — не
   «высокая гамма», а **широкополосный интегратор полной энергии**; он равен
   100 % почти в каждом кадре. Проверено на белом/розовом/красном шуме, тоне и
   всех семи стемах: `argmax` кадра — всегда 6.
2. **`P = global_max = max_k S_6(k)`** (измерено: `global_max = 523980.598 =
   max S_6`): референс 0 дБ — полная спектральная энергия **самого громкого
   кадра**, а не пик отдельной полосы. Луч 6 тише 100 % только в кадрах тише
   максимума (пример: 82.176 / 70.005 / 89.877 % для кадров в 2× / 10× / 2× тише).

Демонстрация на чистом тоне 1 кГц (окно Hann, fs = 48000):

```
S = [0, 8637.8, 0, 0, 0, 0, 8637.8]   →   rays = [0, 100, 0, 0, 0, 0, 100]
```

Тон попал в бин 683 (блок 9 → луч 1), а его зеркало бин 32085 — в блок 14 →
луч 6; суммы **равны** (8637.8 = 8637.8). Луч 6 всегда «дублирует» содержание
спектра, поэтому форма звезды несёт на 1/7 меньше независимой информации, чем 7.

### 8.4. Перекос из-за числа бинов (проверено)

Счётчики суммируют амплитуды без нормировки на ширину блока, а ширина растёт как
`2^k`. Для **спектрально плоского** сигнала это даёт фиксированный «веер»:

| материал | `S_6/S_0` | наклон | `rays`, % |
|---|---|---|---|
| белый шум (A = const) | 62.33 | **+6.0 дБ/луч** | 39.8 / 49.9 / 59.7 / 70.0 / 79.7 / 90.0 / 100 |
| розовый (A ∝ f^−0.5) | — | +3.0 дБ/луч | 57.1 / 61.9 / 67.4 / 72.1 / 78.0 / 84.7 / 100 |
| красный (A ∝ f^−1) | — | ≈0 дБ/луч (0…5) | 73.6 / 73.7 / 70.8 / 72.2 / 72.1 / 72.6 / 100 |

Комментарий: 6.02 дБ = `20·log10(2)` — ровно удвоение числа бинов. Лучи 0…5
«плоского» сигнала образуют постоянную гребёнку с шагом ≈10 % радиуса, которая
не зависит от содержания кадра; выравнивание наступает только при спектральном
наклоне A ∝ f^−1 и круче. Луч 6 при любом наклоне — 100 % (зеркало, §8.3),
последний скачок (+9…+25 дБ) — вклад `Σ_{B_14}`.

### 8.5. Соответствие «полоса ЭЭГ → луч» (проверено сквозным прогоном)

Полосовая стема транспонируется умножением мгновенной частоты на `2^p`
(`core.py::band_stem`: `hilbert` → ресемпл ×96 → `u ← u^(2^p)` → `a·Re(u)`),
поэтому полоса ЭЭГ `[f_1, f_2]` оказывается в аудио-полосе `[2^p f_1, 2^p f_2]`.
Полоса с октавным индексом `m` (т.е. `2^m … 2^(m+1)` Гц) попадает в блок
`b = ⌊log2(2^p·2^m/Δ)⌋`, `Δ = fs/n`, и в счётчик `(b − 1) mod 7`:

```
fs = 48000:  k = (m + p − 2) mod 7
fs = 32000:  k = (m + p − 1) mod 7
```

Сквозной прогон (`band_stem` → `counter_sums` → `db_rays`, синус в центре полосы):

| полоса ЭЭГ | `f_c`, Гц | аудио @p=7 | пик-бин | **луч по формуле** | тот же при p=5 |
|---|---|---|---|---|---|
| `delta` 0.5–2 | 1.00 | 128 Гц | 87 | **5** (`gamma`) | 3 |
| `delta_theta` 2–4 | 2.83 | 362 Гц | 247 | **6** (`high_gamma`)\* | 4 |
| `theta` 4–8 | 5.66 | 724 Гц | 494 | **0** (`delta`) | 5 |
| `alpha` 8–16 | 11.31 | 1448 Гц | 989 | **1** (`delta_theta`) | 6 |
| `beta` 16–32 | 22.63 | 2896 Гц | 1977 | **2** (`theta`) | 0 |
| `gamma` 32–64 | 45.25 | 5793 Гц | 3954 | **3** (`alpha`) | 1 |
| `high_gamma` 64–128 | 90.51 | 11585 Гц | 7909 | **4** (`beta`) | 2 |

\* Луч 6 и так равен 100 % из-за зеркала (§8.3), поэтому для полосы, попадающей
в блок 7 (δ/θ при `p = 7`), «содержание» и «зеркало» неразличимы — они совпадают
в одном луче. Измеренные лучи (кроме 6) для этих прогонов показывают второе
по величине значение именно в расчётном луче (например `alpha` →
`[42.1, 92.7, 74.2, 60.3, 59.3, 61.9, 100]`).

Комментарий: при штатных `p = 7` и 48 кГц подписи лучей δ…γ-high **повёрнуты
относительно фактического содержания на 5 позиций** (луч, подписанный «α»,
несёт γ-содержимое 32–64 Гц и т.д.); при `p = 5` поворот — 3 позиции. Соответствие
«луч k ↔ полоса k» выполняется только при `p ≡ 2 (mod 7)` на 48 кГц, т.е. вне
доступных значений {5, 6, 7}. Подробности и предложение по устранению — §15.2.

## 9. Шаг 5. Децибельная шкала → проценты радиуса

`emo_radar.py::db_rays(raw, peak)` — один вызов на всю матрицу кадров `K × 7`:

```
P = float(raw.max())            # глобальный референс 0 дБ: все кадры, все лучи
if P ≤ 0:  pct ← zeros(K, 7)    # полная тишина
mask = raw > 0
db[mask]  = 20 · log10(raw[mask] / P)                       # всегда ≤ 0 дБ
pct[mask] = 100 · (db − EMO_DB_FLOOR) / (0 − EMO_DB_FLOOR)  # EMO_DB_FLOOR = −60
          = 100 · (db + 60) / 60
pct ← clip(pct, 0, 100)
```

Замкнутая форма (при `S > 0`, `P > 0`):

```
pct = clip( 100 + (100/60) · 20 · log10(S / P), 0, 100 ) = clip( 100 + 33.333 · log10(S/P), 0, 100 )
```

Карта «дБ → % радиуса» (проверено):

| `db` | `S/P` | `pct`, % | `r`, px (R = 90) |
|---|---|---|---|
| 0 | 1 | 100.000 | 90.0 |
| −6 | 0.501 | 90.000 | 81.0 |
| −12 | 0.251 | 80.000 | 72.0 |
| −20 | 0.100 | 66.667 | 60.0 |
| −30 | 0.0316 | 50.000 | 45.0 |
| −40 | 0.010 | 33.333 | 30.0 |
| −54 | 0.002 | 10.000 | 9.0 |
| −60 | 0.001 | 0.000 | 0.0 |
| −80 | 0.0001 | 0.000 (зажим) | 0.0 |

Цена деления: **1 дБ = 1.667 % R = 1.5 px**; полный диапазон 60 дБ = 100 % R.

Комментарии:

* **Референс глобальный** (`normalization = "db_relative"`, шкала владельца
  08.10.2026): `P` — максимум по всем кадрам и лучам трека, а не по кадру.
  Поэтому тихий passage даёт маленькую звезду целиком, громкий — большую:
  анимация показывает **абсолютную** динамику, а форму кадров можно сравнивать
  между собой во времени. Покадровый максимум прижал бы каждый кадр к 100 % и
  уничтожил динамику.
* По §8.3 `P = max_k S_6(k)`: 0 дБ — полная спектральная энергия самого
  громкого кадра.
* `20·log10` — **амплитудная** шкала (сырые суммы — амплитуды, не мощности):
  удвоение суммы = +6.02 дБ = +10 % R. Энергетическая `10·log10` дала бы вдвое
  меньший разброс и «сжала» звезду.
* Порог −60 дБ — жёсткий: всё тише становится 0 % **необратимо** (в payload нет
  данных ниже порога, восстановить в UI нельзя — см. §10).
* Нули: `S = 0` → 0 % (не −∞); `P ≤ 0` → все нули. Верхний зажим `clip(…, 100)`
  страховочный: `S > P` по построению невозможно (страж
  `test_db_rays_decibel_scale`: `db_rays([2P], P) = 100`).
* Округление в payload: `rays` — 3 знака (квант 0.001 % R ≈ 0.0009 px),
  `t_sec` — 6 знаков.
* Доминанта и геометрия полигона считаются в UI **из этих же dB-лучей** — масштаб
  наследуется автоматически, второго перевода в проценты нет.

## 10. Шаг 6. Перенос динамического диапазона в UI (`dbRangeDb`)

Отображение **без пересчёта анализа**: параметр «Динамический диапазон» панели
«ЕмоЛаб» (`DB_RANGE_OPTIONS`: −96…0 / −60…0 / −40…0 дБ; штатно
`EMO_DB_RANGE_DEFAULT = 60` — шкала контракта без изменений).

`emoRadar.ts::raysDbRange(rays, fromFloorDb, toFloorDb)`:

```
scale = (оба порога конечны и < 0) ? fromFloorDb / toFloorDb : 1
pct₂  = clamp(pct · scale, 0, 100)          (нечисловой луч → 0)
```

`framesDbRange(frames, dbFloor, dbRangeDb)`:

```
if !isFinite(dbFloor) || dbFloor ≥ 0            → frames как есть
if !(dbRangeDb > 0) || dbRangeDb === |dbFloor|  → frames как есть (без копий)
иначе → каждый кадр: rays = raysDbRange(rays, dbFloor, −dbRangeDb)
```

При `dbFloor = −60` (контракт): `scale = 60 / dbRangeDb`, и с учётом карты §9:

```
pct₂ = 100 · (db + 60) / dbRangeDb
```

| `dbRangeDb` | `scale` | −60 дБ | −40 дБ | −20 дБ | 0 дБ |
|---|---|---|---|---|---|
| 40 | 1.5 | 0 | 50.0 | 100 (зажим) | 100 (зажим) |
| 60 | 1.0 | 0 | 33.3 | 66.7 | 100 |
| 96 | 0.625 | 0 | 20.8 | 41.7 | 62.5 |

Комментарии:

* Ноль шкалы **остаётся на серверном пороге −60 дБ**, меняется цена деления
  (наклон): 1 дБ = `100/dbRangeDb` % R вместо 1.667 %.
* Применяется **один раз на входе компонента** (`RadialChart.tsx::scaledFrames`,
  `emolab/Emogram.tsx`), дальше все шаги (интерполяция, вращение, темп,
  доминанты, облако) работают с перенесёнными лучами — «Эмограмма» читает ту же
  шкалу, расхождений между представлениями нет.
* В окне шире серверного (−96…0) данных ниже −60 дБ не существует (кадры писались
  с порогом −60): всё тише остаётся на нуле, а 0 дБ не доходит до обода (62.5 % R).
  В окне уже (−40…0) всё громче −20 дБ прижимается к ободу. Обе особенности —
  предмет оценки в §15.3.
* Если перенос не нужен, возвращаются **те же** объекты кадров (без аллокаций на
  кадр анимации).
* `hopSeconds(hopSamples, fsAudio) = hop / fs` (0 при негодных входах) — шаг сетки
  для §11: 32000/48000 = 2/3 с, 32000/32000 = 1 с.

## 11. Шаг 7. Выбор кадра и интерполяция лучей

Ступенчатый выбор (счётчики/таблицы) — `emoRadar.ts::frameIndexAt`:

```
if frameCount ≤ 0 || !(hopSec > 0) || !isFinite(tSec) → 0
index = clamp(⌊tSec / hopSec⌋, 0, frameCount − 1)
```

Плавные лучи для анимации — `interpolatedRays(frames, hopSec, tSec)`:

```
нет кадров || !(hopSec > 0)                     → null
time     = isFinite(tSec) ? tSec : frames[0].t_sec
position = (time − frames[0].t_sec) / hopSec
index    = clamp(⌊position⌋, 0, K − 1)
from     = frames[index].rays
to       = frames[min(K − 1, index + 1)].rays ?? from
frac     = clamp(position − index, 0, 1)
frac === 0                                      → копия from
луч_k    = from_k + (to_k − from_k) · frac       (to_k undefined → from_k)
```

Комментарии:

* Интерполяция **покомпонентная линейная** между соседними кадрами: кадр `k`
  плавно перетекает в `k+1` на всём своём отрезке `[k·hop, (k+1)·hop)` — решение
  владельца («звезда дышит»), а не ступеньки раз в 2/3 с.
* Отсчёт от `frames[0].t_sec` (может ≠ 0), хвост держит последний кадр,
  некорректное время → первый кадр, `to` на последнем кадре — он сам (значение
  держится).
* Нечисловые/NaN лучи → 0 (в `starPolygon`), битый кадр не ломает полигон.
* Та же семантика сетки у `interpolatedRotation` (§12) и `interpolatedTempo`
  (§13): три параллельных ряда (лучи, угол, темп) интерполируются одной сеткой
  `hopSec`, поэтому фаза «дыхания», доворот и темп не расходятся.
* Источник времени — позиция плеера (`getActivePlayer()?.position` в
  `RadialChart.tsx`, цикл `requestAnimationFrame`).

## 12. Шаг 8. Вращение звезды по аккордам

### 12.1. Карта аккордов (сервер)

VAMP Chordino (`vamp:nnls-chroma:chordino:simplechord`, вывод «Chord Estimate»).
Трансформ — `backend/vamp/transforms/chordino-simplechord.n3` (мастер 48 кГц:
`sample_rate 48000`, `step_size 4800` = 0.1 с, `block_size 24576` = 0.512 с) либо
`chordino-simplechord-32k.n3` (моно 32 кГц «ЕмоЛаб»); параметры плагина —
дефолты MIREX (`useNNLS=1`, `useHMM=1`, `boostn=0.1`). CSV → `parse_chord_csv`:

```
строка len 3 → (row[1], row[2]);  len 2 → (row[0], row[1]);  иначе пропуск
t_sec = float(row) — конечное;  label = name.strip()
if label == prev_label → пропуск        (схлопывание одинаковых соседей)
code = chord_key_code(label);  None → пропуск (например «N» — аккорда нет)
сегмент = { t_sec: round(t, 6), key_code: code, label }
```

`chord_key_code(name)`:

```
match = ^([A-G])([#b]?)                    (не совпало → None)
semitone = {C:0, D:2, E:4, F:5, G:7, A:9, B:11}[root] + (# → +1, b → −1)
quality  = name[match.end():].lower()
minor    = ("dim" в quality) или (quality начинается с "m" и не с "maj")
key_code = (13 if minor else 1) + semitone
```

Проверено: `C→1, C#→2, Db→2, Bb→11, B→12, Am→22, Ebm6→16, G7→8, Dm6→15,
Cdim→13, Gaug→8, Csus4→1, F#m7b5→19, N→None` (строка отбрасывается);
`parse_chord_csv("0.0 C / 0.5 C / 1.2 N / 2.0 Am")` → два сегмента (0.0 C, 2.0 Am).

Комментарии:

* `key_code` несёт **только корневую ноту и лад** — надстройки не влияют (`G7` и
  `G` дают один код 8), а `label` сохраняет точное имя для таблицы UI.
  Enharmonic-крайности — §15.4.
* Ловушка hop (21.10.2026): `step_size` обязан быть 0.1 с — при 0.2 с
  HMM-сглаживание плагина «съедает» смены аккордов (C+Am сливаются в один
  сегмент); `block_size` 24576 = 0.512 с окна (пропорционально 16384/32000
  моно-файла «ЕмоЛаб»).

### 12.2. Угол вращения (клиент)

Единица смещения `δ = KEY_DELTA_RAD = π/42 ≈ 4.2857°` — 1/12 сектора
(сектор `2π/7` → `2π/84 = π/42`).

```
keyRotationRad(code):
  code не число → 0;  code = round(code);  code ∉ [1, 24] → 0
  code ≤ 12 (мажор): φ = +(code − 1) · δ                     (против часовой)
  code ≥ 13 (минор): tonic = code − 13
                     steps = ((9 − tonic) mod 12 + 12) mod 12
                     φ = 0 при steps = 0, иначе −steps · δ    (по часовой)
```

Полная карта кодов (δ = 4.285714°; проверено):

| код | тоника | φ, ° | код | тоника | φ, ° |
|---|---|---|---|---|---|
| 1 | C | 0.000 | 13 | Cm | −38.571 |
| 2 | C# | +4.286 | 14 | C#m | −34.286 |
| 3 | D | +8.571 | 15 | Dm | −30.000 |
| 4 | D# | +12.857 | 16 | D#m/E♭m | −25.714 |
| 5 | E | +17.143 | 17 | Em | −21.429 |
| 6 | F | +21.429 | 18 | Fm | −17.143 |
| 7 | F# | +25.714 | 19 | F#m | −12.857 |
| 8 | G | +30.000 | 20 | Gm | −8.571 |

сектора 51.429°, поэтому разрыв окружности не пересекается и интерполяция угла —
простая линейная, без shortest-path.

### 12.3. Привязка к кадрам и интерполяция

`frameRotations(keyTrack, frames)` — параллельный ряд длины `K`:

```
нет трека/пустой → нули на все кадры (вращение выключено)
для кадра: сегмент = последний с t_sec ≤ t кадра (сегмент длится до следующего)
           φ кадра = keyRotationRad(segment.key_code), до первого сегмента → 0
курсор segmentIndex двигается только вперёд (линейный проход по треку)
```

`interpolatedRotation(rotations, frames, hopSec, tSec)` — та же сетка, что у
лучей (§11): `from ?? 0`, `to ?? from`, результат `from + (to − from) · frac`.
`activeKeySegment(keyTrack, tSec)` — последний сегмент с `t_sec ≤ t` (источник
счётчика «Аккорд» в `EmoCounters.tsx`).

Комментарии:

* Вращается **полигон** (вершины), а сетка, дуги секторов и подписи неподвижны:
  аккорд поворачивает звезду, а не шкалу. Доминанты считаются **после** вращения.
* VAMP — best-effort: инструмент недоступен → `key_track = null`,
  `key_source = null`, φ = 0; расчёт лучей при этом не меняется.
* `rotations` считаются по `frames` (не по `scaledFrames` — важны только `t_sec`,
  длина рядов одинаковая), мемоизируются и меняются только со сменой кадров.

## 13. Шаг 9. Темп-коррекция радиусов

### 13.1. Карта темпа (сервер)

VAMP `vamp:qm-vamp-plugins:qm-tempotracker:tempo`; трансформ
`backend/vamp/transforms/qm-tempotracker-tempo.n3` (`sample_rate 44100`,
`step_size 512`, `block_size 1024`, `plugin_version 6`, параметры `method=1`,
`dftype=3`, `whiten=0`, `alpha=0.9`, `inputtempo=120`, `constraintempo=0`) →
CSV → `parse_tempo_csv`:

```
строка len 4 → (row[1], row[2]);  len 3 → (row[0], row[1]);  иначе пропуск
bpm = float(...), условие bpm > 0 и конечное
сегмент = { t_sec: round(t, 6), bpm: round(bpm, 3) }
```

Комментарий: вывод плагина — «locked tempo estimates»: по одной оценке на
изменение темпа, сетка **неравномерная** (не по битам).

### 13.2. Темп кадра

`frameTempos(tempoTrack, frames, hopSec)` — ряд длины `K` из `number | null`:

```
нет трека || !(hopSec > 0) → все null
sorted = tempo_track по возрастанию t_sec;  cursor = 0;  last = null
кадр: start = t_sec, end = start + hopSec
      оценки с t_sec ∈ [start, end) → sum, count (курсор только вперёд)
      if count > 0 → last = sum / count
      tempos[index] = last      (hold: кадр без оценок держит предыдущее)
```

`interpolatedTempo(tempos, frames, hopSec, tSec)` — та же сетка (§11):
`from === null → null`; `to === null → from`; иначе `from + (to − from) · frac`.

Комментарий: несколько оценок внутри окна кадра усредняются; до первой оценки —
`null` (коррекция нулевая); после последней — последнее значение (индекс зажат).

### 13.3. Ось темпа и коэффициент `Kr`

```
y  = tempoY(bpm): bpm null/нечисловой/≤ 0 → 0
                  clamped = clamp(bpm, 60, 240)
                  y = clamp(log2(clamped / 120), −1, +1)
s  = sin(π/2 · y) ∈ [−1, +1]
Kr = s² ∈ [0, 1]
```

| bpm | `y` | `s` | `Kr` | множитель `1 + Kr` |
|---|---|---|---|---|
| ≤ 60 | −1.0000 | −1.0000 | 1.0000 | 2.000 |
| 90 | −0.4150 | −0.6067 | 0.3681 | 1.368 |
| 120 | 0.0000 | 0.0000 | 0.0000 | 1.000 (нет коррекции) |
| 150 | +0.3219 | +0.4842 | 0.2345 | 1.235 |
| 180 | +0.5850 | +0.7947 | 0.6315 | 1.632 |
| ≥ 240 | +1.0000 | +1.0000 | 1.0000 | 2.000 |

Комментарии:

* Ось **логарифмическая**: 60 / 120 / 240 — равноотстоящие точки (−1 / 0 / +1),
  поэтому ускорение 120→240 и замедление 120→60 симметричны по `|y|`.
* `Kr` — квадрат синуса, всегда ≥ 0: величина коррекции не зависит от знака,
  знак `s` выбирает только половину круга (правка 10.10.2026 — было
  `sin(π/2·|y|)`).
* 120 bpm — центр: `Kr = 0`, коррекция отсутствует. Крайние значения (≤ 60,
  ≥ 240) → `Kr = 1` → радиусы выбранной половины удваиваются.

### 13.4. Применение к вершинам

`tempoCorrectedRays(values, angles, bpm)`:

```
rays = clamp(values, 0, 100)              (нечисловые → 0)
s = tempoSine(bpm);  Kr = s²
if Kr ≤ 0 → копия без изменений
для каждой вершины i:
  normalized = ((angles[i] mod 2π) + 2π) mod 2π
  isLower    = normalized ≥ π                       (квадранты 3–4)
  if (s < 0 ? isLower : !isLower) → rays[i] ← rays[i] · (1 + Kr)
max = max(rays)
if max > 100 → rays ← rays · (100 / max)            (условная нормализация)
```

`tempoStarPolygon(values, R, center, rotationRad, bpm)` фиксирует порядок:

```
angles    = segmentBoundaries() + rotationRad       (углы ПОСЛЕ вращения)
corrected = tempoCorrectedRays(values, angles, bpm)
вершины   = starPolygon(corrected, R, center, rotationRad)
```

Комментарии:

* Половину круга выбирает **знак `s`**: `s < 0` (bpm < 120) → удлиняются
  вершины 3–4 квадрантов (θ ∈ [π, 2π)); `s > 0` (bpm > 120) → 1–2 квадрантов
  (θ ∈ [0, π)). Вершины «чужой» половины не меняются.
* `angles` — углы **после** вращения (§12): квадрант определяется повёрнутым
  углом, поэтому один и тот же темп удлиняет разные вершины при разных аккордах.
  Порядок «вращение → темп → доминанты» зафиксирован спецификацией владельца.
* Условная нормализация срабатывает **только** при `max > 100`: если все радиусы
  ≤ R, абсолютный масштаб не трогается — «дыхание» звезды по громкости (§9,
  глобальная шкала) сохраняется.
* Чекбокс «Учитывать темп при расчёте лучей звезды» (`tempoRays`): `false` →
  в `tempoStarPolygon` передаётся `bpm = null` (радиусы без коррекции), но метка
  темпа на оси Y продолжает показывать bpm кадра.
* Та же логарифмическая ось у визуальных меток: засечка на оси Y радара
  `y = CENTER − tempoY(bpm) · RADIUS` (60 внизу, 120 в центре, 240 вверху) и
  ступень над волной плеера `radarTempoStepY(bpm, height) = (height/2)(1 − y)` —
  при одном bpm они стоят на одинаковой высоте. Темп не определён → засечка
  скрыта (`opacity = 0`).
* Счётчик «Темп»: `formatTempoBpm` — один знак и запятая («120,4 bpm»),
  `null` → «—».

## 14. Шаг 10. Геометрия звезды, доминанта и облако

### 14.1. Сектора и углы лучей

```
RADIAL_SEGMENTS = 7                 SEGMENT_STEP  = 2π/7 ≈ 51.4286°
SEGMENT_START   = π/2 + π/7 ≈ 115.7143°
θ_k = SEGMENT_START + k · SEGMENT_STEP,  k = 0…6   (против часовой)
GRID_FRACTIONS  = [0.25, 0.5, 0.75] — круги сетки
sectorIndexOf(a): relative = ((a − SEGMENT_START) mod 2π + 2π) mod 2π
                  → min(6, ⌊relative / SEGMENT_STEP⌋)
pointAt(θ, r, c) = { x: c.x + r·cos θ, y: c.y − r·sin θ }   (SVG: y вниз)
```

| `k` | луч | θ, ° | положение |
|---|---|---|---|
| 0 | δ | 115.714 | верх-лево |
| 1 | δ/θ | 167.143 | лево |
| 2 | θ | 218.571 | низ-лево |
| 3 | α | 270.000 | **точно вниз** |
| 4 | β | 321.429 | низ-право |
| 5 | γ | 12.857 | право |
| 6 | γ-high | 64.286 | верх-право |

Комментарий: `π/2 + π/7` выбран так, чтобы **сектор между лучами 6 и 0 был
симметричен вертикали** (его середина — ровно 90°), а вершина 3 смотрела точно
вниз. Вершины стоят на **границах** секторов (лучи-разделители), дуга сектора `k`
идёт по кругу-границе от θ_k до θ_k + SEGMENT_STEP и красится цветом полосы
`BAND_ORDER[k]` (`SECTOR_COLORS`, гамма базовых полос «Диполей»; включается
пропсом `bandColors` — «ЕмоЛаб»).

### 14.2. Вершины полигона

`radialChart.ts::starPolygon(values, R, center, rotationRad = 0)`:

```
pct_k    = isFinite(values[k]) ? clamp(values[k], 0, 100) : 0
вершина_k = pointAt(θ_k + rotationRad, R · pct_k / 100, center)
```

Геометрия чертежа (`RadialChart.tsx`): `VIEW = 200`, `CENTER = 100`,
`RADIUS = 90`, `CENTER_PT = {100, 100}`; 1 % радиуса = 0.9 единицы viewBox.
«Семилучевая звезда» — термин владельца (07.10.2026) для точек отрисовки
полигона по 7 лучам.

### 14.3. Доминанта кадра

`dominantPoint(vertices, center, R)`:

```
sumX = Σ_i (x_i − c.x);   sumY = Σ_i (y_i − c.y)        (без деления на 7)
length = hypot(sumX, sumY)
if length > R и length > 0 → sumX, sumY ← sumX·R/length, sumY·R/length
доминанта = { c.x + sumX, c.y + sumY }
```

Комментарии:

* Это **векторная сумма радиус-векторов вершин** («суммарные синусы и косинусы»):
  при равных лучах сумма = 0 (семь равномерных направлений), при разных —
  указывает на «тяжёлую» сторону полигона.
* Формально длина суммы достигает ~1.6 R (две смежные длинные вершины), поэтому
  вектор зажимается к `R`: доминанта не выходит за круг-границу.
* Считается **после** вращения и темп-коррекции (`tempoStarPolygon` →
  `dominantPoint` в `paint` и в статике).
* Луч 6 (§8.3) практически всегда 100 %, поэтому доминанта систематически
  подтянута к направлению `θ_6 + φ` — смещение расчётное, а не содержательное
  (оценка в §15.5).

### 14.4. Облако доминант и суммарная точка

```
dominantCloud(frames, R, c):
  для каждого кадра → dominantPoint(
      tempoStarPolygon(rays, R, c, rotation ?? 0, tempo ?? null), c, R)

totalDominant(points, c, R):
  пустое облако → центр
  x = Σ(p.x − c.x) / N;  y = Σ(p.y − c.y) / N          (центроид)
  if hypot(x, y) > R → зажим к R
```

Комментарии:

* Каждая точка облака — доминанта своего кадра **после его вращения и
  темп-коррекции**; порядок — порядок кадров.
* Суммарная точка — **центроид** (правка 08.10.2026): «сырая» сумма на реальном
  миксе (тысячи кадров) всегда упиралась в зажим и лежала на ободе почти в одном
  месте для разных записей; центроид по построению внутри выпуклой оболочки
  облака, зажим к `R` остаётся страховкой.
* Кружки облака держат экранный диаметр `DOMINANT_DOT_PX = 8 px`: радиус делится
  на `pxPerUnit = min(width, height) / VIEW` (приём `MriProjection`,
  `ResizeObserver`); в jsdom раскладки нет → масштаб 1.

### 14.5. Порядок применения в кадре анимации

```
rAF tick:  position = getActivePlayer()?.position ?? 0
  rays     = interpolatedRays(scaledFrames, hopSec, position)            (§10, §11)
  rotation = interpolatedRotation(rotations, scaledFrames, hopSec, position) ?? 0   (§12)
  tempo    = interpolatedTempo(tempos, scaledFrames, hopSec, position)    (§13)
paint(rays, rotation, tempo):
  vertices = tempoStarPolygon(rays, R, CENTER_PT, rotation, tempoRays ? tempo : null)
  polygon.points = vertices;  круги вершин (⌀10 px) → те же точки
  dominant = dominantPoint(vertices, CENTER_PT, RADIUS) → линия из центра + точка
  метка темпа: y = CENTER − tempoY(bpm)·RADIUS (bpm null → opacity 0)
```

Статика (без анимации): `cloud = dominantCloud(scaledFrames × {rays, rotation,
tempoRays ? tempo : null})`, `totalPoint = totalDominant(cloud)`. Фоллбэк без
данных — `randomRayPercents()` (10…100 %, один раз на монтирование); `frames` не
массив → фоллбэк (защита от дрейфа API/мока). Пауза/seek → сразу слайд текущей
позиции (тот же интерполятор).

## 15. Независимая оценка (мнение автора разбора)

> Раздел отделён от фактического описания: §4–§14 — что делает код, §15 — что я
> думаю об этом. Все утверждения ниже опираются на измерения §8–§13.

### 15.1. Что в расчёте сильно

* **Одна математика на оба раздела.** `emo_frames(mono, fs, …)` параметризован
  частотой, поэтому «Нейромузыка» (48 кГц, кадр 2/3 с) и «ЕмоЛаб» (32 кГц, кадр
  1 с) расходятся только источником сигнала и `fs` — дублирования формул нет,
  дрейф «две реализации одной звезды» исключён.
* **Глобальная шкала.** `P = max` по всему треку (§9) делает кадры сравнимыми во
  времени: «звезда дышит» — это реальная динамика громкости, а не артефакт
  покадровой нормировки. Расчёт детерминирован (случайные лучи — только
  фоллбэк при отсутствии данных).
* **Self-describing payload.** `fft_size`, `hop_samples`, `db_floor`,
  `normalization`, `global_max` едут вместе с кадрами: клиент выводит
  `hop_seconds = hop/fs` и порог шкалы из данных, а не хардкодит константы.
  Версия контракта (`schema_version = 6`) отвергается при несовпадении →
  ленивая добивка вместо молчаливого смешивания шкал.
* **Граница сервер/клиент.** Сервер отдаёт только числа (7 процентов на кадр +
  две карты), вся геометрия — в UI: визуализацию можно менять без пересчёта и
  без сервера. Все геометрические модули — чистые функции без DOM, покрыты
  Vitest; бэкенд — pytest-стражами.
* **Отказоустойчивость.** VAMP best-effort (`None` вместо 500), `frames`
  проверяется на массив, нечисловые значения → 0, темп/аккорды отсутствуют →
  нейтральные значения (φ = 0, Kr = 0), а не падение.
* **Три ряда одной сеткой.** Лучи, угол и темп интерполируются одним `hopSec`
  (§11–§13) — фазы «дыхания», доворота и темп-коррекции не расходятся.
* **Экономия в UI.** `useMemo` для рядов, `rAF` пишет атрибуты DOM напрямую
  (без state), `framesDbRange` возвращает те же ссылки, когда перенос не нужен.

### 15.2. Поворот «полоса ЭЭГ → луч» (§8.5) — главная содержательная проблема

Факт: при штатных `p = 7` и 48 кГц луч `k` несёт полосу ЭЭГ с октавным индексом
`m = (k + 2) mod 7`, т.е. подписи δ…γ-high и гамма секторов **смещены на 5
позиций** относительно фактического содержания; при `p = 5` смещение — 3.

Последствие: читатель сравнивает «звезду» с полосами ЭЭГ-сессии (δ…γ-high) и
получает неверное соответствие; цвет дуги сектора не соответствует спектру стемы.

Варианты устранения (все — без изменения формул §5–§9):

| # | Что сделать | Цена |
|---|---|---|
| a | Переставить лучи на сервере при сборке payload: `ray[k] = S[(k − p + 2) mod 7]` (48 кГц) | меняет данные → `schema_version` +1, пересчёт кэша |
| b | Добавить в payload аддитивное поле «какая полоса ЭЭГ в луче k» (вычисляется из `p` и `fs`), UI берёт подписи/цвета оттуда | старый кэш остаётся валидным, один источник истины |
| c | Исправить только подписи/цвета секторов в UI по готовой таблице §8.5 | без сервера, но знание о повороте живёт в клиенте |

Рекомендация: **(b)**, при желании «честного» порядка в данных — (a). Ключевое
требование к любому варианту: поворот зависит от `p` **и** `fs`, поэтому он
должен вычисляться, а не быть константой (при `p = 5/6` и при 32 кГц карта
другая — §8.5).

### 15.3. Параметр «Динамический диапазон» (§10) — имя не совпадает с математикой

Факт: реализован `pct₂ = pct · 60/F = 100·(db + 60)/F` — меняется **наклон**
шкалы, ноль остаётся на серверном пороге −60 дБ. Аффинный перенос окна
`[−F…0]`, которого ожидает название, — это `pct₂ = (60/F)·pct + 100·(F − 60)/F`.

Последствия текущей формулы: `F = 96` → 0 дБ даёт лишь 62.5 % R (обод
недостижим, звезда выглядит тише); `F = 40` → всё громче −20 дБ прижато к ободу
(различия на вершинах теряются).

Принципиальное ограничение: кадры пишутся с порогом −60 дБ (§9), поэтому
«настоящее» окно −96…0 дБ **невозможно** без серверных изменений — данных ниже
порога нет. Варианты: (i) переименовать параметр в «Масштаб шкалы лучей»
(соответствует фактическому поведению, ноль кода); (ii) применить аффинный
перенос и явно показывать «нет данных» ниже −60 дБ; (iii) поднять серверный
`db_floor` до −96 (пересчёт + `schema_version`). Текущее поведение — не баг
кода, а расхождение имени параметра и его формулы.

### 15.4. `chord_key_code`: энгармонические крайности

Измерено (§12.1): `Cb → 0`, `B# → 13` (= Cm вместо C = 1), `Cbm → 12`
(= B-мажор вместо Bm = 23). Причина — `semitone` не приводится по модулю 12.

Риск: `Cb` даёт `key_code = 0`, а контракт требует `ge=1`
(`AudioKeySegment.key_code`) → **валидация ответа падает целиком** (один сегмент
ломает весь `GET …/emo`, а не одну строку). Вероятность низкая (словарь Chordino
использует имена в пределах C…B, `Cb`/`B#` не встречаются), но защиты нет.

Предложение: `semitone = ((semitone % 12) + 12) % 12` перед сложением с базой
(тогда `Cb → 1`, `B# → 1`, `Cbm → 13`) + страж-тест на эти три имени;
дополнительно — отбрасывать в `parse_chord_csv` код вне 1…24 так же, как уже
отбрасывается `None` (локализация отказа до одного сегмента).

### 15.5. Луч 6 как широкополосный интегратор (§8.3) и его влияние на доминанту

Факт: `S_6 ≥ S_k` для всех `k` всегда (блок 14 = зеркало бинов 2…16385), поэтому
луч 6 = 100 % почти в каждом кадре, а `P = max S_6`.

Последствия:

* 1/7 данных дублирует весь спектр → форма звезды имеет на одну степень свободы
  меньше, чем кажется;
* доминанта (§14.3) систематически подтянута к направлению `θ_6 + φ`
  (64.286° + φ), и суммарная доминанта облака — к тому же направлению:
  сравнение «куда указывает доминанта» между записями частично отражает эту
  константу, а не содержание;
* шкала «0 дБ = глобальный максимум счётчиков» фактически всегда означает
  «полная энергия самого громкого кадра» — это стоит проговорить в описании
  шкалы (docstring говорит «глобальный максимум», что верно, но не раскрывает,
  что это всегда счётчик 6).

Если потребуется «честная» семантика лучей: считать блоки только по
положительным частотам (бины 1…16383, зеркало не суммировать) **или**
нормировать счётчик на число бинов (`S_k / width_k`). Первое убирает
дублирование, второе — ещё и веер белого шума (§8.4). Оба варианта меняют
данные → `schema_version` +1 и пересчёт кэша; текущее поведение воспроизводимо и
покрыто тестами, поэтому решение — за владельцем метода.

### 15.6. Мелкие наблюдения

* **Перекос числа бинов** (§8.4): на спектрально плоском материале лучи 0…5 дают
  постоянную гребёнку ~6 дБ/луч — форма звезды частично определяется «цветом»
  материала, а не его изменением во времени. Устраняется нормировкой на ширину
  блока (§15.5).
* **Прямоугольное окно**: утечка и боковые лепестки ±13 дБ; на чистом тоне
  соседний луч получает ~74 % (§8.5). Hann/Hamming снизили бы утечку ценой
  уширения линии, но изменили бы данные.
* **Zero-pad хвоста** (§5) занижает последний кадр; на коротких треках (1–2 кадра)
  это заметно. Альтернатива — масштабировать сумму на долю заполненного окна
  (`S · n / len(window)`); тоже меняет данные.
* **Отсчёт времени кадра**: `t_sec` — начало окна, окно покрывает `[t, t + hop)`,
  «центр тяжести» кадра — `t + hop/2`. Явной поправки на пол-окна нет;
  интерполяция к следующему кадру (§11) частично это компенсирует.
* **Тишина и «ниже порога» неразличимы** — оба дают 0 % (§9). Маркер «нет данных»
  (например −1) помог бы диагностике, но сломал бы зажимы в UI.
* **Дрейф комментария**: `keyRotation.ts` описывает коды как «QM Key Detector»,
  тогда как с `schema_version` 6 коды даёт Chordino (§12.1, §16). Диапазон 1…24
  и смысл кодов совпадают, поэтому поведение верное — устарел только текст.
* **Дедупликация аккордов** (§12.1) обновляет `prev_label` и для меток без кода
  («N»): серия «N, N» не порождает сегментов — корректно, но неявно.
* **`tempo_track` rate 44100** в параметрах трансформа при WAV 32/48 кГц: Sonic
  Annotator ресемплит сам, времена в CSV абсолютные, парсер берёт `t_sec` как
  есть — расхождения сетки нет.
* **`frames` — список dict** внутри `emo_frames`; контракт обеспечивается
  `response_model=AudioEmoOut` на роуте, поэтому «сырых» dict в HTTP-ответе нет
  (конвенция `AGENTS.md` соблюдена).

## 16. Контракт данных (payload)

`emo_frames()` возвращает dict, валидируемый `app/schemas/audio.py::AudioEmoOut`
(`response_model` роута `GET /api/v1/audio/render/{id}/emo` и ответа «ЕмоЛаб»).
Поля — сверено на живом payload (17 ключей):

| поле | тип | значение |
|---|---|---|
| `schema_version` | int | 6 (`parse_emo` отвергает иное → пересчёт) |
| `fs_audio` | int | 48000 (рендер) / 32000 («ЕмоЛаб») |
| `fft_size` | int | 32768 |
| `hop_samples` | int | 32000 |
| `overlap_samples` | int | 768 |
| `normalization` | Literal | `"db_relative"` |
| `db_floor` | float | −60.0 |
| `global_max` | float | `P` (§9) |
| `duration_s` | float | `round(N / fs, 6)` |
| `frame_count` | int | `K` |
| `frames` | list | `{t_sec ≥ 0 (6 знаков), rays: float[7] (0…100, 3 знака)}` |
| `key_track` | list \| null | `{t_sec, key_code 1…24, label}` |
| `key_source` | str \| null | `vamp:nnls-chroma:chordino:simplechord` |
| `tempo_track` | list \| null | `{t_sec, bpm > 0}` |
| `tempo_source` | str \| null | `vamp:qm-vamp-plugins:qm-tempotracker:tempo` |
| `segment_track` | list \| null | `{t_sec ≥ 0, name, segment_type 1…12}` |
| `segment_source` | str \| null | `vamp:qm-vamp-plugins:qm-segmenter:segmentation` |

История версий контракта (из докстринга схемы): **2** — дБ-шкала лучей;
**3** (09.10.2026) — `key_track`; **4** (09.10.2026) — `tempo_track`;
**5** (21.10.2026) — `segment_track`; **6** (21.10.2026) — карта аккордов VAMP
Chordino «Chord Estimate» вместо QM Key Detector (`label` — точное имя аккорда,
`key_code` — только корневая нота + лад).

Комментарии:

* `*_source` = `null` вместе с `null`-треком: клиент отличает «плагин
  недоступен» от «пустая карта».
* `segment_track` — только визуально-слуховой контроль (таблица и линии UI), в
  расчёте лучей не участвует. Трансформ `qm-segmenter-segmentation-32k.n3`:
  `nSegmentTypes = 8` (дефолт плагина 10) и `neighbourhoodLimit = 2 с`
  («Minimum segment duration», дефолт 4 с) — постановление владельца
  21.10.2026. `name` — метка плагина, пустая достраивается буквой по типу
  (1 → A, 2 → B, …); пустой/чужой CSV → пустой список (`null` зарезервирован
  под «инструмент недоступен»).
* Хранение: `emo.json` в каталоге рендера/трека + запись в манифесте `files`;
  байты — `json.dumps(sort_keys=True, separators=…)` (стабильность для
  ETag/304 и кэша). «ЕмоЛаб» — каталог по `track_id = sha256(blob)[:32]`.
* TS-типы UI генерируются из OpenAPI (`npm run gen:api`): поля `AudioEmoOut` ↔
  `schema.d.ts`, рассинхрон ловят стражи.

## 17. Сводный псевдокод (сервер → клиент)

```
# ---------- сервер (один раз на рендер/трек) ----------
mono   = (L + R) / 2                    # 48000 Гц (рендер) | 32000 Гц («ЕмоЛаб»)
starts = frame_starts(|mono|)           # 0, 32000, 64000, …
for k, s in enumerate(starts):
    w      = mono[s : s + 32768]        # zero-pad, если короче окна
    mag    = |fft(w)|                   # 32768 бинов, окно прямоугольное
    raw[k] = counter_sums(mag)          # 7 сумм по 14 октавным блокам (§7–§8)
P      = max(raw)                       # = max_k raw[k][6] — зеркало блока 14 (§8.3)
rays[k] = clip(100 · (20·log10(raw[k] / P) + 60) / 60, 0, 100)          # (§9)
payload = { метаданные окна/шкалы, frames: [{t_sec = s/fs, rays}],
            key_track, tempo_track, segment_track }                     # (§16)

# ---------- клиент (каждый кадр анимации) ----------
hop     = hop_samples / fs_audio                                   # 2/3 с | 1 с
frames₂ = framesDbRange(frames, db_floor, dbRangeDb)               # (§10)
rot     = frameRotations(key_track, frames)                        # φ кадра (§12)
bpmRow  = frameTempos(tempo_track, frames, hop)                    # bpm кадра (§13)
t       = player.position
r       = interpolatedRays(frames₂, hop, t)                        # (§11)
φ       = interpolatedRotation(rot, frames₂, hop, t)               # (§12)
b       = interpolatedTempo(bpmRow, frames₂, hop, t)               # (§13)
θ_k     = π/2 + π/7 + k · 2π/7 + φ,  k = 0…6                       # (§14.1)
pct     = tempoCorrectedRays(r, θ, tempoRays ? b : null)           # (§13.4)
vertex_k= (100 + 90·(pct_k/100)·cos θ_k, 100 − 90·(pct_k/100)·sin θ_k)   # (§14.2)
dominant= center + clamp_len(Σ_k (vertex_k − center), 90)          # (§14.3)
cloud   = [dominant каждого кадра];  total = центроид(cloud)       # (§14.4)
```
