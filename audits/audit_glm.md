## 0. Методика и ограничения

- **Глубоко в код не погружались** (по заказу): опора на структуру каталогов,
  `AGENTS.md`, реестр разделов UI (`frontend/src/app/sections/registry.ts`),
  `todo.md`/`docs/history.md`/`docs/session-start.md`, правила `docs/rules/*`,
  git-историю и точечные grep-проверки (размеры файлов, `n_jobs`, `to_thread`,
  состав миграций).
- **Счётчики из стражей:** pytest 1055 (1035 без integration), Vitest 1229,
  OpenAPI 118 путей (Консилиум — 50 операций); миграции `0001`–`0013`;
  `backend/app` — 109 py-файлов (78 в `services/`), `frontend/src` — 222 ts/tsx
  (110 тестовых).
- **Не проверялось запуском:** полные прогоны pytest/Vitest, e2e на реальном
  EDF/`~/mne_data`, профилирование CPU/RSS — оценки производительности помечены
  как **гипотезы до замеров** (инструмент замеров есть: `services/journal.py` +
  `analytics_db`).
- **Модель эксплуатации:** локальное рабочее место одного исследователя, один
  uvicorn-процесс; серверные требования — только «потолок на вырост».

## 1. Общая архитектура

| Позиция | Оценка | Аргумент |
|---|---|---|
| Слоёность «роут = форма/контракт, работа — в сервисах» | 🟢 замечательно | 78 модулей в `services/`, один шаг пайплайна = один модуль; приём файлов (`uploads.py`), формы/400 (`params.py`), задачи записи (`recording_jobs.py`) вынесены из `routes.py`; правило закреплено и ловится тестами (`test_api_assets`, `test_api_params`) |
| Единый источник конфигурации (`core/config.py`) | 🟢 замечательно | 446 строк Pydantic-settings; частотные диапазоны/длины эпох/пороги отчёта/порог Jev — из одного места; «не хардкодить пути» выполняется |
| Контракт API: Pydantic → OpenAPI → TS-типы | 🟢 замечательно | `gen:api` + стражи свежести OpenAPI (pytest и CI) — редкий для проектов такого размера инвариант; «сырые» dict в ответах запрещены конвенцией |
| Кэширование (RAM A4 + `cache_store` + ETag/304 + `asset_versions` + LRU-квота + сироты) | 🟢 замечательно | по consensus предыдущих аудитов — сильнейшая часть системы; дисковый персист полосы (Фаза B) добавил третий уровень без смешения ответственности |
| Схема БД через alembic, данные — только через владельцев | 🔵 хорошо | 13 миграций, паритет моделей/миграций — стражем `test_migrations.py`; write-API (`recording_store`/`results_store`) закрыт, **read-API 4.7 остаётся открытым** — БД пишет больше, чем читает через API |
| Job-очередь (`job_manager` + `job_store` + журнал + отмена) | 🔵 хорошо | этапы/прогресс/`cancelled`/run-manifest/restore закрыты; узкое место — семафор на всё (уже в `docs/rules/consilium.md` помечено как доработка общей очереди перед Т2/Т3) |

| Размер `api/routes.py` | 🟡 требует доработки | 2755 строк на HEAD против 1260 на 28.09 (`audit_opt_max` OM6): вынос `consilium.py`/`recording_jobs.py` не остановил рост — групповые роуты и отчёты осели там же; ломать не срочно, но точку входа ревью уже тяжело читать |

## 2. Ключевые решения реализации

| Решение | Оценка | Аргумент |
|---|---|---|
| Быстрый расчёт диполей `fast_grid` (сферическая модель, сетка) отдельно от точного `mne.fit_dipole` | 🟢 замечательно | честная маркировка `method` («не выдаётся за точный фитинг»), GOF между полосами объявлен несравнимым (RIV/CI как кросс-полосной фильтр), eLORETA — отдельный средний профиль; методологическая честность — образец |
| ИИ через модельный роутер внешних API (openai/anthropic + шлюз Jev) вместо локального llama.cpp | 🔵 хорошо | вердикт зафиксирован после проб; ключи маскируются, `data/llm_router.json` не коммитится; зависимость от внешних провайдеров — принятая цена (451 по региону уже встречался — риск задокументирован) |
| Консилиум: идемпотентность и версии (`request_id`, `expected_version`, 409, append-only реплики) | 🟢 замечательно | повтор не шлёт данные, правка = новая ревизия, архив read-only, SQL-ошибки не отражают тексты; дисциплина данных уровня продакшена в исследовательском разделе |
| Стриминг ответов советников (механизм 0011) | 🔵 хорошо | единый механизм переиспользован штурмом и чатом; «сырой текст в draft, нераспознанное — в warnings, ничего не достраивается за модель» — правильная честность |
| Перезапуск бэкенда из UI (`server_control`, `os.execv`) + режим лаунчера | 🔵 хорошо | для одного локального рабочего места прагматично (снимает класс ошибок «устаревший процесс»); для многопользовательского сервера недопустимо — но это заявленный «потолок на вырост», не текущая модель |
| GPU-тумблер (`gpu.py`, автоопределение CuPy → `n_jobs='cuda'`) | 🔵 хорошо | автоопределение вместо предположений; применение CPU↔GPU фактически ограничено refine — честно, без обещаний |
| SQLite (dev) / PostgreSQL (prod) | 🔵 хорошо | соответствует модели эксплуатации; alembic одинаков для обоих |
| Экспериментальные ветки (Нейромузыка ×128, IR pyroomacoustics/Tone.js, радар «Эмо») | 🔵 хорошо | изолированы в `services/audio_render/` + `audio_ir.py`, не мешают ядру; VAMP-тесты герметичны без бинаря; честная пометка «эксперимент» |
| Заглушки разделов «Эмо-лаб»/«Нейроаудио» в реестре до готовности | 🔵 хорошо | осознанный стаб (`Stubs.tsx`: «навигация и хоткеи не меняются потом») — правильное планирование, а не долг; ядра частично уже существуют (радар «Эмо», `audio_render`) |

**Сводка:** 6 разделов 🟢, 5 🔵, 2 плана-заглушки, 1 🟡 (Консилиум — самый крупный
открытый фронт). Оценки «сомнительно — есть лучший вариант» на этом уровне
погружения не заработал никто: спорные места (модельный роутер внешних API,
`os.execv`-перезапуск, стабы) имеют зафиксированные вердикты и осознанные
альтернативы. Ядро научного анализа (EDF → диполи → таблица/отчёт) — готово
и стабильно; рост последних трёх недель почти целиком в Консилиуме.

## 4. Возможности оптимизации (сверка `audit_opt_max` на HEAD)

> Все оценки — гипотезы до замеров; инструмент замеров уже есть
> (`services/journal.py` + `analytics_db`). Порядок: сначала замер — потом правка.

1. **PSD в один поток** (`bandpass_filter`/`spectral`): `n_jobs` на HEAD встречается
   только в refine диполей (`dipole_refine_n_jobs`) — находка **OM11 актуальна**;
   ×2–4 на многоядерной машине за ~0.5 дня.
2. **Локализация по точке в цикле** (`dipole_scanner._localize_point` —
   по-прежнему одна функция на точку): находка **OM10, по-видимому, актуальна**
   (батчинг `head_to_mni`+атрибуции); −20…40 % быстрого расчёта. Требует замера.
3. **Межзаписный кэш ядра скана** (OM12): ядро кэшируется на процесс, но не между
   записями с одинаковым монтажом — холодный старт каждой задачи дороже.
4. **Внутренние контракты `dict[str, Any]`** (OM1): типы OpenAPI спасает Pydantic в
   роутах, но между сервисами проверки нет — цена «поле переименовали — фронт не
   заметил» растёт вместе с числом сервисов (78).
5. **Декомпозиция крупных файлов** (OM2/OM6/OM17–OM19): `MriProjection` разрезан
   (закрыто 29.09), но тренд не остановлен — `routes.py` 2755, `schemas/analysis.py`
   1870, `report.py` 1490, `compare.py` 1181, `llm_router.py` 1170,
   `edfRecording.ts` 1046, `TrackStack.tsx` 952, `EdfPanel.tsx` 944. Порог
   читаемости перешагнут восемью файлами; `edfRecording.ts` — один стор на всю
   сессию просмотра без slice-подписок (OM19).
6. **Сводные метрики производительности** (OM21): журнал шагов есть, сводных чисел
   для регрессии нет — без них пункты 1–3 остаются недоказуемыми.
7. **Производительность клиента** (Этап 5, P7–P9): воркеров/GPU в клиенте нет —
   корректно отложено до замеров (`docs/rules/frontend-perf.md`).

## 5. Итог и приоритеты дальнейшей работы

**Общий вывод.** Архитектура сложилась правильной и зрелой: слои, конвенции,
контракты, кэши и дисциплина данных — сильнее большинства исследовательских
проектов сопоставимого размера. «Большого переписывания» не требуется. Проект
находится в фазе **расширения** (Консилиум, аудио-направления), а не починки ядра;
научное ядро (EDF → артефакты → эпохи → фильтры → диполи → таблица/отчёт) готово.

**Рекомендуемый порядок (по соотношению ценности/цены):**

1. **Закрыть Консилиум Т2 → Т4 → Т6** — самый крупный открытый фронт; Т2
   (аудиозагрузка/стенограмма) опирается на готовый ASR-класс и модельный роутер;
   перед Т2 — заявленная доработка общей очереди LLM/ASR.
2. **Read-API 4.7** — БД уже пишет больше, чем читает; открывает динамику ROI-пар
   и пакетную визуализацию «инструменты оркестра».
3. **Замерить и закрыть OM11/OM10/OM12** — дешёвые (0.5–2 дня) и проверяемые
   (`journal`/`analytics_db`); до замеров не трогать.
4. **Декомпозиция по мере касания**: `routes.py` и `edfRecording.ts` резать
   ближайшими срезами, их тронувшими, а не отдельной кампанией.
5. **Отложенное не поднимать**: sLORETA-профиль для δ/длинных окон и пакетная
   визуализация — после пакетных данных (вердикт 25.09 остаётся в силе);
   Этап 5 клиента — по замерам.
