## 1. Фронтенд отдаёт один бандл на 1,8 МБ — разделения кода нет (наибольшая отдача)

(`wiki/glossary.ts`, 38 КБ) и весь UI Консилиума.

**Исправление:** сделать `SECTION_MODULES` набором `lazy(() => import(...))` по разделу
и обернуть `<Component />` в `SectionRoute` (`:126`) одним `<Suspense>`; добавить
`build.rollupOptions.output.manualChunks` с выделением `tone`, `uplot`,
`react-router-dom`. Оценка: начальный чанк ~200–300 КБ вместо 1,8 МБ — вьюер остаётся

**Ревью: хорошо.** Доказательства перепроверены и сходятся: бандл ровно 1 795 487 Б,

## 2. Детектор ЭМГ копирует весь Raw по одному разу на канал

**Доказательство:** `backend/app/services/artifact_detector.py:289-292`

```python
for ch in raw.ch_names:
    result = mne.preprocessing.annotate_muscle_zscore(
        raw.copy().pick([ch]), ...
```

`raw.copy()` дублирует **все** каналы × все отсчёты; `.pick([ch])` затем выбрасывает
всё, кроме одного. Выполняется безусловно на стадии артефактов (`:546`).

**Масштабирование (оценка):** 64 канала × 30 мин × 500 Гц float64 ≈ 460 МБ на копию ×
64 канала ≈ **29 ГБ аллокаций** на прогон артефактов. На комплектном `test.edf`
(18 каналов, 130,7 с) это всего ~9 МБ — поэтому в числах журнала проблема не
проявлялась.

**Исправление:** собирать одноканальный объект вместо копирования контейнера —
`mne.io.RawArray(raw.get_data(picks=[ch]), raw.info.copy().pick([ch]))` — 0,5 МБ на
итерацию вместо полного массива. Поканальная детекция (научное требование из
докстринга) сохраняется.

**Ревью: хорошо.** Ключевой факт подтверждён: `raw` приходит с `preload=True`
(`edf_loader.py:79`) — `copy()` дублирует весь массив в памяти, арифметика ≈29 ГБ
аллокаций верна. Важно: в установленной MNE `BaseRaw.copy()` — просто `deepcopy`
**без** параметра `picks` (проверено по исходникам `mne/io/base.py:2374`), поэтому
предложенный RawArray-вариант — правильный выбор, а не «однострочник» `copy(picks=...)`.
Уточнения: (1) вместо `raw.info.copy().pick([ch])` надёжнее
`mne.pick_info(raw.info, [ch], copy=True)` — дрейф MNE API (`docs/rules/safety.md`),
поведение закрыть тестом; (2) у RawArray не будет аннотаций исходного raw — скопировать
`raw.annotations`, чтобы поведение было идентичным; (3) ещё проще — взять
`raw.get_data()` один раз и собирать одноканальный RawArray из строк массива.

## 3. `job_store.load_records()` парсит все файлы задач, без ограничения

**Доказательство:** `services/job_store.py:122` читает и делает `json.load` каждого
`*.json` в `results/jobs`, каждый до `job_result_max_bytes = 2_000_000`
(`core/config.py:222`). Вызывается **без** `limit` в:

- `services/session_bundle.py:85` — затем фильтрует по `recording_id` в Python
- `services/report.py:502` — затем фильтрует по kind/recording/stage в Python
- `services/consilium/sources.py:65`

`job_path` (`:59`) использует имя файла uuid4, поэтому отфильтровать до парсинга нечем.
Стоимость — O(все задачи × до 2 МБ) на каждый запрос отчёта/пакета/консилиума, и растёт
бесконечно.

**Исправление:** добавить параметр `predicate`/`limit` и ранний выход, либо кодировать
`recording_id` + `kind` в имени файла, чтобы кандидатов отбирал сам листинг каталога.
~~Самое дешёвое немедленное улучшение: передать `limit=cfg.jobs_history_limit` (50) в
трёх местах, где важны только свежие прогоны.~~ **Не делать** — см. ревью.

**Ревью: частично.** Проблема подтверждена (три вызова без `limit`, uuid4 в именах
файлов — `job_store.py:59-68`), основное исправление верно. Но «дешёвый» quick-fix с
`limit=50` семантически опасен: все три вызова фильтруют по `recording_id`/`params_sig`
(сверка отчёта со старой стадией — `report.py:506-515`, пакет записи —
`session_bundle.py:83-88`, источники консилиума — `consilium/sources.py:63-73`), им нужны
**все** файлы конкретной записи, а не «глобально свежие 50». Глобальный limit молча
отрежет старые задачи: сверка отчёта начнёт отвечать «стадия не выполнялась», пакет
потеряет файлы. Применять только predicate или кодирование `recording_id`+`kind` в
имени файла.

## 4. `head_to_mni` вызывается на точку внутри циклов диполей

**Доказательство:** `services/dipole_scanner.py:379-389` вызывает
`mne.head_to_mni(position_m.reshape(1, 3), ...)` по одной эпохе внутри
`for pos in range(n_epochs)` (`:620`); `services/dipole_fitter.py:254` делает то же на
каждую точку траектории.

Собственный замер проекта (`docs/rules/frontend-perf.md` §2) даёт `head_to_mni` =
**93,1 мс** на вызов. На 100 эпохах это ≈ 9,3 с чистой поточечной накладной — вторая по
величине стоимость после перебора сетки.

**Исправление:** `head_to_mni` уже принимает массив `(n, 3)`. Собрать все позиции,
вызвать один раз, затем разложить результаты обратно по словарям точек. То же в
`dipole_fitter`. Оценка экономии: ~90 мс × (n−1) на скан.

**Ревью: хорошо.** Подтверждено: `_localize_point` (`dipole_scanner.py:373-393`)
вызывается на каждую эпоху (`:634` внутри `for pos in range(n_epochs)`),
`dipole_fitter.py:254` — на каждую точку траектории; `head_to_mni` принимает массив
`(n, 3)` (сигнатура MNE проверена по исходникам). Находка даже сильнее: `_localize_point`
на каждую точку заново делает `mne.read_trans` (чтение файла transform), а `head_to_mni`
внутри вызывает `read_talxfm` — чтение `talairach.xfm` + заголовка `orig.mgz` **без
кэша** (`lru_cache` нет, проверено). 93 мс — это в основном диск; батчинг убирает обе
потери разом. Попутно: `_mri_head_transform` тоже закэшировать на запись (в
`dipole_fitter` transform уже кэшируется через `_get_transform` — там остаётся только
батчинг).

## 5. `TrackRow` перерисовывается 18–64 раза за кадр панорамы, и `memo` «как есть» не поможет

**Доказательство:** `grep -c "memo("` по `frontend/src` = **0**. `TrackStack.tsx` держит
`cursor` (`:154`) и `levelMark` (`:161`) в состоянии и коммитит один рендер стека на
кадр rAF при панораме (`:459`). Каждый кадр перерисовывает все строки `visible.map(...)`
(`:765`).

Обернуть `TrackRow` в `React.memo` само по себе не поможет: три пропа создаются заново
на каждый рендер:

- `qc={{...}}` — `TrackStack.tsx:782`
- `zones={name === expandedChannel ? expandedZones : []}` — `:804` (новый литерал `[]`)
- `epochFrames={... epochFramesForChannel(epochs, name) : []}` — `:807`

**Исправление:** `memo(TrackRow)` + `useMemo` для объекта `qc` по ключу
`[channelQc, name, qcThresholds]`, модульная константа `const NO_ZONES: ArtifactZone[] = []`
для пустого случая и `useMemo` для `epochFrames` по каналу. Жизненный цикл чарта уже
корректен (создаётся один раз, `setData` отдельно — `TrackRow.tsx:164-199`), так что речь
только о пропуске работы React.

**Ревью: частично** (диагноз верен, лечение не бьёт в цель и было неполным). Факты
подтверждены: `memo(` в проекте нет, `cursor`/`levelMark` в состоянии (`:154`/`:161`),
один рендер стека на кадр rAF при панораме (`:455 setCenterSec` → `:459`). **Пять**
нестабильных пропов на месте: `qc`-объект (`:782-800`), литерал `[]` в `zones` (`:804`),
`epochFramesForChannel` возвращает новый массив от `.filter`
(`shared/lib/viewerLayers.ts:391-399`) плюс литерал `[]` (`:808`), **а также**
`onLabelClick`/`onToggleExpand` (`:801-802`): `handleLabelClick` (`:531`) и
`handleToggleExpand` (`:537`) — обычные функции, новая идентичность на каждый рендер, нужен
`useCallback` на обе (зависимости тривиальны: `navigate` стабилен, `setExpandedChannel` —
стабильный сеттер). Остальные обработчики строк уже стабильны: `onZoneSelect` (`:611`),
`onCanvas` (`:181`), `onPickLevel` (`:641`), `wasDragged` (`:645`) — все `useCallback`.
**Но** при панораме каждый кадр меняет `window` (мемоизирован от `centerSec`,

пропсы, увидит новый `window` и **не пропустит ни одну строку именно в заявленном
сценарии (панорама)**; плюс эффект строки `[env, window]` (`TrackRow.tsx:198-201`) всё
равно обязан выполнить `setData`/`setScale` каждый кадр. Стабилизация
`qc`/`zones`/`epochFrames` **+ `useCallback` на `handleLabelClick`/`handleToggleExpand`** —
правильная гигиена, но выигрыш «18–64 строк за кадр» она не даст: `memo` поможет только на
редких событиях (клик курсора/уровня, смена QC). Чтобы реально убрать React-работу из кадра
панорамы, окно нужно вынести из пропсов строк: императивно обновлять x-шкалу в rAF-commit
через **новый** реестр экземпляров uPlot (паттерн реестра уже есть — ref + стабильный
`registerCanvas`, но `canvasesRef` (`:180-183`) хранит `HTMLCanvasElement` для
PNG-снапшота (`:674`), а `setScale` вызывается на экземпляре uPlot, не на холсте; отдавать
экземпляры придётся из `TrackRow`, где `chart` создаётся — `TrackRow.tsx:172-179`) либо
через подписку на стор — тогда `memo` заработает и задуманное получится.

## 6. У движка SQLite нет прагм и настройки пула

**Доказательство:** `models/db.py:38` — `create_async_engine(DATABASE_URL, echo=False)`.
Нет `connect_args`, нет `pool_pre_ping`, нет `pool_size`. `grep` по
`PRAGMA journal_mode` / `busy_timeout` / `event.listen` в `backend/app` вне
`analytics_db.py` (там только `user_version`) ничего не находит.

Режим журнала по умолчанию — `delete`, поэтому читатель блокирует писателя. При
`max_concurrent_jobs = 2` (`core/config.py:63`) плюс асинхронные пути записи в
`results_store`/`consilium` конкурентные записи могут проявиться как `database is locked`
вместо очереди.

**Исправление:** для SQLite — `connect_args={"timeout": 30}` плюс событие `connect` с
`PRAGMA journal_mode=WAL` и `PRAGMA synchronous=NORMAL`; для PostgreSQL —
`pool_pre_ping=True` и явный `pool_size`. Это исправление корректности под нагрузкой не
меньше, чем скорости.

**Ревью: хорошо** (это и про корректность). Подтверждено: `models/db.py:38` — engine без
`connect_args`/`event.listen`/PRAGMA; в `services/analytics_db.py` — только
`user_version`, его отдельное sqlite3-соединение тоже стоит накрыть теми же прагмами.
Уточнения: слушать событие на `engine.sync_engine`; прагмы вынести в helper, чтобы
тестовые движки (их много, с подменой `db.engine`) тоже их применяли; WAL не работает на
некоторых сетевых ФС — для локального `data/` ок.

счётчик по `kind` в `:284` — уже правильный образец.

**Ревью: хорошо** (мелочь, низкий приоритет). Уточнение к заголовку: COUNT-запросов

корректен; из-за низкой частоты вызова — последний в очереди.

## 8. `/init-status` обходит дерево исходников в event loop каждые 30 с

**Доказательство:** `main.py:189` → `utils/versions.py:49` делает `root.rglob("*.py")` +
`path.stat()` по всем 128 модулям бэкенда, синхронно внутри `async def`.
`StatusBar.tsx:37-38` опрашивает его с `refetchInterval: 30_000` на каждую открытую
вкладку. `cache_usage` корректно вынесен в `to_thread` (`main.py:183`), а
`code_freshness()` — нет.

В абсолюте немного (~1–3 мс), но это блокирующая работа в цикле, повторяемая на вкладку,
ради значения, которое меняется только при правке файлов.

**Исправление:** мемоизировать `code_freshness` на ~10 с (модульный guard по метке
времени) либо перенести в существующий блок `to_thread`.

**Ревью: хорошо** (гигиена). Подтверждено: синхронный вызов прямо в `async def`
(`main.py:277`), `StatusBar.tsx:38` — `refetchInterval: 30_000`; соседний `cache_usage`
уже честно в `to_thread` (`main.py:183`) — контраст виден. Оба варианта исправления
корректны; для индикатора `stale` мемоизация в 10 с допустима (задержка появления плашки
«код устарел» некритична).
