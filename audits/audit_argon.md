## 1. Резюме (один экран)

**Общий вердикт: хорошо, с отдельными блоками «замечательно».** Инженерная база (слои,
контракты, кэши, задачи, тесты-стражи) — сильнейшая часть проекта и соответствует масштабу
(десятки тысяч строк с обеих сторон, 125 путей API, ~2.2 тыс. тестов) без признаков
расползания. После закрытия С0–С3/С8 продукт впервые **целиком покрывает измерительный
контур методики**: поддиапазоны → КД → кластеры → пакет архива. Дальше ограничение не
инженерное, а методическое: значения X %, GOF и признаков кластеров приходят от эксперта
и не изобретаются в проекте — до их получения часть функций работает в режиме «измерено,
но не оценено» (честный `NULL` вместо вердикта).

**Замечательно:** сервисная декомпозиция «один шаг = один модуль»; слоистость «роут =
форма, работа — в сервисах»; контракт Pydantic → OpenAPI → TS-типы с двумя стражами
свежести; многоуровневый кэш (RAM → диск → `cache_store` → ETag/304) с отпечатками ассетов
и квотой; воспроизводимость (run-manifest с паспортом критерия С0, журнал шагов,
`analytics.db`); методическая честность («GOF между полосами не сравним», `fast_grid` ≠
`fit_dipole`, честный `None` вместо нуля); тесты/CI и документация как система со стражами.

**Хорошо:** разделы EDF, ЭЭГ, Диполи, Итоги, Wiki, Нейромузыка (эксперимент), Настройки/
Сервер; пакетная обработка архива и read-API новой схемы; job-очередь с отменой и
восстановлением; async-дисциплина.

**Требует доработки:** Консилиум (Т1 принята 11.10, но Т2/Т4/Т6 и политика внешнего ИИ
открыты — крупнейший фронт); ЕмоЛаб и Нейроаудио (заглушки — честно заявлены, но в
«готовности продукта» это ноль); `api/routes.py` (≈2.7 тыс. строк, шесть доменов); два
поколения схем результатов (legacy `sessions/epochs/dipoles` живут рядом с
`analyses/analysis_bands/dipole_points`); Таблица без фильтров/виртуализации/экспорта
выборки; производительность клиента (бандл ~2.4 МБ, P7–P9) — только после замеров.

**Сомнительно — есть лучший вариант:**
1. **Долгая жизнь legacy-ветки `/analyze`** с собственными таблицами `sessions/epochs/
   dipoles`: их пишет только она, тогда как весь новый функционал (С1/С2/С8, read-API,
   групповой) живёт на `recordings/analyses/dipole_points`. Лучший вариант — заморозить
   legacy-таблицы как deprecated (как уже сделано с `/sessions*`) и перевести остатки
   потребителей на новую схему, а не поддерживать два поколения вечно.
2. **Ручной набор полос в «Диполях» при готовом разведочном спектре (С3)**: пик PSD
   (`psd_peak_hz`) уже возвращается как готовый вход выбора поддиапазонов — автоподсказка
   2–3 кандидатов узких полос (параметр просмотра, без автозапуска расчёта) сэкономит
   рутину и снизит риск набрать «красивую», но пустую полосу. Выбор остаётся за человеком.
3. **Один семафор на всю job-очередь** (LLM/ASR-запросы и дорогие MNE-прогоны в одной
   очереди): перед Т2/Т3 нужна раздельная/приоритетная очередь — заявлено в
   `docs/rules/consilium.md`, но всё ещё «на потом».

## 2. Архитектура — **замечательно** (с оговорками §2.3)

### 2.1 Что сделано правильно (и это держится стражами, а не традицией)

| Решение | Оценка | Обоснование |
|---|---|---|
| «Один шаг пайплайна = один модуль» в `services/` (55+ модулей) | **замечательно** | Декомпозиция по шагам методики, а не по техническим слоям; новый шаг = новый модуль без разрастания соседей |
| Слоистость «роут = форма и контракт, работа — ниже» (`params.py`, `recording_jobs.py`, `uploads.py`, `assets.py` — адаптеры) | **замечательно** | HTTP-нюансы изолированы; сервисы тестируются без `TestClient`; `routes.py` — единственная крупная точка (§2.3) |
| Контракт: Pydantic в `schemas/` → OpenAPI → генерация TS (`gen:api`) + два стража свежести (pytest + CI) | **замечательно** | Расхождение контракта и реализации падает тестом, а не молча в UI; «сырые dict» запрещены конвенцией |
| Кэширование: RAM (`prepared_signal`) → диск-персист (`prepared_persist`) → `cache_store` → ETag/304 (`assets.py`), отпечатки `asset_versions`, LRU-квота, сироты | **замечательно** | Четыре уровня без смешения ответственности; уроки A7 (версии ассетов) усвоены — инвалидация через отпечатки |
| Задачи = jobs (`job_manager` + `job_store` + `run_manifest` + журнал) | **хорошо** | Этапы/прогресс/кооперативная отмена/восстановление после рестарта; узкое место — один семафор (§1 п.3) |
| Схема БД только через alembic, write/read-API через `recording_store`/`results_store`, паритет моделей/миграций стражем | **хорошо** | Миграционная дисциплина образцовая; минус — два поколения таблиц (§2.3) |
| Async-дисциплина (тяжёлое — `asyncio.to_thread`, правило `ASYNC` в ruff) | **хорошо** | Регулярный риск блокировки event loop закрыт автоматически |
| Ассеты большие/статичные (меш, BA, МРТ, контуры) — отдельными кэшируемыми эндпоинтами | **замечательно** | `/analyze` не тащит мегабайты; 304 экономит трафик |
| Документация как контракт (лимиты размера, стражи `test_docs_guards.py`, правило «сначала кирпич — потом расчёт») | **замечательно** | Редкость: документация не гниёт, потому что её ломание падает тестами |

### 2.2 Принятые решения реализации — оценка

- **Методическая честность как архитектурный инвариант — замечательно.** Разделение
  «измерение / отображение / интерпретация» проводится последовательно: интерполяция
  playback подписана «отображение, не измерение», `fast_grid` ≠ `fit_dipole`, GOF не
  сравним между полосами, числа патента не в дефолтах. Это главный актив проекта с точки
  зрения его научного назначения.
- **Решения по отклонениям (autoreject, ICLabel advisory, Parquet/DuckDB с 4.7, самописный
  3D против Niivue, перенос расчётов на клиент) — хорошо:** за каждым стоит замер или
  спайк в `docs/history.md`, а не вкус. Журнал решений ведётся.
- **Pydantic-settings как единственный источник конфига — хорошо**; после Шага 1 дефолты
  перестали хардкодить `/home/...`.
- **Внешний ИИ (модельный роутер вместо локального llama.cpp) — хорошо с оговоркой:**
  выбор аргументирован (спайк 10.10), ключи маскируются, `data/llm_router.json` вне git,
  но **политика передачи данных добровольца провайдеру не опубликована** (todo.md Шаг 4) —
  это единственный вопрос безопасности уровня продукта, а не кода. До его закрытия
  расширение ИИ-функций (Т2/Т6) преждевременно.

### 2.3 Архитектурный долг (требует доработки, без срочности)

1. `api/routes.py` — ≈2.7 тыс. строк, шесть доменов. Вынос `consilium.py`/`recording_jobs.py`
   не остановил рост (групповые роуты и отчёты осели там же). План разрезки есть
   (`todo.md` Шаг 5, образец — `consilium.py`); делать по мере касания, не кампанией.
2. Два поколения схем результатов: legacy `sessions/epochs/dipoles` (пишет только
   `/analyze`) ↔ `recordings/analyses/analysis_bands/dipole_points` (весь новый контур).
   Read-API 4.7 закрыт, групповой переведён — направление верное, но миграция не доведена
   до конца (см. §1 «сомнительно» п.1).
3. `edfRecording.ts` (клиент) — крупный слой состояния; `TypedDict`-контракты сервисов
   (`artifact_detector`, `results_store`) — заявлены, не сделаны. Оба пункта — Шаг 5.

## 4. Возможности оптимизации функционала

Правило проекта «сначала замер — потом правка» соблюдается; ниже — кандидаты с
аргументацией и ожидаемым эффектом, отсортированные по отношению «ценность/риск».

### 4.1 Высокая ценность

1. **`n_jobs` для `compute_psd`/`eloreta`/`compare`** (`todo.md` Шаг 5, замеры OM10–OM12
   актуальны). Самая дешёвая оптимизация: параметр уже существует в MNE, нужен прогон
   `journal`/`analytics.db` до/после. Ожидание — линейный выигрыш на многоядерных.
2. **Пакетные прогоны как источник данных для всего остального (С8 → С7/С2/отчёты).**
   Оптимизация не кода, а сценария: один обход архива снимает сразу три задачи
   (наполнение БД, кластеры по популяции, дифференциальный анализ). Это главный
   функциональный рычаг сейчас.
3. **Переиспользование кэшей пакета между сессиями**: ядро перебора кэшируется на
   «модель × монтаж» — при пакетной обработке архива одного монтажа 10-20 выигрыш на
   прогон большой; проверить, что С8 его получает.
4. **Приоритетная/раздельная job-очередь** (см. §1 п.3): LLM-запрос не должен ждать
   10-минутный MNE-прогон и наоборот. Заодно закрывает заявленное в `consilium.md`.

### 4.2 Средняя ценность (по мере касания, по замерам)

5. **Код-сплиттинг клиента** (~2.4 МБ бандл): разделы грузятся лениво — эффект на старте
   и на слабых машинах исследователя. После замеров `__diplockPerf.stats()`.
6. **float32 в `prepared_signal`** — экономия RAM примерно вдвое; риск — точность,
   поэтому только со сверкой (заявлено в todo).
7. **Воркер + `OffscreenCanvas` для спектрограммы (P7–P9)** — снятие фризов UI на
   длинных записях; зоны артефактов на canvas; пирамида в IndexedDB.
8. **Разрезка `routes.py`/`models/db.py`/`edfRecording.ts`** — не даёт скорости, даёт
   скорости разработки; делать при касании файлов (уже так и запланировано).
9. **Предел числа audio-вариантов Нейромузыки на запись** — квота включена, но
   до 1.9 ГБ на запись при рендере остаётся фактом; стоит добавить явный лимит/жизненный
   цикл (auto-evict старых батчей).

### 4.3 Низкая ценность / не поднимать без решения

- sLORETA-Lite для δ, `doppler` в sidecar, ROI-динамика взаимодействия, пресеты δ1/δ2 —
  вердикты «отложено» остаются в силе.
- Parquet/DuckDB/Zarr — с версии 4.7 и только если `analytics.db` упрётся в объём.
- Docker — официально не поддерживается (вердикт 15.10): не восстанавливать без
  осознанного решения.

### 4.4 Оптимизация процесса (не кода)

- **Integration-job в CI (остаток F12)** — сейчас «зелёный» CI не гоняет научные ветки;
  это риск регресса методики, который растёт с каждым новым расчётом.
- **coverage-отчёт** — отсутствует как показатель; инвентарь в `docs/rules/tests.md`
  хорош, но числовой coverage позволил бы ловить дыры системно.

## 5. Аудит UI: удобство и визуальная информативность (по разделам)

Общие впечатления: UI выстроен вокруг двух сильных принципов — **«правка не запускает
расчёт»** и **«воспроизводимая ссылка»** — и это чувствуется: пользователь всегда знает,
что результат устарел, а состояние не теряется. Тёмная тема, крупный шрифт, тултипы,
аккордеоны панели, меню быстрого перемещения — уровень проработки выше среднего для
научного инструмента. Сквозные замечания (применяются ко всем разделам):

- **A. Перегрузка тулс-хедера в «тяжёлых» разделах** (Диполи, EDF, Итоги): до 10–12
  элементов в один ряд. Кнопки-иконки экономят место, но цена — запоминание: новичок
  читает хедер по тултипам. Рекомендация: группировать по логическим кластерам
  (загрузка / расчёт / навигация / экспорт) с визуальными разделителями.
- **B. Единый язык «свежести результата»**: фраза «параметры изменены — результат не
  пересчитан» местами дублируется пятью разными формулировками (точечный индикатор,
  подпись, предупреждение таблицы…). Стоит свести к одному токену-статусу с цветом
  (зелёный/жёлтый/красный), как уже сделано точками стадий в EDF.
- **C. Доступность чисел**: во многих панелях ключевые величины (GOF, доля выживших
  эпох, RIV) показаны текстом без визуального ранжирования. Микро-бары или sparkline
  внутри ячеек повысили бы «читаемость с одного взгляда» без новых расчётов.

### 5.1 Главная — **хорошо**
- **Удобство:** понятная точка входа, строка готовности, быстрые действия. Минимум
  шума — правильно для заставки.
- **Информативность:** строка готовности бинарна («все/часть/сервер недоступен»).
  Улучшение: раскрыть «часть компонентов не готова» конкретным списком (что именно не
  готово — MNE? fsaverage? БД?) прямо на заставке; сейчас это вынужденный переход в
  «Состояние сервера».

### 5.2 EDF (просмотр записи) — **замечательно**, с замечанием
- **Удобство:** лучший раздел проекта. Раздельные кнопки стадий с индикаторами
  «считалось/устарело/ошибка» — образцовое решение; ручные пометки эпох Ctrl+кликом,
  таймлайны с причинами блокировки, рамки «канал-виновник», меню секций панели.
  Неотключаемый скроллбар с пропорциональным ползунком — мелочь, а показывает положение
  окна в записи.
- **Информативность:** слои (артефакты 11 видов, эпохи, зоны чистки) наложены грамотно,
  легенда общая с «ЭЭГ». Каветы («канал-виновник не определён» при `reject=None`) —
  честные.
- **Замечание:** плотность информации максимальная из всех разделов; для первого
  контакта полезен бы «режим новичка» или прогрессивное раскрытие слоёв (сейчас все
  включаются/выключаются вручную и по умолчанию набор широк).

### 5.3 ЭЭГ (трек и спектрограмма) — **хорошо**
- **Удобство:** разделение селекторов «Канал»/«Микс» (30.09) устранило путаницу;
  связанный курсор, режимы «связано/обзор», рамка окна трека — всё решает реальные
  задачи («когда появился ритм»). ERD/ERS с baseline-полями — мощный контроль.
- **Информативность:** палитра/окно дБ/сглаживание считаются на клиенте — правки
  мгновенные. Но: **нет линейки-легенды палитры** с числами (градиент дБ/ERD-шкала
  рядом со спектрограммой) — цвет читается без опорных значений; горизонтальные линии
  (частота клика, уровень) есть, а цветовой ключ — нет.
- **Улучшения:** (1) вертикальный зум (из `todo.md`) — просится сам; (2) легенда-градиент
  с подписями дБ/%; (3) подпись режима (дБ / ERD %) прямо на холсте, а не только в
  панели.

### 5.4 Диполи — **хорошо** (самый сложный раздел — и это видно)
- **Удобство:** три проекции с кликабельным срезом и линейкой, реальный МРТ-срез,
  playback с интерполяцией и честной оговоркой «это отображение», форма фильтров с
  optgroup и подписью «В расчёт уйдёт: …». Панель «Пакет поддиапазонов» (С1) и
  «Разведочный спектр» (С3) — логичное продолжение сценария «спектр → полосы →
  прогон».
- **Информативность:** слои (анатомия, БА, диполи) переключаются; хит-тест называет
  структуру/поле под точкой; FFT-гистограмма с интерактивным окном частот.
- **Проблемы:** (1) слой точек диполей без фильтра «прошедшие КД» — после С0 это главный
  кандидат на фильтр отображения (показывать серым/скрывать `kd_passed=false`); (2) в
  пакете поддиапазонов сопоставление полос — таблица чисел, визуальное сравнение полос
  (наложенные траектории/сдвиги) отсутствует; (3) «зачатки» топокарт и спектра по
  диапазонам всё ещё названы зачатками в документации — в UI стоит явно подписать их
  статус, чтобы не выглядели готовой функцией.

### 5.5 Таблица локализации — **требует доработки** (по составу), **хорошо** (по форме)
- **Удобство:** семантическая таблица, липкая шапка, состав колонок чекбоксами,
  сортировка — база сделана правильно. Честное «—» вместо выдуманных значений.
- **Информативность:** атрибуция («около X ~N мм», «вне мозга») — сильно; но без
  фильтров и поиска таблица на сотни строк нечитаема. Нет визуального выделения строк,
  прошедших КД (с С0 данные есть — осталось показать).
- **Улучшения (в порядке ценности):** (1) фильтр «только прошедшие КД» + пороги GOF/
  момент; (2) экспорт выборки CSV/JSON; (3) клик по строке → фокус диполя в разделе
  «Диполи»; (4) виртуализация — когда архивные прогоны дадут тысячи строк.

### 5.6 Групповой анализ — **хорошо**
- **Удобство:** кандидаты пар/группы из read-API новой схемы, блоки «Кластеры B8»,
  экспорт CSV, тепловая карта «BA × сессии». Отчёты Тип 1/Тип 2 собраны по месту.
- **Информативность:** агрегаты понятны; но UI-плейсхолдеры (динамика ROI-пар) и
  отсутствие единого «светофора» качества сравниваемых записей (доля выживших эпох,
  предупреждения КД) оставляют риск сравнения несопоставимых сессий — с С0 данные для
  такой подсказки уже есть.

### 5.7 Итоги (автоотчёт) — **хорошо**
- **Удобство:** сценарий «собрать → прогресс → открыть HTML» прост; тема светлая/тёмная
  с синхронизацией URL, печать всегда светлая — проработано. Вкладка «Динамика структур»
  с таймлайном и экспортом CSV закрывает главный вопрос чтения отчёта.
- **Информативность:** 8 кросс-проверок с вердиктом первой строкой — сильное решение
  (отчёт сам предупреждает о рисках данных). Минус: тепловая карта — PNG со светлым
  фоном в тёмной теме (заявлено как осознанное ограничение); кросс-предупреждения
  видны только внутри HTML — в UI-панели нет краткого «списка замечаний» до открытия.
- **Улучшения:** вынести предупреждения/вердикт в карточку результата рядом с кнопкой
  «Открыть отчёт»; прозрачный фон PNG для тёмной темы.

### 5.8 Консилиум — **хорошо** (качество), **требует доработки** (полнота сценария)
- **Удобство:** Т1 (дело, контекст, история, материалы/снимки) принята владельцем —
  рабочий ручной контур есть. Советники Т3, штурм, библиотека предложений, чат через
  роутер — сделано аккуратно; ограничения методики («вывод — гипотеза, не диагноз»)
  соблюдены.
- **Информативность:** основания по раскрытию — правильно; но граница «что из текста
  пришло от ИИ, а что ввёл человек» и граница «данные покидают машину» должны быть
  **визуально неснимаемыми** (плашка на уровне раздела, а не тултипа) — до политики
  внешнего ИИ это вопрос безопасности, а не удобства.
- **Улучшения:** плашка «внешний ИИ» с маскированным провайдером и счётчиком бюджета;
  прогресс ASR с временем (когда Т2 придёт); единый статус очереди (сейчас один семафор
  на всё — §1 п.3).

### 5.9 Нейромузыка (эксперимент) — **хорошо**
- **Удобство:** сценарий «рендер → статус → WAV+sidecar» понятен; варианты
  Экспресс/Монтаж, выбор октав, партитура и плеер — богато для эксперимента.
- **Информативность:** партитура 7 треков ×128 — плотная визуализация; радар «Эмо»
  читается. Вторая нижняя область визуализации (из todo) как раз даст «глубину» трекеру.
- **Улучшения:** размер рендеров (до 1.9 ГБ/запись) должен быть виден в UI перед
  запуском (оценка стоимости — принцип раздела «Долгие операции», здесь он не
  реализован); индикация «сколько вариантов уже отрендерено и сколько места занято».

### 5.10 ЕмоЛаб / Нейроаудио — **требует доработки** (ожидаемо)
- Заглушки с планом работ — честное решение, но пользователь видит два раздела-пустышки
  с хоткеями 8/9. Улучшение: показывать на заглушке не только план, но и **то, что уже
  доступно смежно** (ERD/ERS из «ЭЭГ», динамика из «Итогов») — это снижает ощущение
  «дыры» и направляет пользователя.

### 5.11 Wiki / Настройки / Состояние сервера — **хорошо…замечательно**
- **Wiki — замечательно:** статьи + глоссарий + хеш-навигация; пояснения переехали из
  UI (решение верное — UI не засорён модалками). Риск — двойное хранение текста с
  `docs/`: нужна механика сверки (или единый источник с генерацией).
- **Настройки — хорошо:** read-only параметры расчёта, GPU-тумблер с причиной отказа.
  Единственный редактируемый элемент с серверным источником истины — образцово.
- **Состояние сервера — хорошо:** полный разбор `/init-status`, поллинг только при
  открытой вкладке. Улучшение: цветовые бейджи по строкам проверок (сейчас — текстовый
  список); кнопка «Перезапустить бэкенд» есть, guard на `/server/restart` — открытый
  пункт.
