## Бэкенд — новые находки (по убыванию ожидаемой отдачи)

### Б1. Список готовности читает все записи и всю историю прогонов до пагинации (высокая)

`backend/app/services/readiness.py:453-460` выбирает **все** подходящие
`RecordingRecord` и передаёт все ID в `_stages_for`; срез страницы — только в конце:
`items[offset:offset + limit]` (`:473-474`). `_stages_for` тянет session/analysis/report-прогоны
для всех ID без ограничения истории (`:264-268`), хотя списку нужна лишь сводка
(`full_history=False`, `:342-417`).

**Масштабирование (оценка):** стоимость страницы растёт с числом записей и накопленных
прогонов, а не с размером страницы; деградирует по мере наполнения БД.

**Лечение:** сначала пагинировать ID записей (SQL `offset/limit`), затем `_stages_for`
только для страницы. Частота — на запрос страницы готовности (раздел «БД»).

### Б2. Async-роуты ассетов синхронно строят тома в event loop (высокая на холодном кэше)

`backend/app/api/routes.py:1926-1935` — `async def get_mri_slices` напрямую зовёт
`mri_meta(settings)`; докстринг обещает ~0,7 с на первую сборку MNI-тома
(`services/mri_slices.py:408-432, 487-490`). То же в `routes.py:2072-2080` —
`contours_meta` (~1 с на тома атласа). Синхронный срез тоже вызывается напрямую
(`routes.py:2103`).

**Почему медленно:** на промахе кэша дисковый I/O и построение массивов занимают поток
цикла событий и тормозят все прочие запросы воркера. Времена — из докстрингов роутов,
не замер этого аудита.

**Лечение:** `asyncio.to_thread` — по действующей конвенции проекта (66 мест уже так).

### Б3. CSV-экспорт диполей — N+1 по сессиям (средняя)

`backend/app/api/routes.py:1737-1747` берёт до 1000 сессий и для каждой последовательно
`await list_session_dipoles`; та сначала проверяет существование сессии (`session.get`),
потом отдельный запрос диполей (`services/results_store.py:738-758`) — ≥2 операций БД на
сессию плюс листинг; лимит 100 000 диполей на сессию до сборки CSV.

**Лечение:** один пакетный запрос диполей по списку session ID, разложить в Python.
Частота — по клику экспорта (низкая), но большие выгрузки заметно медленнее.

### Б4. Составные индексы не покрывают реальные filter+order (средняя, растёт с БД)

Сравнение объявленных индексов с запросами (не план запросов — паттерн):

- `Session`: фильтр `recording_id`/`kind`, сортировка `created_at, id`
  (`results_store.py:683-689`); индекс только по `recording_id` (`models/db.py:98-109`).
- `Analysis`: то же (`results_store.py:888-899`; `models/db.py:201-217`).
- `RecordingRecord`: сортировка `created_at, recording_id`
  (`recording_store.py:224-229`); только unique-индекс digest (`models/db.py:174-187`).
- `ConsiliumRound`: опрашивается и сортируется по `created_at, id`
  (`consilium/rounds_store.py:335-350`); индекс только `case_id` (`models/db.py:552-565`).
- Сообщения чата: сортировка по времени, индекс только `chat_id`
  (`consilium/chat_store.py:107-130`; `models/db.py:785-800`).

**Лечение:** добавить индексы в `models/db.py` + одна миграция
`alembic revision --autogenerate` (паритет ловит `tests/test_migrations.py`).
Попутно: списочный эндпоинт анализов грузит полные ORM-строки, включая JSON
`channels`/`warnings`, которые `_analysis_summary` не отдаёт
(`results_store.py:786-807, 888-899`) — выбрать только нужные колонки.

### Б5. Очистка сирот — 13 последовательных DELETE на сироту (средняя на PostgreSQL)

`backend/app/services/recording_store.py:159-169` грузит все ID записей и на каждого
сироту зовёт `_delete_recording_rows` — 13 последовательных
`session.execute(delete(...))` (`:55-93`). Вызывается на старте (`main.py:75-78`)
и после загрузки файла.

**Лечение:** по одному set-based `DELETE ... WHERE recording_id IN (...)` на таблицу
вместо цикла. На удалённом PostgreSQL экономит ~(13×N−13) RTT.

### Б6. Источники консилиума сканируют все группы и членство глобально (средняя)

`backend/app/services/consilium/sources.py:95-98` зовёт
`group_analysis.list_research_groups`, которая выбирает **все** `GroupAnalysis` и
**все** `GroupAnalysisMember`, а фильтр по кейсу применяет в Python
(`services/group_analysis.py:571-584`).

**Лечение:** SQL-join с фильтром по case_id; работа и память — по размеру данных кейса,
а не глобальных таблиц.

### Б7. Жадные тяжёлые импорты на старте (низкая, опционально)

Цепочка `main.py:12-16` → `api/routes.py:164-225` на уровне модулей тянет MNE, nibabel,
SciPy, Matplotlib (`atlas_contours.py:44-47`, `filter_design.py:38`,
`group_reports.py:34`, `report.py:38`, `spectral.py:83-85`). Увеличивает холодный старт
и базовую память. Оговорка: MNE нужен почти каждому запросу, выигрыш — только
cold-start; по умолчанию **пропустить**, делать только при явном запросе.

## Фронтенд — новые находки (по убыванию ожидаемой отдачи)

### Ф1. Кадры панорамы всё ещё реконсайлят линейки и эпохи по всей таймлинии (высокая)

`TrackStack.tsx:477-485` коммитит один setState на кадр rAF при панораме; на каждый
рендер создаётся новый объект `geometry` (`:634-635`), а компоненты таймлинии не
мемоизированы. Каждый кадр:

- `EpochRuler` мапит **все** ячейки эпох (`TrackRulers.tsx:106-139`);
- `EpochLayer` фильтрует ячейки и мапит границы (`TrackLayers.tsx:214-274`);
- `TimeRuler` перестраивает видимые секундные ячейки и зовёт `cellAtTime` на каждую
  (`TrackRulers.tsx:162-185`), а `cellAtTime` — линейный `find` по списку эпох
  (`shared/lib/viewerLayers.ts:237-245`) — O(секунды × эпохи) на кадр.

**Лечение:** `memo` линеек/оверлеев со стабильными пропами + бинарный поиск в
`cellAtTime`. Частота — на кадр rAF при панораме; растёт с числом эпох.

### Ф2. Hover МРТ перерисовывает все три проекции и сканирует всё на каждое движение (высокая–средняя)

Каждая проекция на каждый `mousemove` ставит локальный hover и зовёт общий колбэк
курсора (`dipoles/MriProjection.tsx:359-367`); `DipolesSection.tsx:283-307` передаёт
курсор всем трём немемоизированным проекциям — движение мыши рендерит все три.
Плюс на hover: `dipoleAt` сканирует все маркеры диполей (`:319-333`), пересчёт
принадлежности атласу (`:370-376`) — `shapeAtPoint` обходит фигуры,
`shapeContainsPoint` трансформирует вершины полигонов на каждый тест
(`shared/lib/atlasContours.ts:186-203, 213-221`).

**Лечение:** `memo` проекций, мемоизация структур хит-теста (диполи/контуры),
троттлинг hover до rAF. Частота — на событие pointermove; дорого при многих
диполях/детальных контурах.

### Ф3. Остаточные мелочи прошлого аудита — не сделаны (низкая)

- `TrackStack.tsx:673-676` — `signal.channels.filter(... visibleChannels.includes ...)`
  без мемоизации, O(каналы × видимые) на каждый рендер, включая кадр панорамы.
  Лечение: `useMemo` + `Set`.
- `EdfPanel.tsx:139-142, 168-176` — `eventOptions`/`channelOptions`/`epochOptions`
  через `Object.entries`/`.map` на рендер; компонент подписан на весь объект params
  (`:108`). Лечение: `useMemo`.

Делать заодно с Ф1, отдельной задачей не стоит.

### Ф4. Экспорт «БД» добирает выбранные записи последовательно (низкая–средняя)

`db/DbSection.tsx:240-255` — `resolveSelection` ждёт каждую недостающую запись в
цикле `for`: последовательные сетевые RTT перед выгрузкой. Лечение: `Promise.all`.
Частота — по клику экспорта; поиск при этом уже с debounce 300 мс и пагинацией
(`:46, 201-223`) — в порядке.

### Ф5. `gcTime: 0` у вкладок консилиума — рефетч на каждый возврат (низкая–средняя)

`CaseWorkspace.tsx:43-47`, `CaseMaterials.tsx:55-73` — запросы с `gcTime: 0` без
`staleTime`; вкладки условно размонтируются (`CaseWorkspace.tsx:229-237`,
`CaseSidebar.tsx:80-84`), поэтому каждый возврат к вкладке теряет кэш и качает заново.
Лечение: небольшой `staleTime`/`gcTime`, чтобы переключение вкладок переиспользовало
кэш. Самое явное улучшение remount/refetch из найденных.

## Предлагаемый порядок работ

1. **Бэкенд, батч A** (Б1–Б3): пагинация readiness до выборки стадий;
   `to_thread` для meta ассетов; пакетный CSV-экспорт диполей. Наибольшая отдача,
   точечные правки + pytest по каждому сервису.
2. **Бэкенд, батч B** (Б4–Б6): индексы + одна alembic-миграция (страж
   `tests/test_migrations.py`); set-based очистка сирот; SQL-фильтр групп в
   источниках консилиума; попутно — узкая выборка колонок в списке анализов.
3. **Фронтенд** (Ф1–Ф5): memo линеек + бинарный поиск `cellAtTime`; memo/hover
   МРТ-проекций; остаточные `useMemo` (Ф3) заодно с Ф1; `Promise.all` в экспорте
   «БД»; кэш-таймеры вкладок консилиума. Vitest по каждому задетому компоненту.
4. **Б7** (ленивые импорты) — только по явному запросу, по умолчанию пропустить.

Проверки по правилам проекта: `pytest`, `ruff check`, `mypy`, паритет миграций;
`npm run test / typecheck / lint / build` (правки UI видны на :8000/ui/ только после
сборки). Новое поведение закрывать тестами; документацию (`docs/history.md`,
правила) обновлять только по фактически сделанному.
